# 토픽·파티션·오프셋은 어떤 관계일까?

[목차](README.md) · [이전: 카프카는 왜 필요하고, 큐와 무엇이 다를까?](why-kafka.md) · [다음: 프로듀서는 메시지를 어느 파티션에 보낼까?](producer-partitioning.md)

## 다루는 범위

토픽과 파티션, 오프셋의 관계를 정리하고, 이 구조에서 나오는 규칙을 따라간다.

- 컨슈머 그룹 안에서 파티션을 나눠 맡는 규칙과 그 이유
- 오프셋 커밋과 "어디서부터 다시 읽는가"
- 보존 기간이 지난 메시지의 삭제와 `auto.offset.reset`
- 파티션 수를 정하는 방법

메시지 키로 파티션을 고르는 방법은 [다음 문서](producer-partitioning.md)에서 다룬다. 이 문서의 숫자와 시나리오는 모두 설명용이다.

## 시작한 질문

알림 서비스가 3시간 동안 죽어 있다가 다시 살아났다. 그동안 주문은 계속 들어왔다.

1. 같은 토픽을 읽는 결제 서비스도 영향을 받을까?
2. 다시 살아난 알림 서비스는 어떤 메시지부터 처리할까?
3. 보존 기간이 1시간이었다면 어떻게 될까?

그리고 주문이 초당 10만 건 들어오는데 토픽이 로그 파일 하나뿐이라면, 어디가 먼저 막힐까?

## 내가 이해한 내용

### 1. 토픽은 이름이고, 실제 로그는 파티션이다

토픽은 논리적인 이름이다. 메시지가 실제로 append되는 로그는 **파티션**이고, 토픽 하나는 여러 파티션으로 나뉜다.

```text
Topic: order-created (파티션 3개)

Partition 0 │ 0 │ 1 │ 2 │ 3 │ 4 │ ──▶   브로커 1
Partition 1 │ 0 │ 1 │ 2 │ ──▶           브로커 2
Partition 2 │ 0 │ 1 │ 2 │ 3 │ ──▶       브로커 3
```

브로커 디스크에는 파티션마다 디렉터리가 따로 있다.

```text
<log.dirs 경로>/
├── order-created-0/
│   ├── 00000000000000000000.log        ← 메시지가 append되는 세그먼트 파일
│   ├── 00000000000000000000.index
│   └── 00000000000000000000.timeindex
├── order-created-1/
└── order-created-2/
```

로그를 나누는 이유는 두 가지다.

- **저장 분산**: 로그가 하나면 브로커 한 대의 디스크와 네트워크를 넘을 수 없다. 파티션은 여러 브로커에 흩어 놓을 수 있다.
- **읽기 병렬화**: 한 그룹 안에서 파티션 하나는 컨슈머 한 대만 읽는다. 로그가 하나면 컨슈머를 10대 띄워도 1대만 일한다.

브로커가 죽었을 때를 대비하는 장치는 파티션이 아니라 복제다.

### 2. 오프셋은 파티션마다 따로 매긴다

오프셋은 파티션 안에서만 의미가 있다. Partition 0의 3번과 Partition 2의 3번은 다른 메시지다. 메시지의 정확한 주소는 **(토픽, 파티션, 오프셋)**이다.

```text
아파트 단지 = 토픽 (order-events)
 ├─ 0동 = Partition 0 : 0호, 1호, ... 42호
 ├─ 1동 = Partition 1 : 0호, 1호, ... 42호
 └─ 2동 = Partition 2 : ... 42호

"42호 가 봐" → "몇 동이요?"
```

그래서 순서도 **파티션 안에서만** 보장된다. 토픽 전체로 보면 순서가 섞일 수 있다.

### 3. 그룹 안에서는 나눠 읽고, 그룹끼리는 각자 다 읽는다

- **파티션 하나는 그룹 안에서 컨슈머 한 대만** 맡는다.
- **컨슈머 한 대는 파티션 여러 개**를 맡을 수 있다.

| 파티션 4개일 때 컨슈머 수 | 배정 |
| --- | --- |
| 1대 | A: P0 P1 P2 P3 |
| 2대 | A: P0 P1 / B: P2 P3 |
| 4대 | 한 대가 하나씩 |
| 6대 | 4대가 하나씩 맡고 2대는 쉼 |

파티션 수가 **한 그룹 안에서 동시에 일할 수 있는 컨슈머 수의 상한**이다. 쉬는 컨슈머는 일하던 컨슈머가 죽으면 리밸런스로 파티션을 넘겨받는 대기 인력이 된다.

이 규칙이 있는 이유는 두 가지다.

```text
두 대가 같은 파티션을 읽는다면?
P0: [10번: order-1 결제] [11번: order-1 취소]

C1이 10번을 처리하는 동안 C7이 11번을 먼저 처리
→ ① 순서가 깨짐
커밋: C1은 "10까지", C7은 "11까지"
→ ② (그룹, 파티션)마다 숫자 하나인 오프셋으로 진행 상황을 표현할 수 없음
```

반면 **그룹이 다르면** 오프셋도 따로라서 같은 메시지를 독립적으로 읽는다.

```text
파티션 3개 토픽
          P0      P1      P2
그룹 X:   X1      X2      X3      (X4, X5 대기)
그룹 Y:   Y1      Y1      Y2      (Y1이 2개 맡음)

→ P0의 메시지 하나는 그룹 수만큼, 총 2번 처리된다
```

그래서 그룹은 **용도(서비스)마다 하나**다. 같은 서비스의 처리량을 늘리려고 그룹을 더 만들면 같은 메시지를 중복 처리하게 된다. 확장은 그룹 **안에서** 컨슈머를 늘리는 것이고, 그 상한이 파티션 수다. 4.x의 Share Group은 이 "파티션 하나에 컨슈머 한 대" 규칙을 바꾼 방식이라 별도로 정리한다.

### 4. 커밋한 위치부터 다시 읽는다

컨슈머는 "어디까지 처리했는지"를 **offset commit**으로 기록한다. 커밋은 내부 토픽 `__consumer_offsets`에 (그룹, 토픽, 파티션)마다 저장되고, 커밋하는 값은 **다음에 읽을 번호**다. 104번까지 처리했다면 105를 커밋한다.

다시 시작한 컨슈머는 "마지막으로 읽은" 위치가 아니라 **"마지막으로 커밋한"** 위치부터 읽는다. 처리와 커밋 사이에는 틈이 있다.

```text
101~105 처리 완료(알림 5건 발송) → 커밋 직전에 장애
→ 커밋된 값은 아직 101
→ 재시작하면 101부터 다시 읽음 → 같은 알림이 두 번 나감
```

그래서 카프카 컨슈머는 기본적으로 **최소 한 번(at-least-once)**이고, 중복이 생겨도 괜찮게 만드는 것이 실무의 숙제다.

### 5. 보존 기간이 지나면 읽었는지와 상관없이 지운다

- 메시지 하나씩이 아니라 **세그먼트(파티션 로그를 나눈 파일 조각) 단위**로 지운다.
- 세그먼트 안의 **가장 최근 메시지**까지 보존 기간이 지나야 그 파일이 통째로 지워진다.
- 삭제 검사도 주기적으로(기본 5분마다) 돈다.

그래서 보존 기간이 1시간이어도 정확히 1시간에 지워지지 않고, 조금 더 남아 있을 수 있다.

커밋한 위치가 이미 지워졌다면 `auto.offset.reset` 설정을 따른다. 이 설정은 새로 만든 그룹처럼 커밋이 아예 없을 때도 쓰인다.

```text
알림 그룹의 커밋 위치: 120
3시간 뒤 남아 있는 로그: 300번부터  ← 120~299는 삭제됨
```

| `auto.offset.reset` | 동작 | 결과 |
| --- | --- | --- |
| `latest` (기본값) | 가장 최신 위치부터 | 그동안 들어온 메시지를 모두 건너뜀 |
| `earliest` | 남아 있는 가장 오래된 위치(300)부터 | 120~299만 유실 |
| `none` | 예외 발생 | 사람이 판단 |
| `by_duration:PT1H` (4.0부터) | 지금 시각에서 지정한 시간만큼 이전 위치부터 | 시간 기준으로 되돌아가 읽음 |

어느 쪽이든 지워진 메시지는 돌아오지 않는다. 그래서 보존 기간은 **컨슈머가 멈춰 있을 수 있는 가장 긴 시간보다 넉넉하게**(기본값 7일) 잡고, **Consumer Lag**(쌓였지만 아직 안 읽은 양)를 모니터링한다.

### 6. 파티션 수는 계산해서 넉넉히 정한다

| | 너무 적으면 | 너무 많으면 |
| --- | --- | --- |
| 처리량 | 컨슈머를 늘려도 쉬는 컨슈머만 생긴다 | 충분하다 |
| 나중에 늘리기 | 늘리는 순간 키 순서가 깨질 위험이 있다 | 늘릴 일이 거의 없다 |
| 브로커 | 부담이 적다 | 파티션(복제본)마다 디렉터리와 세그먼트·인덱스 파일이 생겨 열린 파일과 메모리가 는다 |
| 프로듀서 | 배치가 잘 모인다 | 키가 있으면 파티션마다 배치가 따로라 배치가 덜 찬다 |
| 장애 복구 | 빠르다 | 죽은 브로커가 리더였던 파티션마다 새 리더를 뽑아야 한다 |
| 리밸런스 | 가볍다 | 다시 나눠 줄 파티션이 많다 |

필요한 수는 이렇게 계산한다.

```text
필요한 파티션 수 = max( 목표 처리량 ÷ 프로듀서가 파티션 하나에 쓰는 속도,
                       목표 처리량 ÷ 컨슈머 한 대가 파티션 하나를 처리하는 속도 )

(설명용 숫자) 목표 60MB/s, 프로듀서 20MB/s, 컨슈머 6MB/s
→ max(3, 10) = 10
```

- 보통 **컨슈머 쪽이 병목**이다. 메시지마다 DB 저장이나 외부 API 호출을 기다리기 때문이다. 두 속도는 직접 성능 테스트로 잰다.
- 1~2년 뒤 **성장분**을 곱한다. 1.5배면 최소 15개다.
- **나누기 좋은 수**로 올린다. 15(약수 1, 3, 5, 15)보다 18이나 24가 컨슈머 몇 대에도 고르게 나뉘고, 브로커 3대의 배수라 브로커마다 고르게 놓인다.

키 순서가 중요한 토픽을 그래도 늘려야 한다면 방법은 두 가지다.

```text
방법 1. 잠깐 멈추고 늘리기
  프로듀서 일시 중지 → lag 0까지 대기 → 파티션 증설 → 프로듀서 재개

방법 2. 새 토픽으로 옮기기
  넉넉한 새 토픽 생성 → 옛 토픽을 다 읽은 뒤 프로듀서·컨슈머 전환
```

둘 다 비용이 커서 **트래픽이 가장 몰릴 때는 쓸 수 없다**. 그때 쓸 수 있는 현실적인 방법은 컨슈머 한 대의 처리 속도를 올리는 것(묶어서 DB에 넣기, 외부 호출 줄이기 등)이다. 처리 속도를 올리려고 한 컨슈머 안에서 스레드를 여러 개 쓴다면, 같은 키는 같은 스레드로 보내야 순서가 유지된다.

브로커 기본 설정은 `num.partitions=1`이다. 토픽 자동 생성이 켜져 있으면 오타 난 토픽도 파티션 1개로 생기므로, 운영에서는 파티션 수를 정해 직접 만드는 경우가 많다.

## 헷갈렸던 점

| 처음의 생각 | 정리한 내용 |
| --- | --- |
| 알림 서비스는 마지막으로 **읽은** offset부터 처리한다 | 마지막으로 **커밋한** 위치, 즉 다음에 읽을 번호부터다. 처리했지만 커밋 전에 죽으면 다시 처리한다. |
| 보존 기간 1시간이면 정확히 1시간 뒤 메시지가 삭제된다 | 세그먼트 단위로, 세그먼트의 최신 메시지 기준으로, 주기적인 검사 때 지운다. 조금 더 남을 수 있다. |
| 처리량을 늘리려면 그룹을 늘린다 | 그룹을 늘리면 같은 메시지를 중복 처리한다. 확장은 그룹 안에서 컨슈머를 늘리는 것이다. |
| 컨슈머 두 대가 파티션 하나를 나눠 맡으면 빨라진다 | 그룹 안에서 파티션 하나는 한 대만 맡는다. 순서와 숫자 하나뿐인 오프셋을 지키기 위해서다. (1회차 RabbitMQ 비교 때도 같은 지점에서 헷갈렸다.) |
| `order-events`의 offset 42번이라고 하면 메시지를 찾을 수 있다 | 오프셋은 파티션마다 따로라 파티션 번호가 있어야 한다. |
| 파티션이 많으면 순서를 장담할 수 없다 | 순서는 파티션 **수가 바뀔 때** 깨진다. 처음부터 고정해 두면 같은 키는 계속 같은 파티션으로 간다. 많은 파티션의 문제는 순서가 아니라 비용이다. |
| 트래픽이 1.5배가 되면 파티션도 1.5배로 하면 된다 | 그건 최소치다. 실제로는 나누기 좋은 수, 브로커 수의 배수로 올린다. |
| lag이 쌓일 때 파티션을 늘리면 밀린 메시지도 나눠 처리된다 | 이미 쌓인 메시지는 원래 파티션에 그대로 있다. 새로 들어오는 메시지만 늘어난 파티션으로 나뉜다. |

## 남은 질문

- 컨슈머가 들어오고 나갈 때 리밸런스는 어떻게 진행될까? 4.x의 새 리밸런스 프로토콜은 무엇이 다를까?
- 커밋은 언제, 어떤 방식(자동·수동, 동기·비동기)으로 해야 중복과 유실을 줄일 수 있을까?
- Share Group은 "파티션 하나에 컨슈머 한 대" 규칙을 어떻게 바꾸고, 대신 무엇을 포기할까?
- 세그먼트와 인덱스 파일은 실제로 어떻게 생기고 지워질까?
