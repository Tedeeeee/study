# 프로듀서는 메시지를 어느 파티션에 보낼까?

[목차](README.md) · [이전: 토픽·파티션·오프셋은 어떤 관계일까?](topic-partition-offset.md)

## 다루는 범위

프로듀서가 보낼 파티션을 고르는 순서, 키가 있을 때와 없을 때의 차이, 카프카가 보장하는 순서의 범위를 정리한다. 키를 고르는 기준과, 파티션 수를 늘릴 때 키와 파티션의 짝이 바뀌는 문제도 함께 본다.

직렬화, 커스텀 파티셔너, 배치가 전송되는 시점(`linger.ms`, `batch.size`)은 프로듀서 문서를 이어 쓰면서 추가한다. 이 문서의 키, 해시값과 파티션 번호는 모두 설명용이다.

## 시작한 질문

주문 1번의 "생성"은 Partition 0에, "취소"는 Partition 2에 들어갔다. 두 파티션을 서로 다른 컨슈머가 읽는다면 "취소"가 먼저 처리될 수 있지 않을까? 같은 주문의 "생성 → 결제 → 취소" 순서는 어떻게 지킬까?

## 내가 이해한 내용

### 1. 메시지는 키와 값으로 이뤄진다

```text
ProducerRecord
├── topic:     order-events
├── partition: (보통 비워 둠)
├── key:       "order-1"                 ← 파티션을 고르는 기준 (없어도 됨)
├── value:     {"type":"CANCELED", ...}  ← 실제 내용
└── headers, timestamp
```

키는 메시지 하나를 식별하는 ID(PK)가 아니다. **어떤 메시지들을 같은 줄에 세울지 정하는 묶음 기준**이다. 같은 키를 가진 메시지가 여러 개 있는 게 정상이다.

### 2. 파티션을 고르는 순서

프로듀서 안의 파티셔너가 정한다. 토픽의 파티션 수는 브로커에서 받아 온 메타데이터로 안다.

```text
1. 레코드에 partition을 직접 지정했나?  → 그 파티션
2. 키가 있나?                          → 해시(키) % 파티션 수
3. 둘 다 없나?                         → 스티키 파티셔닝
```

커스텀 파티셔너를 설정하면 2·3번 대신 그 로직이 쓰인다.

### 3. 키가 있으면 같은 키는 항상 같은 파티션으로 간다

```text
파티션 3개, 키 = 주문 ID

"order-1" (생성) → murmur2 해시 → % 3 = 0 → Partition 0
"order-2" (생성) →               % 3 = 2 → Partition 2
"order-1" (취소) →               % 3 = 0 → Partition 0   ← 같은 곳
```

같은 키를 해시하면 언제나 같은 값이 나오므로, order-1의 이벤트는 Partition 0에 순서대로 쌓인다. Partition 0은 그룹 안에서 컨슈머 한 대만 읽으니 처리도 그 순서대로 된다. 그래서 카프카에서 실무적으로 보장받는 순서는 **토픽 전체의 순서가 아니라 같은 키 안의 순서**다.

### 4. 키가 없으면 스티키 파티셔닝으로 보낸다

키가 없으면 지킬 순서가 없으니 목표는 **골고루, 빠르게**다. 프로듀서는 메시지를 하나씩 보내지 않고 **파티션별 배치에 모았다가** 보낸다는 점이 중요하다.

```text
라운드 로빈 (2.4 이전 기본값)
  m1→P0  m2→P1  m3→P2  m4→P0 ...
  → 배치 여러 개가 동시에 조금씩 차서, 덜 찬 배치가 나가거나 오래 기다림

스티키 (2.4부터 기본값)
  m1~m100 → P0 배치를 채워서 전송 → m101~m200 → P1 → ...
  → 한 파티션에 붙어서 배치 하나를 빨리 채우고 다음 파티션으로 넘어감
```

3.3부터는 이 방식이 다듬어졌다(KIP-794).

- 파티션마다 대략 `batch.size`만큼 보낸 뒤 다음 파티션으로 넘어가서, 오래 보면 파티션별 양이 더 고르다.
- 응답이 느린 브로커의 파티션에는 덜 보낸다. (`partitioner.adaptive.partitioning.enable`, 기본값 true)
- 예전 파티셔너 클래스(`DefaultPartitioner`, `UniformStickyPartitioner`)는 4.0에서 삭제됐고, 이 로직은 프로듀서 안에 들어 있다. 키 해시 방식은 그대로다.

### 5. 키는 순서가 필요한 가장 작은 단위로 고른다

배달 앱에서 주문마다 `주문 생성 → 결제 → 조리 시작 → 배달 출발 → 배달 완료` 이벤트가 들어오고, 같은 주문의 이벤트는 순서대로 처리해야 한다면:

| 키 | 순서 | 결과 |
| --- | --- | --- |
| 키 없음 | 깨짐 | 같은 주문의 이벤트가 여러 파티션에 흩어진다 |
| 가게 ID | 지켜짐 | 대형 가게가 있으면 파티션 하나에 몰린다 (hot partition) |
| **주문 ID** | 지켜짐 | 필요한 만큼만 묶여서 가장 고르게 퍼진다 |
| 고객 ID | 지켜짐 | 대체로 괜찮지만 필요 이상으로 크게 묶는다 |

순서를 지켜 주는 후보는 여러 개다. 그중 **요구사항이 말하는 순서 범위와 딱 맞는 가장 작은 단위**를 고른다. 요구사항이 "같은 고객의 여러 주문 사이에도 순서가 필요하다"로 바뀌면 고객 ID가 답이 된다.

### 6. 파티션 수를 늘리면 키와 파티션의 짝이 바뀐다

```text
(설명용 숫자)
파티션 3개일 때 order-77: hash % 3 = 1 → P1
   P1: [..., 생성, 결제]   ← 컨슈머가 아직 못 읽고 밀려 있음 (lag)

파티션 6개로 늘린 뒤 order-77: hash % 6 = 4 → P4
   P4: [취소]               ← 새 파티션이라 밀린 게 없어서 바로 처리됨

→ "취소"가 "결제"보다 먼저 처리됨
```

- 파티션을 늘리면 리밸런스가 일어나 기존 컨슈머들이 새 파티션까지 나눠 맡는다. 맡을 컨슈머가 없는 파티션이 생기는 게 아니라 **키 순서가 깨지는 게** 문제다.
- 키가 없고 순서도 상관없는 토픽(접근 로그 등)은 이 문제가 없다.
- 파티션은 늘릴 수만 있고 줄일 수 없다. 그래서 키 순서가 중요한 토픽은 처음에 파티션 수를 넉넉히 정한다. ([파티션 수 정하기](topic-partition-offset.md#6-파티션-수는-계산해서-넉넉히-정한다))
- 늘린 직후의 새 파티션에는 커밋된 오프셋이 없다. 그래서 `auto.offset.reset=latest`(기본값)이면, 컨슈머가 새 파티션을 넘겨받기 전에 들어온 메시지를 건너뛸 수 있다. 이건 키가 없는 토픽에도 해당한다. Kafka 4.4 운영 문서는 파티션이 늘어날 수 있는 토픽에 `by_duration`을 권한다.

## 헷갈렸던 점

| 처음의 생각 | 정리한 내용 |
| --- | --- |
| 파티션을 늘리면 새 파티션을 맡을 컨슈머가 없어서, 컨슈머도 같이 늘려야 한다 | 리밸런스로 기존 컨슈머가 새 파티션까지 나눠 맡는다. 처리량을 늘리려면 컨슈머를 늘려야 하지만, 버려지는 파티션은 없다. 키 토픽에서 진짜 위험한 건 키와 파티션의 짝이 바뀌어 순서가 깨지는 것이다. |

## 예제와 확인 결과

- 키, 해시값, 파티션 번호는 모두 설명용이다. 실제 murmur2 해시를 계산한 결과가 아니다.
- 아직 실행한 결과는 없다. 실습 때 확인할 것:
  - 콘솔 프로듀서에서 `parse.key=true`, `key.separator`로 키를 붙여 보내고, 같은 키가 같은 파티션에 들어가는지 보기
  - 키 없이 많은 메시지를 보내 파티션별로 묶음 단위로 들어가는지 보기
