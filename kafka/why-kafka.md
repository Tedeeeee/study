# 카프카는 왜 필요하고, 큐와 무엇이 다를까?

[목차](README.md) · [다음: 토픽·파티션·오프셋은 어떤 관계일까?](topic-partition-offset.md)

## 다루는 범위

서비스끼리 직접 호출할 때 생기는 문제에서 출발해, 카프카가 그 문제를 어떻게 푸는지 정리한다. RabbitMQ 같은 전통적인 메시지 큐와 **저장 방식, 일을 나누는 단위, 고르는 기준**을 비교하고, 카프카의 처리량이 높은 이유와 클러스터 전체 구조를 짧게 본다.

이 문서의 서비스 이름, 토픽 이름과 숫자는 모두 설명용이다. 설치·기동과 KRaft의 자세한 동작은 별도 문서에서 다룬다.

## 시작한 질문

주문이 완료되면 결제·재고·알림·정산 서비스가 모두 그 사실을 알아야 한다. 주문 서비스가 각 서비스를 하나씩 호출하면 안 될까? 중간에 메시지 브로커를 둔다면, 왜 하필 카프카일까? RabbitMQ와는 무엇이 다를까?

## 내가 이해한 내용

### 1. 직접 호출하면 서로 묶인다

```text
[주문 서비스] ──HTTP──▶ 결제
             ──HTTP──▶ 재고
             ──HTTP──▶ 알림   ← 여기가 5초 걸리면?
             ──HTTP──▶ 정산
```

| 문제 | 설명 |
| --- | --- |
| 지연·장애 전파 | 알림 서비스가 느리거나 죽으면 주문 응답도 느려지거나 실패한다. [파일과 I/O](../operating-system/file-io.md)에서 본 "외부 결과를 기다리는 동안 스레드가 묶인다"는 문제가 그대로 생긴다. |
| 강한 결합 | 포인트 적립을 새로 붙이려면 주문 서비스 코드를 고쳐서 다시 배포해야 한다. |
| 속도 차이 | 트래픽이 몰리면 전체 처리 속도가 가장 느린 서비스에 맞춰진다. |

### 2. 카프카를 가운데 두면

주문 서비스는 "주문이 완료됐다"는 **이벤트를 토픽 끝에 한 번 쓰고** 끝낸다. 각 서비스는 자기 속도로 읽어 간다.

```text
[주문 서비스] ──append──▶ Topic: order-created
                         ┌───┬───┬───┬───┬───┬───┐
                         │ 0 │ 1 │ 2 │ 3 │ 4 │ 5 │ ──▶ 계속 뒤에 추가
                         └───┴───┴───┴───┴───┴───┘
                                   ▲           ▲
             결제 그룹: 다음은 2번 ─┘           └─ 알림 그룹: 다음은 5번
```

- 주문 서비스는 누가 이벤트를 읽는지 모른다. 포인트 적립을 추가해도 주문 코드는 그대로다.
- 알림이 느려도 주문 응답과 상관없다. 카프카가 중간에서 버퍼 역할을 한다.
- 알림이 죽었다가 살아나면 멈췄던 위치부터 이어서 읽는다.

여기서 이벤트는 "현재 상태"가 아니라 **"일어난 일"**이다. "주문이 생성됐다", "결제가 완료됐다"처럼 시간 순서로 계속 흘러가는 이벤트의 흐름을 스트림이라고 부른다.

반대로 결과를 사용자에게 바로 돌려줘야 하는 일(결제 승인 여부를 화면에 바로 표시하기 등)은 동기 호출이 맞다. 카프카는 **나중에 처리해도 되는 일, 여러 곳에 퍼뜨려야 하는 일, 흐름을 기록해 둘 일**에 맞다.

### 3. 큐는 "처리하면 사라지는 할 일 목록", 카프카는 "계속 남는 기록장"

| | 전통적인 큐 (RabbitMQ 기본 큐) | 카프카 |
| --- | --- | --- |
| 전달 방식 | 브로커가 컨슈머에게 밀어준다(push) | 컨슈머가 직접 가져간다(pull) |
| 처리 후 메시지 | ack를 받으면 삭제 | 지우지 않는다. 보존 기간(기본 7일)이나 용량 한도를 넘어야 삭제 |
| 읽은 위치 관리 | 브로커가 메시지마다 상태(대기·처리 중·완료)를 관리 | 컨슈머 그룹마다 "어디까지 읽었는지"(오프셋) 숫자만 기록 |
| 여러 시스템이 같은 데이터 받기 | 시스템마다 큐를 두고 Exchange가 복사 | 같은 토픽을 그룹마다 따로 읽음 (복사 없음) |
| 다시 읽기 | 이미 지워져서 어렵다 | 오프셋만 되돌리면 된다 (replay) |

카프카는 메시지가 성공적으로 처리됐는지 자체를 모른다. 아는 건 그룹마다 꽂아 둔 책갈피(오프셋)뿐이다. 그래서 삭제 기준도 "읽었는지"가 아니라 **시간과 용량**이다. 아무도 안 읽어도 보존 기간이 지나면 지워지고, 모두 읽었어도 보존 기간 전에는 지워지지 않는다.

### 4. 줄과 그룹: RabbitMQ는 한 몸, 카프카는 분리

"메시지 하나는 한 명만 처리한다"는 점은 둘이 같다. 다른 것은 **줄 하나에 몇 명이 붙고, 일을 무슨 단위로 나누느냐**다.

```text
RabbitMQ: 큐가 줄이자 그룹
          ┌▶ [알림 큐] ◀─ 알림 서버 1, 2, 3    ← 메시지 단위로 나눠 받음
Exchange ─┤   (복사)
          └▶ [검색 큐] ◀─ 검색 서버 1, 2

카프카: 줄(파티션)과 그룹(오프셋)이 분리
[파티션 0] [파티션 1] [파티션 2]      ← 모든 그룹이 공유 (복사 없음)
   알림 그룹: 0→서버1, 1→서버2, 2→서버3   ← 파티션 단위로 나눠 맡음
   검색 그룹: 0·1→서버1, 2→서버2
```

| 역할 | RabbitMQ | 카프카 |
| --- | --- | --- |
| 메시지가 쌓이는 줄 | 큐 | 파티션 |
| 한 시스템의 몫과 진행 상황 | 큐 (메시지마다 상태) | 컨슈머 그룹 (오프셋) |
| 같은 시스템 안에서 일 나누기 | 메시지 단위 | 파티션 단위 |
| 줄 하나에 붙는 작업자 | 여러 명 | 그룹 안에서 한 명 |
| 작업자를 늘리면 | 늘린 만큼 빨라진다 | 파티션 수까지만 빨라진다 |
| 오래 걸리는 메시지 하나 | 그 작업자만 묶인다 | 같은 파티션의 뒤 메시지가 기다린다 |
| 순서 | 작업자가 여럿이면 보장 안 됨 | 파티션 안에서 보장 |

카프카가 파티션 하나에 한 명만 붙게 한 이유는 오프셋이 **숫자 하나**이기 때문이다. 두 명이 같은 파티션을 동시에 읽으면 "어디까지 처리했는지"를 숫자 하나로 표현할 수 없고, 순서도 깨진다. RabbitMQ는 메시지마다 상태를 따로 기억하니까 한 줄에 여러 명이 붙어도 된다.

### 5. 무엇을 고를까

둘 다 대부분의 일을 할 수 있다. 차이는 **그 일을 브로커가 대신 해 주느냐, 내가 코드로 짜느냐**다.

| 질문 | "예"라면 |
| --- | --- |
| 처리한 뒤에도 남겨 둬야 하나? | 카프카 |
| 같은 메시지를 여러 시스템이 각자 받나? (앞으로 늘어나나?) | 카프카 |
| 키별 순서가 중요한가? | 카프카 |
| 처리 시간이 제각각이고 작업자를 유연하게 늘려야 하나? | RabbitMQ (또는 카프카 Share Group) |
| 메시지별 재시도나 DLQ가 필요한가? | RabbitMQ (또는 카프카 Share Group) |
| 우선순위, 지연 메시지, 복잡한 라우팅이 필요한가? | RabbitMQ |

- 메시지가 **"해야 할 일"**이면 RabbitMQ, **"일어난 일"**이면 카프카가 자연스럽다.
- 카프카 4.x의 Share Group은 RabbitMQ식 메시지 단위 분배를 카프카에 들여온 기능이다. 한 파티션을 여러 컨슈머가 나눠 읽고, 메시지마다 ack하며, 4.4부터는 DLQ도 지원한다. 그래서 이미 카프카를 운영 중이라면 단순한 작업 큐 때문에 RabbitMQ를 따로 들일 이유는 줄었다.
- 반대로 RabbitMQ에도 지우지 않고 다시 읽는 Streams 기능이 생겼다. 둘의 경계는 흐려지는 중이다.

### 6. 카프카의 처리량이 높은 이유

| 이유 | 설명 |
| --- | --- |
| 순차 쓰기 | 로그 끝에 붙이기만 하니 디스크 쓰기가 항상 순차 I/O다. |
| Page Cache 활용 | 데이터를 자기 메모리에 따로 쌓지 않고 OS의 Page Cache에 맡긴다. 밀리지 않고 따라 읽는 컨슈머는 Cache hit으로 메모리에서 바로 읽는다. ([파일과 I/O](../operating-system/file-io.md)) |
| 배치 | 프로듀서가 메시지를 묶어서 보내고, 브로커는 그 묶음을 풀지 않고 저장하며, 컨슈머도 묶음으로 가져간다. 압축도 묶음 단위다. |
| zero-copy | 컨슈머에게 보낼 때 애플리케이션 메모리로 복사하지 않고 Page Cache에서 바로 네트워크로 보낸다. 단, TLS를 쓰면 암호화 때문에 이 이점이 사라진다. |
| 단순한 브로커 | 메시지마다 상태·ack·라우팅을 관리하지 않는다. 받아서 이어 쓰고, 요청한 위치부터 내준다. |
| 파티션 분산 | 한 토픽의 파티션이 여러 브로커에 흩어져 있어 브로커를 늘리면 처리량도 늘어난다. |

```text
일반적인 방식: 디스크 → Page Cache → (복사) 애플리케이션 메모리 → (복사) 네트워크
카프카:        디스크 → Page Cache ───────────────────────────────▶ 네트워크
```

### 7. 전체 구조와 바뀐 점

```text
 프로듀서 ──쓰기──▶ ┌──────────────── 카프카 클러스터 ────────────────┐
                   │  브로커 1          브로커 2          브로커 3      │
                   │  orders-P0(리더)   orders-P1(리더)   orders-P2(리더)│
                   │  orders-P1(복제)   orders-P2(복제)   orders-P0(복제)│
                   │  컨트롤러: 클러스터 메타데이터 관리                  │
                   └──────────────────────────────────────────────────┘
                          │ 읽기                     │ 읽기
                 알림 그룹(컨슈머 3대)        검색 그룹(컨슈머 2대)
```

- **브로커**는 카프카 서버 한 대, **클러스터**는 브로커들의 묶음이다.
- 파티션마다 다른 브로커에 **복제본**을 둔다. 원본 역할은 리더, 복사본은 팔로워다.
- **컨트롤러**는 어떤 토픽이 있는지, 파티션별 리더가 누구인지 같은 메타데이터를 관리한다.
- 예전(3.x)에는 이 메타데이터를 외부 ZooKeeper에 저장했다. 지금(4.0부터)은 ZooKeeper가 완전히 제거되고, 카프카 안의 컨트롤러들이 Raft로 합의해 `__cluster_metadata` 로그에 기록하는 **KRaft** 방식만 남았다. 메타데이터도 "끝에 붙이는 로그 + 따라 읽기"로 관리하는 셈이다.

## 헷갈렸던 점

| 처음의 생각 | 정리한 내용 |
| --- | --- |
| "메시지 하나를 컨슈머 하나만 처리한다"는 건 읽으면 메시지가 사라진다는 뜻이다 | 서로 다른 두 질문이다. ① 누가 처리하나(둘 다 한 명) ② 처리 후 남나(RabbitMQ는 삭제, 카프카는 남음). RabbitMQ는 ①을 지키려고 꺼내서 지우고, 카프카는 메시지를 두고 오프셋으로 ①을 지킨다. |
| RabbitMQ는 큐마다 작업자가 한 명씩 붙는다 | 반대다. RabbitMQ 큐에는 작업자 여러 명이 붙고, 카프카는 그룹 안에서 파티션 하나에 한 명만 붙는다. |
| RabbitMQ 큐는 카프카 파티션과 같고, 그룹 개념이 없다 | 줄이라는 구조는 비슷하다. 다만 RabbitMQ 큐는 그룹 역할까지 겸해서, 서로 다른 시스템은 각자 큐를 가져야 한다. |
| 환영 메일, 영상 인코딩, 30분 뒤 취소는 RabbitMQ만 할 수 있다 | 모두 카프카로도 가능하다. 차이는 재시도·지연·긴 작업 처리를 브로커가 설정만으로 해 주느냐, 내가 코드로 구현하느냐다. |
| 결제 서비스가 알림 토픽에 메시지를 전달한다 | 결제와 알림은 같은 토픽을 각자 읽는 별개의 그룹이다. 브로커는 밀어주지 않고 컨슈머가 가져가므로, 알림이 죽어 있어도 결제는 영향이 없다. |

## 예제와 확인 결과

- 주문 이벤트, 이메일 작업 큐, 결제·알림 그룹 예시는 모두 설명용이다.
- 아직 카프카를 띄워서 실행한 결과는 없다. 실습은 이론 회차를 진행한 뒤 Docker `apache/kafka`(KRaft)로 한다.
