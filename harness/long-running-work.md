# 몇 시간짜리 일은 어떻게 이어 갈까?

[목차](README.md) · [이전: AI가 검사를 통과해야만 끝나게 하려면?](completion-gate.md) · [다음: 여러 에이전트로 나누면 무엇이 좋아지고 무엇이 비싸질까?](multi-agent.md)

## 다루는 범위

컨텍스트 창 하나에 다 안 들어가는 긴 작업을 하네스가 어떻게 이어 가게 하는지 정리한다.

- 창 하나로 긴 일을 하면 생기는 두 가지 실패
- 교대 세션: 준비 담당과 작업 담당, 그리고 바깥 루프
- 창과 창을 잇는 인수인계 파일 네 가지
- 작업 담당 창 하나의 흐름: 출근 → 점검 → 일 → 퇴근
- 압축과 리셋, 컨텍스트 불안

여러 에이전트를 동시에 나눠 돌리는 구조는 [10번 주제](README.md#공부-계획)에서 다룬다.

## 시작한 질문

8장까지는 창 하나 안에서 AI를 안내하고 막는 법을 봤다. 그런데 "홈쇼핑 만들어 줘" 같은 일은 몇 시간이 걸리고, 창 하나의 컨텍스트에 다 들어가지 않는다.

1. 창 하나에 안 들어가는 일은 어떻게 이어 갈까?
2. 새 창은 앞 창의 대화를 모르는데, 어떻게 이어서 일할까?
3. 창이 차면 압축으로 버틸까, 창을 새로 열까?

## 내가 이해한 내용

### 1. 창 하나로는 안 끝나는 일과 두 가지 실패

이 장에서 세션은 대화 하나, 컨텍스트 하나를 말한다. 채팅 앱으로 치면 창 하나다. 3장에서 본 대로 API는 상태가 없어서, 세션은 매번 통째로 다시 보내는 대화 목록이다. 새 세션을 연다는 건 그 목록을 빈 것으로 다시 시작한다는 뜻이다.

Anthropic이 긴 작업을 창 하나에 맡겨 보니 실패가 두 가지로 나왔다.

| 실패 | 무슨 일이 생기나 |
| --- | --- |
| 한 번에 다 하려다 중간에 끊김 | 컨텍스트가 차서 기능이 반쯤 만들어진 채, 기록도 없이 창이 끝난다. 다음 창은 뭐가 어디까지 됐는지 몰라 추측하느라 시간을 쓴다. |
| 일찍 "다 됐다"고 선언함 | 뒤의 창이 둘러보니 뭔가 많이 만들어져 있어서 "완료됐네요" 하고 끝낸다. |

### 2. 교대 세션: 준비 담당과 작업 담당

해결책은 교대 근무다. 창을 여러 개로 나누고, 창 하나에 기능 하나만 맡긴다.

```text
창 #1 (준비 담당)  app_spec 읽기 → 기능 목록·init.sh·진행 기록·첫 커밋 → 닫기
창 #2 (작업 담당)  인수인계 읽기 → 기능 하나 → passes: true·기록·커밋 → 닫기
창 #3 (작업 담당)  인수인계 읽기 → 다음 기능 하나 → … → 닫기
…
```

- 요청은 채팅이 아니라 파일(`app_spec.txt`)로 미리 준다. 첫 창이 그걸 읽고 기능 목록으로 쪼갠다.
- 준비 담당과 작업 담당은 같은 모델, 같은 하네스다. 시스템 프롬프트와 도구가 같고, 첫 지시만 다르다. 7장에서 본 대로 "역할 이름"일 뿐 다른 AI가 아니다.
- 창마다 새 대화다. 창 #3은 창 #2에서 오간 대화를 전혀 모른다. 남은 건 폴더의 파일뿐이다.
- 새 창을 여는 건 AI의 판단이 아니라 바깥 코드다. Anthropic 예제(`autonomous-coding/agent.py`)의 루프를 줄이면 이렇다.

```python
while True:
    client = create_client(project_dir, model)   # 새 컨텍스트(새 창)
    if is_first_run:
        prompt = get_initializer_prompt()         # 준비 담당 지시
        is_first_run = False                      # 딱 한 번만
    else:
        prompt = get_coding_prompt()              # 작업 담당 지시
    async with client:
        status, response = await run_agent_session(client, prompt, project_dir)
    await asyncio.sleep(3)                        # 3초 뒤 다음 창
```

사용자는 스크립트를 한 번 실행하고 터미널도 하나만 보인다. 그래도 안에서는 루프가 돌 때마다 창이 새로 열린다. "프로그램은 하나, 세션은 여러 개"다.

비슷해 보이는 것들과 비교하면 이렇다.

| | 교대 세션 (이 장) | 서브 에이전트 (4장) | Codex `/goal` |
| --- | --- | --- | --- |
| 창 | 기능마다 새 창 | 부모 창 안에서 자식을 띄움 | 창 하나에서 턴만 계속 붙임 |
| 누가 다음을 시작하나 | 바깥 `while` 루프 | 부모 AI가 도구로 부름 | 대화가 멈추면 하네스가 다음 턴 시작 |
| 결과가 가는 곳 | 폴더의 파일 | 부모 창 컨텍스트에 요약으로 | 같은 창의 대화에 쌓임 |

서브 에이전트와 교대 세션은 같이 쓸 수도 있다. 작업 담당 창 하나가 일하다가 탐색용 서브 에이전트를 띄울 수 있다. 교대 세션은 창과 창 사이, 서브 에이전트는 창 안의 이야기다.

Codex `/goal`도 "사람이 매번 시키지 않아도 긴 일을 알아서 이어 간다"는 느낌은 같다. 하지만 세션을 나누지 않는다. 같은 대화에 턴을 붙이고, 길어지면 압축으로 버티는 쪽이다. 이어 갈 때 끼워 넣는 프롬프트에는 8~9장 생각이 글로 들어 있다.
- 기억보다 현재 작업 폴더와 외부 상태를 믿어라.
- 성공 기준을 더 작고 쉬운 일로 바꾸지 마라.
- 완료는 요구 사항마다 증거로 확인하기 전까지 안 된 것으로 본다.
- 같은 장애가 연속 3턴 반복될 때만 `blocked`로 표시해라.

### 3. 창과 창을 잇는 인수인계 파일

앞 창은 파일을 폴더에 남기고 닫히고, 다음 창은 시작하자마자 그걸 꺼내 읽는다. 다음 창에 무언가를 보내 주는 게 아니라, 책상에 두고 퇴근하는 것이다.

| 파일 | 알려 주는 것 | 준비 담당 | 작업 담당 (매 창) |
| --- | --- | --- | --- |
| `feature_list.json` (기능 목록) | 뭘 해야 하고 뭐가 끝났나 | 만든다 | 하나 골라 끝내면 `passes`를 `true`로 |
| `claude-progress.txt` (진행 기록) | 뭘 했고 어디서 막혔나 | 만든다 | 한 일, 문제, 다음 할 일, 진행률을 덧붙인다 |
| git 커밋 | 코드가 어떻게 바뀌어 왔나 | 첫 커밋 | 기능 하나마다 깨끗한 상태로 커밋 |
| `init.sh` | 일 시작 전에 환경을 어떻게 켜나 | 만든다 | 창을 열면 실행한다 |

기능 목록은 칸이 정해진 JSON이다.

```json
[
  {
    "category": "functional",
    "description": "이 기능이 무엇을 확인하는지",
    "steps": ["1: 페이지로 이동", "2: 동작 수행", "3: 결과 확인"],
    "passes": false
  }
]
```

txt가 아니라 JSON인 이유는 두 가지다.

1. 코드도 이 파일을 읽는다. 예제 하네스는 이 파일이 없으면 준비 담당, 있으면 작업 담당 프롬프트를 고르고(`is_first_run = not tests_file.exists()`), 창 사이마다 `passes: true` 개수를 세서 진행률을 보여 준다. AI는 이 파일을 읽고 `passes`를 바꾸고, 코드는 이 파일을 보고 역할을 고르고 진행률을 센다.
2. Anthropic 글에 따르면 모델은 Markdown보다 JSON을 함부로 고치거나 덮어쓸 가능성이 낮다.

진행 기록은 "여기서 막혔다" 같은 메모라서 자유로운 글(txt)로 둔다.

**목록은 처음에 확정하고, 이후에는 `passes`만 바꾼다.** 순서는 준비 담당이 "기본 기능 먼저"로 정한다. 항목은 나뉘어 있어도 서로 완전히 독립은 아니다. 로그인이 있어야 장바구니를 테스트할 수 있다. 작업 담당 프롬프트에는 하지 말 것이 이렇게 적혀 있다.

- 항목 삭제, 설명 수정, 테스트 단계 수정, 합치기, 순서 바꾸기

준비 담당 프롬프트에는 "이후 세션에서 기능을 지우거나 고치는 건 재앙(CATASTROPHIC)이다"라고까지 적혀 있다. 목록이 곧 8장의 "끝"의 정의라서 그렇다. 작업 담당이 목록을 고칠 수 있으면 어려운 항목을 빼고 "다 됐다"고 할 수 있다. 5장에서 본 "AI가 테스트 코드를 고칠 수 있으면 검사가 의미 없다"와 같은 문제다.

작업 담당은 일을 고르지만 기준은 정해져 있다. `passes: false` 중 우선순위가 제일 높은 것 하나다. 누가 출근해도 같은 일을 집게 되니, 결과로 보면 리스트 자체가 배정표다. 실시간으로 일을 나눠 주는 부모나 팀장이 없을 뿐이다. 그래서 처음에 순서를 잘 정하는 준비 담당의 일이 중요하다.

### 4. 작업 담당 창 하나의 흐름

작업 담당 프롬프트(`prompts/coding_prompt.md`)는 "이건 새 컨텍스트 창이고, 이전 세션에 대한 기억이 없다"로 시작한다. 그래서 창 하나의 흐름이 STEP 1~10으로 정해져 있고, 묶으면 회사원의 하루와 같다.

| 단계 | 하는 일 | 왜 |
| --- | --- | --- |
| 출근 (STEP 1) | `pwd`, `ls`, `app_spec.txt`, 기능 목록, 진행 기록, `git log`, 남은 개수 확인 | 기억이 없으니 파일로 상황을 파악한다 |
| 점검 (STEP 2~3) | `init.sh`로 서버를 켜고, 이미 `passes: true`인 핵심 기능 1~2개를 다시 테스트. 깨졌으면 `false`로 되돌리고 그것부터 고친다 | 깨진 걸 모르고 그 위에 쌓지 않기 위해 |
| 일 (STEP 4~6) | 안 끝난 것 중 맨 위 하나를 골라 만들고, 브라우저로 사람처럼 확인 | 창 하나에 기능 하나. "이번 세션에 하나만 끝내도 괜찮다" |
| 퇴근 (STEP 7~10) | 확인한 것만 `passes: true`, 커밋, 진행 기록 갱신, 커밋 안 된 변경 없이 앱이 돌아가는 상태로 끝내기 | 다음 창이 반쯤 된 코드 위에서 시작하지 않게 |

**점검을 왜 매번 하나.** `passes: true`는 "그때 확인했다"는 기록이지 "지금도 된다"는 보장이 아니다. 앞사람이 서둘러 확인을 허술하게 했을 수도 있다. 하지만 더 큰 이유는 회귀 버그다. 확인을 제대로 했어도, 그 뒤 창이 다른 기능을 만들면서 공용 코드를 고쳐 이미 되던 기능을 깨뜨렸을 수 있다. PR마다 CI가 기존 테스트까지 다시 돌리는 것과 같다. 200개 전부가 아니라 핵심 1~2개만 돌려서, 적은 비용으로 나중의 큰 비용을 막는다.

**왜 브라우저로 확인하나.** Anthropic이 실제로 겪은 문제 때문이다. 단위 테스트나 curl까지는 돌려 놓고, 실제 화면에서는 기능이 안 되는데 완료로 표시하는 일이 많았다. 브라우저 자동화 도구를 주니 결과가 크게 좋아졌다. 그래서 프롬프트에 "curl로만 확인하지 마라", "JavaScript로 화면을 건너뛰지 마라", "스크린샷으로 확인한 뒤에만 `passes`를 바꿔라"가 들어 있다.

**깨끗한 퇴근**이 첫 번째 실패(반쯤 만든 채로 끊김)를 막고, **고정된 목록 + 확인 후에만 `true`**가 두 번째 실패(일찍 완료 선언)를 막는다.

이 예제에서는 이 흐름 전부가 프롬프트(글)다. 6~8장 기준으로 보면 "`passes` 말고 다른 칸이 바뀌면 막는 훅"이나 "퇴근 전에 커밋 안 된 변경이 있으면 막는 Stop 게이트"처럼 코드로 옮길 수 있는 자리가 있다.

### 5. 압축과 리셋, 컨텍스트 불안

창이 차면 길이 두 개다.

| | 압축 (compaction) | 리셋 (context reset) |
| --- | --- | --- |
| 하는 일 | 같은 창에서 앞부분을 요약으로 바꾸고 계속 | 창을 통째로 비우고 새 에이전트로 시작 |
| 예 | Claude Code 자동 압축(4장), Codex `/goal` | 이 장의 교대 세션 |
| 좋은 점 | 흐름이 이어진다 | 깨끗하게 새로 출발한다 |
| 대가 | 깨끗한 출발이 아니다. 요약하면서 세부가 빠질 수 있다 | 인수인계 자료가 상태를 충분히 담아야 하고, 구조가 복잡해지고 토큰과 시간이 더 든다 |

**컨텍스트 불안(context anxiety).** Anthropic 글의 정의는 모델이 "컨텍스트 한계라고 믿는 지점에 다가가면 일을 일찍 마무리하기 시작한다"는 것이다. 시험 시간이 끝나 간다고 착각해서 남은 문제를 대충 찍고 내는 것과 같다. 단계를 건너뛰고, 검증을 대충 하고, "나머지는 다음에"라며 멈춘다. 실제로는 자리가 남아 있어도 그렇다. "불안"은 감정이 아니라 이런 행동 패턴에 붙인 이름이다.

불안과 압축은 하는 주체가 다르다.

```text
대화가 길어짐
  → (모델) "자리가 별로 없겠네" → 서둘러 마무리   ← 컨텍스트 불안
  → (하네스) 실제로 차면 압축                       ← 압축
```

불안은 압축 때문에 생기는 게 아니라 창이 길어져서 생긴다. 압축이 일어나기 전에도, 압축이 없어도 생길 수 있다.

**모델에 따라 부품이 바뀐 사례.**

- Sonnet 4.5는 불안이 강해서 "압축만으로는 부족"했다. 그래서 리셋과 구조화된 인수인계를 썼다.
- Opus 4.5는 그 행동을 "스스로 대부분 없앴다". 그래서 리셋을 통째로 빼고 Claude Agent SDK의 자동 압축만 남겼다. 리셋과 압축을 함께 쓴 게 아니라 바꾼 것이다.
- Managed Agents 글은 Opus 4.5 기준으로 컨텍스트 리셋이 "dead weight(쓸데없는 짐)"가 됐다고 쓴다.

바꾼 핵심 이유는 "압축이 좋아져서"가 아니라 "모델이 좋아져서 리셋의 대가만 남았다"는 것이다. 리셋은 "모델이 창이 차면 서둘러 끝낸다"는 약점을 메우려고 붙인 부품이었다. 하네스 부품은 모델이 혼자 못 하는 것에 대한 가정이라서, 모델이 바뀌면 다시 본다. 이 내용은 12장으로 이어진다.

**불안이 남아 있는 모델이라면 하네스로 메울 수 있다.** 하네스는 모델의 버릇 자체를 고치지는 못하지만, 그 버릇이 결과를 망치지 않게 막을 수 있다. 리셋이 바로 그런 부품이었다.

| 방법 | 종류 | 무엇을 막나 |
| --- | --- | --- |
| 리셋 + 인수인계 파일 | 코드 | 창이 길어질 일 자체를 없앤다 |
| 창 하나에 기능 하나 | 글 + 구조 | 한 창의 일을 작게 잡아 덜 길어지게 한다 |
| 서브 에이전트 (4장) | 구조 | 무거운 탐색을 밖으로 빼서 메인 창을 가볍게 한다 |
| 완료 게이트 (8장) | 코드 | 서둘러 "다 됐다"고 해도 검사를 통과 못 하면 못 끝낸다 |
| "서두르지 마라" 지시 | 글 | 서두르는 행동 자체를 줄이려 한다 |

마지막 방식은 실제 프롬프트에도 있다. Anthropic 예제 작업 담당 프롬프트는 "시간은 무제한이다. 제대로 될 때까지 충분히 시간을 써라"로 끝나고, Codex `/goal` 이어 가기 프롬프트에는 "예산이 거의 다 됐다는 이유로 목표를 완료 처리하지 마라"가 있다. 다만 글은 안 지킬 수도 있으니(6장), 불안이 강한 모델에는 리셋이나 게이트 같은 코드 장치가 더 확실하다.

Claude Code를 쓰는 입장에서는 CLAUDE.md 지시, Stop 훅 게이트, 서브 에이전트, 직접 `/clear`하고 인수인계 파일로 이어 가기는 바로 할 수 있다. 창을 자동으로 새로 여는 리셋 루프는 기본 기능이 아니라서, 예제처럼 바깥 스크립트를 직접 짜야 한다.

**리셋을 빼는 것과 파일을 지우는 것은 다른 얘기다.** 리셋과 압축은 컨텍스트 하나 안의 작업을 안정적으로 끌고 가는 방식이고, 파일은 작업의 진행 현황과 "끝"의 기준을 담은 기록이다. 교대 근무를 없애고 한 사람이 쭉 맡아도 체크리스트와 업무 일지는 버리지 않는다.

1. 한 사람이 쭉 일해도 기억은 흐려진다. 압축하면 대화의 세부가 요약되면서 빠지지만, 파일은 그대로 남는다.
2. 체크리스트는 인수인계용이 아니라 "끝"의 기준이다. 혼자 일해도 서둘러 "다 됐다"고 할 수 있고, 그걸 기능 목록과 `passes`가 막는다.

실제로 Anthropic도 리셋은 뺐지만, 에이전트끼리 파일로 주고받는 구조는 그대로 뒀다.

### 6. 이미 하고 있던 방식

이 저장소에서 새 창을 열면 README와 `git log`로 어디까지 했는지 확인하고 이어 간다. 이 공부 대화도 컨텍스트가 차서 한 번 이어졌는데, 그래도 계속할 수 있었던 건 README와 진행 기록 덕분이다. 교대 세션 패턴을 손으로 하고 있던 셈이고, Anthropic 예제는 그걸 코드로 자동으로 돌린 것이다.

| 작업 담당이 각각 서브 에이전트로 돈다 | 서브 에이전트는 부모 창 안에서 띄우고 결과가 부모에게 돌아간다. 교대 세션은 부모 없이 창을 새로 열고, 파일로만 이어진다. |
| 하나의 세션에서 작업만 나눠서 한다 | 세션이 여러 개다. 프로그램(루프)과 폴더는 하나지만, 루프가 돌 때마다 대화를 새로 연다. |
| 내게 세션은 채팅 창 하나인데, 이게 창 하나에서 일어나는 일인가 | 그 기준으로 기능마다 새 창을 여는 것이다. 창 #3은 창 #2의 대화를 모른다. |
| Codex `/goal`이 나왔을 때 그 느낌이다 | 긴 일을 알아서 이어 간다는 느낌은 같지만, `/goal`은 창 하나에서 턴을 붙인다. 세션을 나누는지로 보면 정반대다. |
| 준비 담당이 네 가지 자료를 "넘겨 준다" | 폴더에 남기고 닫히면 다음 창이 꺼내 읽는다. 처음 만드는 건 준비 담당이지만, 작업 담당도 매 창 읽고 갱신한다. `init.sh`는 "한 일"이 아니라 "환경 켜는 법"이다. |
| 일의 순서를 이리저리 조합하며 진행한다 | 나누고 순서를 정하는 건 준비 담당이 한 번만 한다. 작업 담당은 순서를 못 바꾸고 `passes`만 바꾼다. |
| 기능 목록은 txt 같은 기록이다 | JSON이다. 코드도 읽어서 역할을 고르고 진행률을 세고, 모델이 덜 망가뜨린다. |
| 작업 담당이 하고 싶은 일을 잡는다 | 맨 위의 안 끝난 것 하나를 잡으니, 결과로 보면 리스트가 배정표다. 실시간으로 배정하는 사람이 없을 뿐이다. |
| 압축 때문에 AI가 서두른다 | 불안은 창이 길어져서 모델이 스스로 서두르는 것이고, 압축은 하네스가 하는 일이다. 모델은 "곧 압축된다"가 아니라 "자리가 없다"고 판단한다. |
| 4.5 전까지는 리셋, 그 뒤로는 압축과 함께 쓴다 | 리셋이 필요했던 건 Sonnet 4.5, 뺀 건 Opus 4.5다. 그리고 함께 쓴 게 아니라 리셋을 빼고 압축으로 바꿨다. |
| 모델에 불안이 있으면 어쩔 수 없다 | 하네스로 메울 수 있다. 리셋 자체가 그런 부품이었고, 작게 쪼개기, 서브 에이전트, 완료 게이트도 있다. |

### 확인 문제와 내 답

| 문제 | 내 답의 요지 | 결과 |
| --- | --- | --- |
| 1. 긴 작업을 창 하나에 맡겼을 때의 대표 실패 두 가지와, 교대 방식에서 각각을 막는 장치 | 컨텍스트 한계로 압축하면서 길을 잃고 계획에서 벗어난다. 그래서 목록과 우선순위를 만들고, 다음 창이 목록·진행·git·sh를 보고 이어 간다 → 실패 2(일찍 완료 선언)가 빠져서 다시 풀기: 각 작업에 `passes`를 걸어 다 끝났는지 확인한다 | 재답변 통과. 실패 1은 "반쯤 된 채 기록 없이 끊김"이고 창 하나에 기능 하나·깨끗한 퇴근으로 막는다. 실패 2는 고정된 목록 + 확인 후에만 `true` 세트로 막는다 |
| 2. 이미 `passes: true`인 기능을 왜 매번 다시 테스트하나 (토큰 낭비 아닌가) | 서두르다 상태만 `true`로 바꿨을 수 있다 → 핵심 몇 개만 돌려 적은 토큰으로 점검한다 → 힌트(세션 5는 확인을 제대로 했다) 뒤: 세션 6이 장바구니를 만들다 `UserService`를 고쳤을 수 있어서 | 재답변 통과. 핵심은 회귀 버그다. `passes: true`는 "그때 확인했다"는 기록이지 "지금도 된다"는 보장이 아니다 |
| 3. "Opus 4.5부터 리셋을 뺐으니 우리도 파일까지 다 지우고 압축만 쓰자"에서 맞는 부분과 틀린 부분 | 왜 뺐는지부터 봐야 한다. 무조건 압축은 안 좋을 수 있는데 설명은 못 하겠다 → 다시 풀기: 리셋을 빼는 것과 파일을 지우는 건 다르다. 파일은 진행 현황이고, 리셋과 압축은 컨텍스트 안 작업의 안정성을 위한 것이다 | 재답변 통과. 보충: 리셋을 뺀 이유는 그 모델의 불안이 줄어서라 우리 모델로 확인해야 한다. 압축하면 세부가 빠지니 기록이 필요하고, 목록은 혼자 일해도 필요한 "끝"의 기준이다 |

## 예제와 확인 결과

2026-11-28에 GitHub API(`gh api`)로 아래 소스를 직접 열어 읽었다. API 키가 필요해서 실행하지는 않았다.

- `anthropics/claude-quickstarts`의 `autonomous-coding/` (커밋 `4a4224b`)
  - `agent.py`: `while True` 루프, 반복마다 `create_client(...)`로 새 컨텍스트, 첫 실행만 준비 담당 프롬프트, 다음 세션까지 3초 대기(`AUTO_CONTINUE_DELAY_SECONDS = 3`). `is_first_run`은 `feature_list.json`이 있는지로 정한다.
  - `progress.py`: `feature_list.json`에서 `passes`가 `true`인 개수를 세서 "Progress: N/M"을 출력한다.
  - `prompts/initializer_prompt.md`: 최소 200개, 기본 기능 먼저 정렬, 전부 `passes: false`로 시작, 이후 세션에서 기능을 지우거나 고치는 건 "CATASTROPHIC". 시간이 남으면 제일 높은 기능 하나부터 시작해도 된다는 선택 항목이 있다.
  - `prompts/coding_prompt.md`: STEP 1~10. "YOU CAN ONLY MODIFY ONE FIELD: passes", 삭제·수정·합치기·순서 바꾸기 금지, 브라우저 자동화로만 확인.
  - 루프 본문에는 `max_iterations` 말고 "전부 `true`면 멈춘다"는 조건이 보이지 않았다.
- `openai/codex`의 `codex-rs/ext/goal/` (main, 커밋 `065e18b`)
  - `src/runtime.rs`: 목표를 대화 ID에 묶어 저장하고(`get_thread_goal(self.thread_id())`), 대화가 멈추면 목표가 `Active`일 때 같은 대화에 턴을 시작한다(`start_goal_turn_if_idle`). 새 대화를 여는 코드는 없다.
  - `templates/goals/continuation.md`: 현재 상태를 기준으로, 목표 축소 금지, 완료 증명, 연속 3턴 막힐 때만 `blocked`.
  - `templates/goals/budget_limit.md`: 토큰 예산을 다 쓰면 하네스가 `budget_limited`로 바꾸고 마무리하라고 끼워 넣는다.
  - `/goal`에서 압축이 어떻게 일어나는지는 확인하지 않았다.

이 장의 창 그림과 표는 설명용이다.
