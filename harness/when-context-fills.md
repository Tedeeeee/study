# 컨텍스트가 차면 무슨 일이 생길까?

[목차](README.md) · [이전: AI는 내 규칙을 어떻게 "기억"할까?](instructions-and-memory.md) · [다음: 도구와 권한은 어떻게 설계할까?](tools-and-permissions.md)

## 다루는 범위

컨텍스트 창이 차 갈 때 생기는 문제와, 하네스가 창을 정리하는 방법들을 따라간다.

- 창은 꽉 차기 전부터 문제가 생긴다
- 정리 방법은 순서대로 하는 단계가 아니라 각자 작동하는 때가 다르다
- 압축: 쌓인 대화를 요약본으로 바꾼다
- 필요할 때만 불러오기(just-in-time): 이름만 올려 두고 쓸 때 꺼낸다
- 도구 결과 짧게 받기
- 하위 에이전트: 긴 탐색은 다른 창에서 하고 요약만 받는다
- 설명서 말고 지도: 지시 파일을 짧게 만든다

도구 결과를 어떻게 설계하는지는 [5번 주제](README.md#공부-계획)에서, 여러 에이전트를 나누는 구조는 10번 주제에서 자세히 다룬다.

## 시작한 질문

이 공부를 하던 대화의 최근 요청에서 모델이 읽은 입력은 549,980 토큰이었다. 컨텍스트 창이 100만 토큰이니 절반 넘게 찬 셈이다.

1. 창이 꽉 차기 전까지는 괜찮은 걸까?
2. 하네스는 창이 차지 않게 무엇을 할까?

## 내가 이해한 내용

### 1. 문제는 꽉 차기 전부터 시작된다

| 문제 | 언제부터 | 증상 | 출처 |
| --- | --- | --- | --- |
| 흐려짐(context rot) | 한도보다 훨씬 전부터 | 토큰이 늘수록 앞 내용을 덜 정확하게 떠올린다. 처음 준 지시가 약해진다 | Anthropic, 컨텍스트 엔지니어링 글 |
| 서두름(context anxiety) | 창이 차 간다고 느낄 때 | 일을 덜 끝냈는데 서둘러 마무리하려 한다(Sonnet 4.5에서 관찰) | Anthropic, 긴 작업용 하네스 설계 글 |
| 비용과 속도 | 계속 | 요청마다 읽는 입력이 커진다. 캐시가 줄여 주지만 0은 아니다 | 3장의 실제 기록 |
| 한도 초과 | 창 크기를 넘을 때 | 요청 자체를 보낼 수 없다 | |

Anthropic은 이걸 "attention budget"(주의력 예산)으로 설명한다. 모델이 한 번에 집중할 수 있는 양에는 한계가 있어서, 넣는 게 많을수록 하나하나에 쓰는 주의가 줄어든다. 그래서 창이 100만 토큰이라고 다 채워도 괜찮은 게 아니다. 반만 차도 이미 흐려지기 시작한다.

### 2. 정리 방법은 순서가 아니라 각자 작동하는 때가 다르다

| 방법 | 언제 작동하나 | 누가 정하나 |
| --- | --- | --- |
| 필요할 때만 불러오기 | 항상. 설계로 깔려 있고, 꺼내는 순간은 그때그때 | 하네스가 이름만 올리고, 꺼낼지는 모델이 판단 |
| 도구 결과 짧게 받기 | 도구 결과가 나올 때마다 | 하네스 코드 |
| 하위 에이전트로 나누기 | 큰 탐색 일이 생겼을 때 | 모델(또는 사람)이 판단 |
| 압축 | 창이 찰 때 | 하네스가 자동으로, 또는 사람이 `/compact` |
| 설명서 말고 지도 | 지시 파일을 쓸 때(일하기 전) | 사람이 설계 시점에 |

자동차 안전장치처럼 안전벨트(항상), ABS(급제동 때), 에어백(충돌 때)이 각자 맡은 상황에서 켜진다. 시간 순서로 보면 필요할 때만 불러오기가 처음부터 끝까지 돌고, 압축은 창이 찰 때의 대청소다. 목표는 아끼는 것만이 아니라, 아끼면서도 필요한 건 잘 보이게 유지하는 것이다.

### 3. 압축: 쌓인 대화를 요약본으로 바꾼다

```text
압축 전: [시스템][CLAUDE.md][대화 1][도구 결과]…[대화 300][도구 결과]
압축 후: [시스템][CLAUDE.md][지금까지의 요약본][최근 파일 몇 개]
```

압축은 원본을 버리는 손실 압축이라 무엇이 살아남는지가 중요하다. Claude Code 문서 기준으로는 이렇다.

| | 무엇 |
| --- | --- |
| 디스크에서 다시 넣어 줌 | 시스템 프롬프트, 프로젝트 루트 CLAUDE.md, 경로 조건 없는 규칙 파일, auto memory, 계획 파일 |
| 다시 읽어 줌 | 최근 수정한 파일 최대 5개, 불러온 스킬 본문(스킬당 5,000토큰, 합쳐서 25,000토큰까지) |
| 요약본으로 바뀜 | 지금까지의 대화와 도구 결과 |
| 사라짐 | 대화로만 준 지시, 하위 폴더 CLAUDE.md, 특정 경로용 규칙(그 폴더를 다시 건드리면 다시 불러온다) |
| 영향 없음 | 백그라운드 명령, 하위 에이전트 |

그래서 오래 지켜야 할 지시는 대화로 말하지 말고 파일로 옮긴다. `/compact 결제 로직 위주로`처럼 초점을 줄 수 있고, CLAUDE.md의 "Compact Instructions" 절로 압축 방식을 정해 둘 수도 있다. 자동 압축 시작 시점은 `/autocompact`로 바꾼다.

압축하는 방식은 하네스마다 다르다.

| 하네스 | 압축 방식 |
| --- | --- |
| Claude Code | 구조화된 요약본으로 바꾸고, 최근 파일 5개와 지시 파일을 다시 넣는다 |
| Hermes | `agent/context_compressor.py`. 도구 출력부터 줄이고, 그래도 크면 싼 보조 모델이 중간 대화를 요약한다. 맨 앞과 맨 뒤는 지킨다 |
| Codex | 한도(`auto_compact_limit`)를 넘으면 OpenAI 서버의 압축 API를 부르고, 결과는 암호화된 항목으로 돌아온다. 압축 직전·직후에 훅을 걸 수 있다 |

다른 건 조건이 달라서다. Claude Code와 Codex는 자기 회사 모델에 맞춰 만들어서 모델 회사가 압축 기능을 직접 제공할 수 있다. Hermes는 아무 모델이나 붙이니 특정 서버 기능에 기댈 수 없어 압축기를 직접 짰고, 상주하며 오래 돌고 사용자가 API 비용을 직접 내니 싼 보조 모델을 쓴다. 앞뒤를 지키는 건 모델이 긴 입력의 처음과 끝은 잘 보고 중간을 잘 놓친다는 연구("Lost in the Middle")와 맞닿아 있다. 다만 Hermes 문서가 이 연구를 이유로 들었는지는 확인하지 않았다. 어느 쪽이 더 잘 압축하는지는 같은 일을 시켜 재 봐야 알 수 있다.

요약까지 안 가는 더 가벼운 방법도 있다. Anthropic은 오래된 도구 결과만 지우는 걸 "가장 가벼운 손질(lightest touch)"이라고 부르고, API에도 그 기능(context editing)이 있다.

압축의 대가는 두 가지다. 대화를 통째로 다시 쓰니 캐시를 거의 처음부터 다시 쌓아야 하고, 요약은 언제나 뭔가를 잃는다. 그래서 압축은 자주 하는 정리가 아니라 창이 찰 때 하는 큰 정리다.

### 4. 필요할 때만 불러오기(just-in-time)

책상에는 무엇이 있는지만 올려 두고 실제 내용은 쓸 때 꺼낸다. "just-in-time"은 원래 재고를 쌓지 않고 필요할 때 만드는 제조 방식에서 온 말이다. Java의 JIT 컴파일러가 실행하다가 자주 쓰는 메서드만 그때 기계어로 바꾸는 것과 같은 생각이다.

| 무엇 | 처음에 올리는 것 | 나중에 꺼내는 것 | 하네스 |
| --- | --- | --- | --- |
| 스킬 | 이름과 설명(합쳐서 1,536자에서 자른다) | 본문, 그다음 보조 파일 | Claude Code |
| 스킬 | 목록을 컨텍스트 창의 2% 안에서만 | 고른 스킬의 `SKILL.md` 전체 | Codex |
| 스킬 | 길이 제한으로 자른 설명 목록 | 쓸 때 본문 | Hermes |
| MCP 도구 | 이름만 | 쓸 때 ToolSearch로 정의 | Claude Code |
| 메모리 | 목차 | 상세 파일 | Claude Code |
| 하위 폴더 규칙 | 없음 | 그 폴더 파일을 건드릴 때 | Claude Code |
| 코드 | CLAUDE.md만 | 모델이 glob·grep으로 찾아 읽기 | Claude Code |

```text
1층: 설명만 (항상 책상 위)       SKILL.md 맨 위의 name, description
        ↓ 모델이 "이거 필요하다" 판단
2층: SKILL.md 본문
        ↓ 본문이 가리키면
3층: 보조 파일 (reference.md 등)
```

스킬을 꺼내는 것도 1장의 요청서다. 모델이 설명을 보고 필요하다고 판단하면 `Skill { skill: "claude-api" }` 같은 요청서를 쓰고, 하네스가 본문을 도구 결과로 돌려준다. MCP 도구도 `ToolSearch`로 정의를 먼저 꺼낸 뒤 쓴다. 사람이 직접 부를 수도 있고(Claude Code는 `/스킬이름`, Codex는 `$스킬이름`), Claude Code는 `disable-model-invocation`으로 모델은 못 부르고 사람만 부르게 막을 수도 있다.

| 장점 | 대가 |
| --- | --- |
| 도구 수백 개, 스킬 수십 개도 이름 몇 줄로 끝난다 | 모델이 필요하다고 알아채야 꺼낸다. 못 알아채면 없는 것과 같다 |
| 상관없는 내용이 주의를 뺏지 않는다 | 꺼내는 데 도구 호출이 한 번 더 든다 |

모델은 1층의 설명만 보고 꺼낼지 정한다. 그래서 설명이 곧 검색 키다. 설명이 흐리면 필요할 때 안 꺼내고, 너무 넓으면 아무 때나 꺼낸다. Claude Code 스킬에 `when_to_use` 칸이 따로 있고, Anthropic이 도구 설명을 "신입에게 설명하듯" 쓰라고 하는 이유다. DB 인덱스와 같다. 인덱스가 엉망이면 필요한 행을 못 찾는다.

압축과는 서로 돕는다. 불러오기를 잘하면 창이 천천히 차서 압축이 덜 필요하다. 그리고 압축 뒤에도 파일은 디스크에 있으니 다시 읽으면 되지만, 대화로만 말한 건 디스크에 없어서 영영 사라진다. 그래서 Anthropic은 내용 자체보다 가벼운 참조(파일 경로, 검색어, 링크)를 들고 있으라고 한다.

### 5. 도구 결과 짧게 받기

도구 결과가 나올 때마다 하네스 코드가 크기를 조절한다. mini-swe-agent는 명령 출력이 1만 자를 넘으면 줄여서 넣고, Claude Code는 도구 응답을 기본 25,000토큰으로 제한한다. 결과를 애초에 짧고 신호가 강하게 설계하는 법은 5장에서 다룬다.

### 6. 하위 에이전트: 긴 탐색은 다른 창에서

많이 읽어야 하는 일은 새 컨텍스트 창을 가진 하위 에이전트에게 맡기고 요약만 받는다. HumanLayer는 이걸 "context firewall"이라고 부른다. 탐색하느라 쌓이는 자료가 메인 창으로 넘어오지 않게 막는다는 뜻이다.

이 공부를 하면서 하네스 자료를 조사할 때 실제로 하위 에이전트를 썼다.

| 하위 에이전트 | 각자 창에서 쓴 토큰 | 도구 호출 |
| --- | --- | --- |
| Claude Code 문서 조사 | 133,066 | 27 |
| 하네스 엔지니어링 글 조사 | 81,103 | 14 |
| Anthropic 블로그 조사 | 97,849 | 20 |
| Codex 문서 조사 | 107,752 | 50 |
| Hermes 문서 읽기 | 81,197 | 6 |
| 합계 | 약 50만 | 117 |

이 읽기는 전부 다른 창에서 일어났고, 메인 창에는 각자 1,500단어 정도의 보고서만 올라왔다.

| | 내용(Claude Code 문서 기준) |
| --- | --- |
| 받는 것 | 메인이 쓴 위임 메시지, 기본 환경 정보, CLAUDE.md(Explore·Plan 타입은 제외) |
| 안 받는 것 | 메인의 대화 기록, 메인이 읽은 파일, 메인이 불러온 스킬 |
| 돌려주는 것 | 최종 보고서 하나 |

Anthropic 글에 따르면 하위 에이전트는 탐색에 수만 토큰을 쓰고 1,000~2,000토큰짜리 요약만 돌려준다. Hermes(`tools/delegate_tool.py`)와 Codex도 같은 방식이다.

| 대가 | 설명 |
| --- | --- |
| 요약에서 빠지는 것 | 메인은 보고서에 적힌 것만 안다 |
| 위임 메시지를 잘 써야 함 | 하위 에이전트는 받은 글만 보고 일한다. 목표와 범위를 빠짐없이 적어야 한다 |
| 비용 | 전체로는 토큰을 더 쓴다. Anthropic의 리서치 시스템에서 멀티 에이전트는 일반 채팅보다 토큰을 약 15배 썼다 |

**언제 띄우나.** 하위 에이전트를 띄우는 것도 `Agent`라는 도구라서 모델이 고른다. 사용자가 시키지 않았는데 조사를 하위 에이전트로 뺀 것도 그래서다. 판단 기준은 Claude Code가 그 도구 설명에 적어 둔 가이드다.

| | 기준(Claude Code `Agent` 도구 설명 요약) |
| --- | --- |
| 써라 | 서로 독립적인 일을 동시에 돌릴 수 있을 때, 여러 파일·자료를 넓게 읽어야 할 때, 흐름을 막지 않아야 할 곁가지 일 |
| 쓰지 마라 | 도구 몇 번이면 끝나는 일, 대상을 이미 아는 단순 조회. 애매하면 띄우지 마라 |
| 따져 봐라 | 비용, 위임과 보고 때의 정보 손실, 가설을 건네면 확인만 해 오는 편향 |
| 위임할 때 | 동료에게 하듯 목표, 이미 배제한 것, 범위를 분명히 적어라 |

Codex는 문서상 사용자가 요청하거나 AGENTS.md나 스킬에 적혀 있을 때 띄운다. 같은 기능인데 누가 띄울지 정하는 방식이 다르다.

그래서 내 스킬에 "조사는 항상 하위 에이전트로" 같은 규칙을 쓰면, 내장 하네스가 이미 가진 "언제 쓰지 말지"까지 담긴 판단을 한 줄로 덮어써서 오히려 잘못 쓰게 될 수 있다. 반대로 "이 폴더는 파일이 수천 개라 여기를 훑을 땐 하위 에이전트로"처럼 내장 하네스가 모르는 사정을 보태거나, `.claude/agents/`에 새 역할을 정의하는 건 도움이 된다. 먼저 내장 하네스에 이미 판단 기준이 있는지 보고, 있으면(Claude Code) 덮어쓰지 말고 정보만 보태고, 없으면(Codex) 적는다.

### 7. 설명서 말고 지도

> "give Codex a map, not a 1,000-page instruction manual" — OpenAI

지시 파일에는 모든 걸 쓰지 말고 어디에 뭐가 있는지만 쓴다. 지시 파일은 매 요청마다 전부 올라가고(3장), 길수록 중요한 게 묻히고(이 장 1절), 내장 지침과 부딪히는 문장이 늘고(6절), 필요할 때만 열게 하면 창이 깨끗해진다(4절).

| 자료 | 내용 |
| --- | --- |
| OpenAI | AGENTS.md는 약 100줄짜리 목차. 자세한 건 저장소의 `docs/`에 두고 가리키기만 한다 |
| HumanLayer | AGENTS.md를 60줄 아래로 유지한다 |
| Claude Code 문서 | CLAUDE.md는 짧게 |
| Osmani | 스타일 가이드가 아니라 조종사의 체크리스트 |
| HumanLayer가 인용한 ETH 연구 | LLM이 써 준 지시 파일은 성능을 떨어뜨리고 비용을 20% 넘게 늘렸다 |

```markdown
# 프로젝트 지도 (설명용)
- 구조: server/(Nest API), web/(React). 계층 규칙은 docs/architecture.md
- 명령: 테스트 `npm test`, 타입 검사 `npm run typecheck`
- 꼭 지킬 것 3가지 (어기면 검사가 막는다)
- 더 알아야 할 때: 도메인 용어는 docs/glossary.md, API 규칙은 docs/api.md
```

하네스도 돕는다. Claude Code는 `.claude/rules/`의 규칙 파일에 `paths`를 적으면 그 경로의 파일을 건드릴 때만 불러온다. Codex는 폴더마다 AGENTS.md를 두고 작업 폴더까지의 경로에 있는 것만 합치며, 기본 32KiB까지만 읽는다.

OpenAI 글은 저장소에 버전 관리되는 것만 에이전트가 볼 수 있다고 한다("agent legibility"). 슬랙에서 정한 결정이나 사람 머릿속 규칙은 에이전트에게 없다. 그래서 지도가 가리킬 실제 문서가 저장소 안에 있어야 한다.

사람들이 개인 스킬을 지우는 이유도 같다. 내장 하네스와 겹치거나(중복), 부딪히거나(충돌), 예전 모델의 약점을 메우던 요령(낡은 가정)이면 오히려 방해가 된다. 정리할 때 보는 기준은 다섯 가지다.

1. 내장 하네스가 이미 하는 일인가? → 지운다
2. 내장 지침과 부딪히나? → 지우거나 고친다
3. 예전 모델의 약점을 메우던 요령인가? → 지금 모델로 다시 시험하고, 필요 없으면 지운다
4. 우리 팀만 아는 정보인가? → 남긴다. 대신 짧게
5. 반드시 지켜져야 하나? → 스킬이 아니라 훅이나 검사 코드로 옮긴다

## 헷갈렸던 점

| 처음의 생각 | 정리한 내용 |
| --- | --- |
| 1단계는 책상 정리하는 것이다 | 1단계는 왜 정리가 필요한지(꽉 차기 전부터 생기는 문제)였다. 정리 방법은 그다음이다. |
| 필요할 때만 불러오기는 압축 다음에 하는 단계다 | 순서대로 하는 단계가 아니다. 시간상으로는 오히려 불러오기가 처음부터 돌고, 압축은 창이 찰 때 한다. |
| 정리 방법들이 전부 동시에 이뤄진다 | 각자 작동하는 때가 따로 있다. 다만 몇 개는 늘 켜져 있어서 결과적으로 여러 개가 같이 돈다. |
| 컨텍스트를 압축하고 절약하는 방법들이다 | 아끼는 것만이 아니라, 아끼면서도 필요한 건 잘 보이게 유지하는 방법들이다. |
| Hermes는 개인이 만들어서 개인의 견해가 많이 들어갔다 | Nous Research가 만든 오픈소스다. 견해가 들어간 건 맞지만, 비용·모델 독립성·긴 입력의 특성 같은 이유가 있는 설계다. |
| Hermes는 Claude Code나 Codex보다 압축 능력이 대단하다 | 다른 조건에 맞춘 다른 선택이다. 어느 쪽이 나은지는 같은 일을 시켜 재 봐야 안다. 대신 압축기 코드를 볼 수 있어서 배우기엔 좋다. |
| 하위 에이전트는 시켜야 띄운다 | `Agent`도 도구라서 모델이 도구 설명의 기준을 보고 골라 띄운다. |
| 스킬에 "이럴 땐 하위 에이전트를 써라"라고 적으면 된다 | 내장 판단을 덮어쓰면 오히려 잘못 쓰게 될 수 있다. 내장 하네스가 모르는 정보만 보탠다. 하네스마다 다르다(Codex는 적는 게 원래 방식). |

### 공부하며 던진 질문

이 장도 문제 풀이 없이 진행했다.

- **JIT는 Java의 JIT 컴파일러랑 같은 말인가?** 이름과 생각이 같다. 미리 다 하지 않고 필요한 순간에 한다.
- **스킬 작성할 때의 name, description이 그건가?** 그렇다. 그게 1층에 올라가는 정보다.
- **필요할 때 모델이 "이거 쓸래" 하는 방식인가?** 그렇다. 스킬을 꺼내는 것 자체가 요청서(`tool_use`)다.
- **하위 에이전트로 빼는 데 기준이 있나?** 있다. 하네스가 도구 설명에 써 준 가이드이고, 적용은 모델의 판단이다.
- **사람들이 개인 스킬을 왜 지우나?** 내장 하네스의 지침과 겹치거나 부딪히거나 낡아서 오히려 방해가 되기 때문이다.

## 예제와 확인 결과

- **창 크기:** 이 공부를 한 Claude Code 세션(2.1.330, Opus 5.5, Windows 11)의 최근 요청 입력은 549,980 토큰이었다. 기록에서 토큰 수가 크게 줄어든 지점이 없어서 이 시점까지 압축은 일어나지 않았다.
- **하위 에이전트 토큰:** 6절 표는 하위 에이전트가 끝날 때 세션에 남긴 사용량 그대로다. "직접 읽었다면 창이 거의 찼을 것"은 단순 합산이라 실제와는 차이가 있을 수 있다.
- **Hermes 압축기:** `agent/context_compressor.py`의 첫머리 설명과 `agent/prompt_builder.py`가 불러오는 함수 이름(`clip_skill_description`, `SKILL_PROMPT_DESC_LIMIT`)으로 확인했다(커밋 `f85f33bf`). 내부 코드는 읽지 않았다.
- **설명용:** 압축 전후 그림, 스킬 세 층 그림, 지도 예시는 설명용이다.
