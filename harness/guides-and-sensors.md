# 무엇을 글로 안내하고, 무엇을 코드로 막을까?

[목차](README.md) · [이전: 도구와 권한은 어떻게 설계할까?](tools-and-permissions.md)

## 다루는 범위

하네스가 AI를 바로잡는 두 방향(가이드와 센서)과 두 방법(계산형과 추론형)을 정리하고, 규칙 하나를 어디에 둘지 정하는 기준을 세운다.

- 가이드와 센서는 파일이 아니라 역할 이름이다
- 네 칸: 가이드·센서 × 계산형·추론형
- 계산형 검사와 추론형 검사, 그리고 AI 리뷰를 믿을 만하게 만드는 법
- 센서를 만드는 법과 센서를 걸 자리는 따로 정한다
- 규칙을 둘 자리를 정하는 질문 세 개

훅을 거는 구체적인 방법은 [7번 주제](README.md#공부-계획)에서, 끝낼 때 검사를 강제하는 장치는 8번 주제에서 다룬다.

## 시작한 질문

팀에 규칙이 20개 있다. 전부 CLAUDE.md에 쓰면 흐려지고, 전부 코드로 막자니 "코드를 깔끔하게 짜라" 같은 건 코드로 검사할 수가 없다.

1. 어떤 규칙을 글로 안내하고, 어떤 규칙을 코드로 막아야 할까?
2. AI가 AI의 결과를 검사하게 해도 될까?

## 내가 이해한 내용

### 1. 가이드와 센서

Böckeler는 하네스가 AI를 바로잡는 방향을 둘로 나눈다.

| | 가이드(Guide, feedforward) | 센서(Sensor, feedback) |
| --- | --- | --- |
| 원문 | "anticipate the agent's behaviour and aim to steer it before it acts" | "observe after the agent acts and help it self-correct" |
| 쉽게 | AI가 일하기 전에 방향을 잡아 준다 | AI가 일한 뒤에 결과를 보고 알려 준다 |
| 비유 | 내비게이션 | 차선 이탈 경고 |
| 예 | CLAUDE.md, AGENTS.md, 스킬, 참고 문서, 구조 지도, 용어 사전, PR 템플릿 | 테스트, 린터, 타입 검사, 구조 검사 스크립트, AI 리뷰 |

한쪽만 있으면 문제가 생긴다.

| 상황 | 문제 |
| --- | --- |
| 센서만 있으면 | AI가 처음부터 규칙을 몰라서 매번 같은 실수를 하고 매번 센서에 걸린다. 센서가 알려 준 내용은 그 세션 대화에만 남아서, 새 세션에서는 또 반복된다. 세션을 넘어 남는 건 파일(가이드)뿐이다 |
| 가이드만 있으면 | 규칙을 써 두긴 했지만 실제로 지켜졌는지 확인할 방법이 없다 |

가이드와 센서는 파일 이름이 아니라 **역할 이름**이다. CLAUDE.md는 가이드 중 하나일 뿐이다. 스프링에서 "컨트롤러"가 역할이고 `OrderController`가 그 역할을 하는 클래스인 것과 같다.

센서도 마찬가지로 **검사 그 자체**를 말한다. 그 검사를 누가 언제 돌리느냐(도구, 훅, git 훅, CI)는 **자리**라는 별개의 축이다.

| | 뜻 | 예 |
| --- | --- | --- |
| 센서(무엇을 검사하나) | 검사 내용 | 구조 검사 스크립트, 린트, 테스트, AI 리뷰 |
| 자리(누가·언제 돌리나) | 실행 방식 | 도구(AI가 보고 골라서 실행), 훅(AI는 모르고 하네스가 정해진 시점에 실행), git 훅, CI |

```text
같은 센서: check-layers.mjs
  ├─ 도구로  → AI가 Bash로 돌리기로 할 때만        (모델이 골라야 도는 자리)
  ├─ 훅으로  → 파일을 고치거나 끝내려 할 때 자동     (무조건 도는 자리)
  └─ CI로    → PR을 올리면 자동                     (무조건, 대신 늦다)
```

백엔드로 치면 테스트 코드가 센서이고, 그 테스트를 손으로 돌리느냐 커밋할 때 돌리느냐 CI에서 돌리느냐가 자리다. 그래서 하네스를 설계할 때는 무엇을 검사할지(센서 만들기)와 어디에 걸지(자리 정하기)를 따로 정한다.

### 2. 네 칸: 가이드·센서 × 계산형·추론형

"일하는 방식은 문서로 알려 주고, 다 했다고 하면 코드로 확인한다"가 가장 흔한 조합이지만 전부는 아니다. 가이드가 코드일 수도 있고, 센서가 AI 판단일 수도 있고, 센서는 끝날 때만이 아니라 고칠 때마다 돌 수도 있다(검사는 가능한 한 앞에서).

| | 코드로(계산형) | AI 판단으로(추론형) |
| --- | --- | --- |
| 가이드(하기 전에) | 템플릿, 생성 스크립트, 코드모드(OpenRewrite 등) | CLAUDE.md, AGENTS.md, 스킬 |
| 센서(한 뒤에) | 테스트, 린터, 타입 검사, 구조 검사 | AI 코드 리뷰, 리뷰 지침 스킬 |

### 3. 계산형 검사와 추론형 검사

| | 계산형(Computational) | 추론형(Inferential) |
| --- | --- | --- |
| 원문 | "deterministic and fast, run by the CPU" | "Semantic analysis, AI code review, 'LLM as judge'" |
| 같은 입력이면 | 항상 같은 결과 | 매번 다를 수 있다 |
| 속도·비용 | 빠르고 거의 공짜 | 느리고 토큰 비용이 든다 |
| 잘하는 것 | "규칙을 어겼나"(import 방향, 타입, 함수 길이) | "의도대로 됐나"(요구사항 반영, 설계, 이름) |

계산형은 보장이 되지만 볼 수 있는 게 좁고, 추론형은 넓게 보지만 보장이 안 된다. 그래서 계산형으로 잡을 수 있는 건 다 잡고, 남는 "의도" 영역을 추론형으로 보완한다.

**AI 리뷰가 틀리기 쉬운 이유**

| 문제 | 내용 | 출처 |
| --- | --- | --- |
| 자기 평가 편향 | 자기가 만든 결과를 후하게 채점한다 | Anthropic, 긴 작업용 하네스 설계 글 |
| 확인 편향 | 만든 쪽의 설명을 같이 주면 그게 맞다고 확인해 오기 쉽다 | Claude Code 하위 에이전트 도구 설명 |
| 흐린 기준 | "좋은지 봐 줘"라고 하면 그날그날 다르게 판단한다 | Anthropic, 평가 글 |

**AI 리뷰를 믿을 만하게 만드는 법**

| 방법 | 내용 |
| --- | --- |
| 만든 AI와 리뷰하는 AI를 나눈다 | Anthropic은 만드는 에이전트와 평가하는 에이전트를 따로 뒀다. Claude Code의 `/code-review`도 새 하위 에이전트로 리뷰한다. 아예 다른 모델로 리뷰하면 맹점이 겹치지 않을 가능성이 크다 |
| 기준을 구체적으로 | 체크리스트를 주고, 기준마다 넘어야 할 선을 정한다. 작업 전에 "끝"의 기준을 미리 합의한다 |
| 계산형으로 먼저 | import 방향 같은 건 스크립트로 잡고, AI 리뷰는 코드로 못 잡는 것만 맡긴다 |
| 막는 용도보다 알려 주는 용도로 | 결과가 매번 다를 수 있으니, 지적을 받아 고치거나 사람이 최종 판단한다 |
| 잘 잡는지 재 보기 | 실제로 있었던 실수를 보여 주고 몇 개나 잡는지 잰다(11장) |

리뷰어에게도 가이드가 필요하다. 기준 없이 시키면 리뷰어는 일반적인 좋은 코드 기준으로 봐서, 팀이 일부러 정한 방식을 문제 삼거나 팀 규칙 위반은 놓친다. Böckeler의 표에도 "리뷰 지침"이 추론형 센서이자 스킬로 구현하는 항목으로 나온다. 대신 기준은 주고 변명은 주지 않는다.

| 리뷰어에게 줘야 할 것 | 주지 말아야 할 것 |
| --- | --- |
| 팀 규칙과 컨벤션, 리뷰 지침 | 만든 AI의 설명("이건 이래서 이렇게 했어요") |
| 구조 지도, 용어 사전 | 만든 AI와 나눈 대화 전체 |
| 이번 작업의 목표와 "끝"의 기준 | |
| 바뀐 코드(diff) | |

Claude와 Codex가 읽는 지시 파일이 달라도, 둘 다 같은 하네스 폴더를 보게 해 두면 한쪽이 만들고 다른 쪽이 리뷰할 때 같은 기준을 보게 된다.

### 4. 센서를 만드는 법

센서는 AI가 만든 결과물을 검사해서 통과·실패와 이유를 돌려주는 것이다. 생산 라인 끝의 품질 검사기와 같다. JUnit 테스트, ESLint·Checkstyle 설정, 타입 검사처럼 백엔드 개발자가 이미 만들던 것이다. 새로운 건 결과를 사람이 아니라 AI가 읽고 스스로 고친다는 점이고, 그래서 메시지를 잘 써야 한다.

"application은 presentation을 import하지 않는다"를 센서로 만드는 방법은 세 가지다(모두 설명용).

```json
// ① 기존 도구 설정: ESLint
"no-restricted-imports": ["error", {
  "patterns": [{
    "group": ["**/presentation/**"],
    "message": "application은 presentation을 import할 수 없어요. DTO는 application/dto/로 옮기세요."
  }]
}]
```

```java
// ② 테스트 코드: ArchUnit
@ArchTest
static final ArchRule application은_presentation에_의존하지_않는다 =
    noClasses().that().resideInAPackage("..application..")
        .should().dependOnClassesThat().resideInAPackage("..presentation..");
```

③ 도구로 안 되는 팀만의 규칙이면 직접 스크립트를 짠다(5장의 `check-layers.mjs`).

```text
1. 규칙 고르기       "application은 presentation을 import하지 않는다"
2. 판정 방법 정하기   "파일의 import 줄을 보면 알 수 있다"
3. 검사 만들기        기존 도구 설정 / 테스트 코드 / 직접 스크립트
4. 결과 정하기        통과면 조용히, 실패면 어디서·왜·어떻게 + 종료 코드
→ 그다음에 자리 정하기: 도구, 훅, CI
```

### 5. 규칙을 둘 자리를 정하는 질문 세 개

```text
규칙 하나
  ├─ Q1. 기계가 맞다/틀리다를 판정할 수 있나?
  │     ├─ 예 → 계산형 센서로
  │     │        └─ Q2. 반드시 지켜져야 하나?
  │     │              ├─ 예    → 무조건 도는 자리(훅 exit 2, CI)
  │     │              └─ 아니오 → 알려 주는 용도(고칠 때마다 경고, CI 경고)
  │     └─ 아니오 → 글로 된 가이드로
  │              └─ Q3. 언제 필요한가?
  │                    ├─ 항상        → CLAUDE.md(짧게)
  │                    ├─ 특정 작업만 → 스킬(설명을 분명하게)
  │                    ├─ 특정 폴더만 → 경로별 규칙
  │                    └─ 자세한 설명 → 참고 문서
  │              + 결과도 확인해야 하면 → 추론형 센서(AI 리뷰, 다른 모델)
  └─ 어느 쪽이든: 센서가 있어도 가이드에 한 줄은 남긴다
```

| 규칙(설명용) | 판정 가능? | 자리 |
| --- | --- | --- |
| application은 presentation을 import하지 않는다 | 예 | 구조 검사 + 훅·CI(+ CLAUDE.md에 한 줄) |
| 테스트 이름은 한글로 | 예 | 린트 규칙 |
| 커밋 메시지는 `docs:` 형식 | 예 | 커밋 메시지 검사(git 훅이나 Claude Code 훅) |
| `.env`는 읽지 않는다 | 예 | 권한 deny 규칙 |
| 도메인 용어를 통일한다 | 일부 | 용어 사전(가이드) + 금지어 린트 |
| 함수 이름은 의도가 드러나게 | 아니오 | CLAUDE.md나 리뷰 지침 + AI 리뷰 |
| 요구사항이 제대로 반영됐나 | 아니오 | 계획에 "끝"의 기준 + AI 리뷰 + 사람 |
| 배포 절차 | 아니오(절차) | 스킬(사람만 부르게 막아 두기) |

**한 규칙도 쪼갤 수 있다.** "PR 설명에는 왜 바꿨는지 배경을 적는다"는 PR 템플릿에 배경 칸을 두고(가이드), 배경 칸이 비었는지는 CI가 검사하고(계산형), 적은 이유가 타당한지는 리뷰로 본다(추론형). 회원가입 폼에 자기소개 칸을 두고, 비면 제출이 안 되게 하고(`@NotBlank`), 성의 있는지는 사람이 보는 것과 같다. 여기서 "왜"는 코드만 봐서는 알 수 없는 바꾼 이유다.

**판단 규칙을 판정 가능하게 바꿀 수 있으면 바꾼다.** "코드를 깔끔하게"의 일부를 "함수 20줄 이하, 파라미터 3개 이하"로 바꾸면 린트로 잡힌다. Böckeler는 코드베이스마다 하네스를 걸기 쉬운 정도(harnessability)가 다르다고 한다. 타입이 강하고 모듈 경계가 분명할수록 기계가 판정할 수 있는 게 많다.

**판정 못 하는 부분은 신호와 사람으로.** "서비스는 리포지토리를 거쳐 DB에 접근한다"에서 서비스가 `EntityManager`, `JdbcTemplate` 같은 DB 클래스를 쓰는지는 구조 테스트로 판정된다. 하지만 겉모양은 지키면서 취지를 어기는 경우는 기계가 확실히 잡기 어렵다. 이런 건 경고용 신호를 띄우고, 가이드에 좋은 예와 나쁜 예를 두고, AI 리뷰에 체크리스트를 주고, 마지막은 사람이 본다.

| 원하지 않는 방향 | 경고용 신호 |
| --- | --- |
| 리포지토리에 비즈니스 로직이 있다 | 리포지토리 메서드에 분기·계산이 많다 |
| 서비스가 쿼리를 직접 만들어 넘긴다 | 서비스 코드에 SQL 문자열이 있다 |
| 리포지토리 하나에 전부 몰아넣는다 | 리포지토리 클래스의 메서드 수·줄 수가 크다 |

> 판정할 수 있으면 코드로, 반드시 지켜야 하면 무조건 도는 자리에, 판단이 필요하면 언제 필요한지에 맞춰 글로. 그리고 센서가 있어도 가이드에 한 줄은 남긴다.

## 헷갈렸던 점

| 처음의 생각 | 정리한 내용 |
| --- | --- |
| 일하는 방식은 문서로 알려 주고, 다 했다고 하면 코드로 확인한다 | 가장 흔한 조합이지만, 가이드가 코드(템플릿)일 수도 있고 센서가 AI 판단(리뷰)일 수도 있다. 센서는 고칠 때마다 돌 수도 있다. |
| AI 코드 리뷰는 잘할 것이다 | 보장이 없다. 자기 평가 편향, 확인 편향, 흐린 기준 때문이다. 평가자를 나누고 기준을 구체적으로 주고 알려 주는 용도로 쓴다. |
| 가이드는 CLAUDE.md와 다른 문서다 | 가이드는 역할 이름이고 CLAUDE.md는 그중 하나다. |
| 센서는 훅이거나 도구다 | 센서는 검사 그 자체이고, 훅·도구·CI는 그 검사를 거는 자리다. |
| 센서를 만든다는 게 무슨 뜻인지 모르겠다 | 테스트, 린트 설정처럼 이미 하던 일이다. 기존 도구 설정, 테스트 코드, 직접 스크립트 중 하나로 만든다. |
| 이름 규칙(`~Response`)은 AI에게 맡겨도 된다 | 판정할 수 있으면 작은 규칙도 린트로 둔다. 보장도 되고 CLAUDE.md도 가벼워진다. |
| PR 배경 규칙은 "AI가 쓴다" | 물은 건 누가 쓰냐가 아니라 규칙이 지켜지게 할 장치(템플릿, 빈칸 검사, 리뷰)였다. |
| 센서만 있는 팀과 가이드만 있는 팀 모두 CLAUDE.md를 정리하면 된다 | 한쪽은 가이드가, 다른 쪽은 센서가 빠진 것이다. 가이드는 처음부터 덜 틀리게, 센서는 틀린 걸 확실히 잡게. 둘은 짝이다. |

### 확인 문제와 내 답

| 문제 | 내 답의 요지 | 결과 |
| --- | --- | --- |
| 1. 규칙 A~D를 어디에 둘까(A `~Response` 이름, B `prod.yml` 수정 금지, C 기존 API와 비슷한 구조, D PR 배경) | A는 AI에게, B는 코드, C는 import 검사 코드, D는 AI가 쓴다 | B 통과(권한 deny + Bash는 훅·샌드박스로 보충). C·D 부분 통과(판정 가능한 부분과 판단 부분으로 쪼개기, 템플릿이라는 코드 가이드). A는 다시 |
| 1 재시험. A의 이름이 `Response`로 끝나는지 코드로 확인할 수 있나 | 코드로 확인되니 린트로 둔다 | 통과. 큰 사고는 아니라 경고나 CI로 충분하고, 가이드에도 한 줄 남긴다 |
| 2. 센서만 있는 X 팀, 가이드만 있는 Y 팀 | X는 CLAUDE.md에 스킬로 가는 안내를, Y는 본문을 분리해 CLAUDE.md를 지도로 | 부분 통과. X는 가이드가 없어 같은 실수를 반복하고(센서의 교훈은 그 세션에만 남는다), Y는 센서가 없어 지켜졌는지 모른다. Y의 보완은 판정 가능한 규칙을 센서로 옮기는 것 |
| 3. Claude가 만든 걸 Codex에게 리뷰시키기 | 자기가 만든 건 객관적으로 못 본다 / 목적과 컨벤션은 주고 개발 과정 설명은 안 준다 / 정답 보장이 없고 일부러 둔 코드도 문제 삼을 수 있어 무조건 막는 데는 안 쓴다 | 통과. 자기 평가 편향, 맹점 겹침, 확인 편향이라는 용어와 diff·"끝" 기준을 보충 |
| 4. "서비스는 리포지토리를 거친다"에서 판정 가능한 부분과 아닌 부분 | import 같은 코드상 의존은 판정 가능, 전체 그림은 AI가 / 계층 의존과 DB 직접 호출을 본다 / 판정 못 하는 건 코드 흐름을 보게 한다 | 부분 통과. 판정 못 하는 걸 구체적으로(비즈니스 로직 유입, SQL을 만들어 넘기기, 한 리포지토리에 몰기), 다루는 법을 누가·무엇을 기준으로까지 |
