# AI가 검사를 통과해야만 끝나게 하려면?

[목차](README.md) · [이전: 루프의 어디에 코드를 끼울 수 있을까?](hooks.md)

## 다루는 범위

AI가 "다 했다"고 끝내려는 순간에 검사를 강제하는 장치, 완료 게이트를 정리한다.

- 완료 게이트 = Stop 시점 + 검사 훅
- 무한 루프 막기: 몇 번은 다시 시키고, 그래도 안 되면 사람에게
- "끝"의 정의: 공통 기준, 작업별 체크리스트, 의도 확인
- 만든 AI가 아니라 다른 평가자가 확인하기, 그리고 비용과 시간
- 지금까지 하네스 공부의 큰 흐름

게이트가 남긴 기록으로 하네스를 고치는 법은 [11·12번 주제](README.md#공부-계획)에서 다룬다.

## 시작한 질문

1장에서 루프는 모델이 요청서를 안 쓰면(`end_turn`) 끝나고, 그 뜻은 "일이 끝났다"가 아니라 "모델이 끝났다고 생각한다"였다. 테스트를 안 돌리고 "다 했습니다" 하고 끝낼 수도 있고, 작업 중 검사는 AI가 돌리기로 할 때만 돈다.

1. AI가 끝내려 할 때 검사를 반드시 통과하게 하려면 어떻게 할까?
2. 검사가 계속 실패하면 어떻게 될까?
3. 검사를 통과했으면 그 결과를 믿어도 될까?

## 내가 이해한 내용

### 1. 완료 게이트 = Stop 시점 + 검사 훅

게이트(gate)는 통과해야만 다음으로 갈 수 있는 관문이다. 백엔드에서 이미 쓰는 게이트가 있다.

| 게이트 | 통과 조건 | 못 넘으면 |
| --- | --- | --- |
| PR 머지 게이트(필수 검사) | CI 테스트 통과 | 머지 버튼이 안 눌린다 |
| 품질 게이트(SonarQube 등) | 커버리지, 심각한 버그 수 같은 기준 | 실패로 표시된다 |
| 배포 게이트 | 승인자의 승인 | 배포가 안 된다 |

완료 게이트는 AI가 끝내려는 Stop 시점에 서 있어서, 거기를 통과해야만 진짜로 끝낼 수 있는 관문이다. Claude Code의 공식 기능 이름이 아니라 Stop 훅으로 만드는 관문을 부르는 이름이다. 7장의 두 겹 루프에서 Stop은 안쪽 루프의 출구였고, 거기에 문지기를 세우는 것이다.

```text
   ┌→ 모델이 생각하고 요청서를 씀
   │    PreToolUse → 도구 실행 → PostToolUse
   └── 결과를 붙여 다시 모델에게
   모델: "다 했습니다"(end_turn)
   Stop 훅: 검사를 돌려 봄
      ├─ 통과 → exit 0 → 진짜로 끝
      └─ 실패 → exit 2 + "테스트 3개 실패: …" → 다시 루프 안으로 → 고침 → 다시 끝내려 함
```

```json
{
  "hooks": {
    "Stop": [
      { "hooks": [{ "type": "command", "command": "node .claude/hooks/done-gate.mjs" }] }
    ]
  }
}
```

Stop은 도구와 상관없는 시점이라 matcher가 없다(설명용).

```js
// done-gate.mjs (설명용)
import { execSync } from 'node:child_process';

try {
  execSync('npm run typecheck && npm test', { stdio: 'pipe' });
  process.exit(0);
} catch (e) {
  console.error('아직 끝낼 수 없어요. 검사가 실패했습니다.\n' + 실패_요약(e));  // 어디서·왜·어떻게
  process.exit(2);
}
```

Claude Code best practices 문서는 "Give Claude a check to run"이라는 항목에서, 통과·실패로 답이 나오는 검사를 주면 AI가 스스로 고치는 루프가 닫힌다고 하고, Stop 훅이 exit 2를 내면 AI를 다시 일하게 보낸다고 설명한다. Codex도 Stop 훅에서 막으면 그 이유를 다음 지시로 삼아 계속 일한다. 2장의 mini-swe-agent가 명시적 제출 신호를 보내야만 끝나게 한 것처럼, 둘 다 모델이 끝났다고 생각하는 것만 믿지 않는 장치다.

우리가 정하는 건 "끝내도 되는 조건"이다. 언제 끝내려고 시도할지는 여전히 모델이 정하고, 게이트는 그 시도를 받아 줄지를 정한다. 문지기는 나가도 되는지 검사할 뿐 억지로 내보내지는 않는다. 그리고 게이트의 조건은 6장처럼 기계가 판정할 수 있어야 한다. "코드가 깔끔한가" 같은 판단을 게이트로 두면 결과가 매번 달라진다.

이것이 "작업 중에 무조건 도는 검증"이다. 검사를 AI가 돌릴 때만 돌고 PR CI에서 늦게 잡히던 빈틈을, AI가 끝내려는 그 자리에서 무조건 잡는다.

### 2. 무한 루프 막기

AI가 고칠 수 없는 이유로 검사가 실패하면 게이트가 끝없이 막는다. 가끔 실패하는 테스트, DB가 안 떠 있거나 환경 변수가 없는 환경 문제, 서로 부딪혀서 둘 다 통과시킬 수 없는 요구사항 같은 경우다.

| 안전장치 | 누가 | 내용 |
| --- | --- | --- |
| 하네스의 상한 | Claude Code 기본 | 같은 Stop 훅이 연속 8번 막으면 그다음엔 무시하고 끝낸다. `CLAUDE_CODE_STOP_HOOK_BLOCK_CAP`으로 바꿀 수 있고, 중간에 도구를 쓰면 연속 횟수는 0부터 다시 센다 |
| `stop_hook_active` 확인 | 우리 훅 스크립트 | Stop 훅의 입력에 들어 있다. 이미 Stop 훅 때문에 다시 일하는 중이면 true다. 이걸 보고 몇 번째 시도인지 판단한다 |
| 사람에게 넘기기 | 우리 설계 | 정해 둔 횟수를 넘으면 더 막지 않고, 왜 막혔는지 남기고 사람이 보게 한다 |

```js
// done-gate.mjs의 재시도 부분 (설명용)
const input = JSON.parse(readFileSync(0, 'utf8'));
const tries = 시도_횟수_읽기(input.session_id);

if (검사_통과()) process.exit(0);

if (tries >= 3) {
  기록하기('검사 실패 상태로 종료', input.session_id);
  process.exit(0);                  // 막지 않고 끝내게 하되 기록을 남긴다
}
시도_횟수_올리기(input.session_id);
console.error('아직 끝낼 수 없어요. 테스트 2개 실패: …');
process.exit(2);
```

순서는 이렇다. 실패하면 막고 이유를 알려 줘서 AI가 몇 번은 스스로 고치게 한다(대부분 여기서 해결된다). 정해 둔 횟수를 넘으면 더 막지 않고 "이런 이유로 막혔고 사람이 봐야 한다"를 기록과 함께 남긴다. 우리 훅에 버그가 있어 계속 막아도 연속 8번 상한이 마지막 비상구가 된다. 사람에게 넘길 때는 막기를 멈추고 기록을 남기는 방식 외에, 훅이 JSON으로 `continue: false`와 `stopReason`을 돌려줘 Claude를 아예 멈추고 이유를 보여 주는 방식도 있다. 재시도 횟수는 검사 속도에 맞춰 팀이 정한다.

애초에 게이트에는 빠르고, 늘 같은 결과가 나오고, AI가 코드로 고칠 수 있는 검사(타입 검사, 단위 테스트, 구조 검사)만 넣는다. 느리거나 불안정하거나 환경에 기대는 검사는 CI로 보낸다. mini-swe-agent에 단계 수·비용·시간 한도와 "형식 오류 3번 연속이면 종료"가 있었고, Anthropic도 자율 에이전트에는 최대 반복 횟수 같은 종료 조건을 두라고 한다. 모든 루프에는 출구가 있어야 한다.

### 3. "끝"의 정의

타입 검사와 테스트만 보면 "망가지지 않았다"까지만 확인된다. "취소하면 환불과 재고 복구까지"를 요청했는데 AI가 재고 복구를 빠뜨렸고, 그걸 검사하는 테스트가 아예 없다면 게이트는 통과한다.

| 층 | 무엇을 확인하나 | 어떻게 |
| --- | --- | --- |
| 공통 기준 | 망가지지 않았나 | 타입 검사, 테스트, 구조 검사(어떤 작업이든 같다) |
| 작업별 기준 | 이번 일을 다 했나 | 작업 전에 "끝"의 체크리스트를 파일로 정해 두고, 게이트가 다 채워졌는지 확인 |
| 의도 확인 | 의도대로 됐나 | AI 리뷰, 평가자 에이전트(4절) |

Anthropic의 긴 작업 하네스는 첫 세션에서 해야 할 기능을 JSON 목록으로 만들고(claude.ai를 따라 만든 예시에서 200개가 넘었다), 항목마다 처음엔 `"passes": false`로 둔다. AI는 기능을 확인한 뒤에만 `passes`를 바꿀 수 있다. JSON을 고른 이유는 마크다운보다 모델이 함부로 덮어쓸 가능성이 낮아서라고 한다. 다른 글에서는 작업 단위마다 "끝"과 확인 방법을 먼저 합의했다(sprint contract, 한 단위에 기준이 27개였던 경우도 있었다). 기능 목록이 파일로 있으면 게이트가 "`passes: false`가 남았나?"를 코드로 확인할 수 있다. "다 했나?"라는 판단을 "체크리스트가 다 찼나?"로 바꾼 것이다.

Claude Code best practices 문서는 AI를 무인으로 오래 돌리기 전에 답해 둘 질문 다섯 개를 제시한다. "끝"의 정의, AI가 스스로 확인하는 방법, 접근 범위, 멈출 조건, 승인할 사람이다.

체크리스트는 AI가 초안을 쓰고 사람이 승인한다. Anthropic의 initializer나 planner처럼 AI가 쓰고, 작업 흐름에 이미 "구현 계획 → 승인" 단계가 있다면 거기에 "끝의 기준" 칸 하나를 더하면 된다. 챙길 점은 세 가지다. AI가 통과하려고 항목을 지우거나 기준을 느슨하게 바꾸지 못하게 하고(체크 표시만 바꿀 수 있게), 작업 크기에 맞게(오타 수정엔 필요 없다), 하다가 빠뜨린 게 보이면 추가하되 사람이 볼 수 있게 남긴다.

### 4. 만든 AI가 아니라 다른 평가자가 확인하기

만든 AI가 스스로 확인하면 자기 결과를 후하게 채점하고(자기 평가 편향), 덜 끝났는데 일찍 "완료"를 선언한다. Anthropic은 단위 테스트나 `curl` 한두 번으로만 확인하고 끝내면 결과가 나빴다고 한다. 그래서 계획하는 AI(planner), 만드는 AI(generator), 평가하는 AI(evaluator)를 나누고, 평가 AI가 브라우저 자동화로 실제 앱을 사용자처럼 써 보며 확인하게 했다. 평가 기준마다 넘어야 할 선을 정해 하나라도 못 넘으면 실패로 처리하고, 예시 몇 개로 채점 기준을 맞췄다.

비용이 크다. 같은 글에서 혼자 만들게 했을 땐 20분·$9, 평가자를 둔 하네스는 6시간·$200이었고 결과물은 훨씬 좋았다. 모델이 좋아진 뒤에는 평가를 마지막에 한 번만 돌리게 줄여 약 3시간 50분·$124.70이 됐다. 다만 이 숫자는 앱 하나를 통째로 만드는 큰 작업이었다.

```text
AI: "다 했습니다"
  ↓
Stop 훅(완료 게이트)
  ① 공통 기준: 타입 검사, 테스트, 구조 검사   → 실패하면 막기(확실하니까)
  ② 작업별 기준: "끝" 체크리스트가 다 찼나?   → 비어 있으면 막기(확실하니까)
  ③ 의도 확인: 다른 AI가 써 보고 평가          → 알려 주기, 심각하면 사람에게
  ↓
  통과 → 끝 / 실패 → 다시 일하게(정해 둔 횟수를 넘으면 사람에게)
```

①②는 코드라서 막는 데 쓰고, ③은 AI 판단이라 6장처럼 주로 알려 주는 데 쓴다. Claude Code에서는 ③을 `/code-review`처럼 새 하위 에이전트로 돌리거나, Stop 시점의 `agent` 훅(실험적)으로 걸 수 있다.

**비용과 시간을 줄이며 쓰는 법.** 싼 코드 검사부터 돌려서 걸리면 평가자까지 가지 않고, 평가자는 큰 일에만, 끝에서 한 번, 바뀐 부분과 체크리스트만 보게 좁혀서, 필요하면 더 싼 모델로 쓴다. 작업 크기에 따라 게이트 강도를 다르게 둔다.

| 작업 | 게이트 |
| --- | --- |
| 오타, 문구 수정 | ① 공통 기준만 |
| 작은 기능, 버그 수정 | ① + ② |
| 큰 기능, 배포 직전 | ① + ② + ③ |

비용은 요청 하나가 아니라 끝낸 작업 하나당으로 따진다. 평가자를 빼서 당장 싸 보여도 재시도나 사람의 수정이 늘면 오히려 비싸다. 시간도 AI가 도는 시간보다 사람이 기다리거나 다시 확인하는 시간이 비싸다. 비싼 평가는 작업 중 Stop 게이트 대신 PR 이후 CI로 보내 사람이 기다리지 않게 할 수도 있고, 사람이 없는 동안 AI 혼자 오래 도는 작업이면 오래 걸려도 괜찮다. 구독으로 쓰는 코딩 하네스에서는 비용이 주로 사용량 한도와 시간이고, API로 직접 돌리는 하네스에서는 토큰이 곧 돈이다.

**게이트를 통과하면 믿어도 되나.** 게이트는 자기가 검사한 것만 보장한다.

| 믿을 수 없는 경우 | 보완 |
| --- | --- |
| 빠진 작업 | 작업 전 체크리스트를 쓰고 사람이 승인, Stop에서 다 채웠는지 확인 |
| 테스트가 약하거나 틀림 | 체크리스트 항목마다 확인한 테스트가 있는지 같이 본다 |
| AI가 통과하려고 검사를 건드림 | 테스트와 체크리스트의 변경은 사람이 따로 보고, 검사 스크립트는 AI가 못 고치게 막는다 |

그래도 의도대로 됐는지는 마지막에 평가자나 사람이 본다. 게이트는 "믿어도 되는 증명"이 아니라 "믿을 수 없는 경우를 줄이는 관문"이다.

### 5. 지금까지의 큰 흐름

1장에서 처음 나온 "문서는 판단에, 코드는 실제로 일어난 일에 작용한다"가 공부 전체의 뼈대였다.

| 갈래 | 무엇에 작용하나 | 장 |
| --- | --- | --- |
| 글로 안내하기(컨텍스트 엔지니어링 포함) | AI의 판단 | 3·4장 |
| 코드로 돕고 제어하기(도구, 권한, 센서, 훅, 게이트) | 실제로 일어나는 일 | 5~8장 |
| 크게, 오래 쓰기 | 몇 시간짜리 일, 여러 에이전트 | 9·10장 |
| 하네스 자체를 보고 고치기 | 게이트가 남긴 기록으로 1·2를 고쳐 가기 | 11·12장 |

훅을 한 문장으로 정리하면, 문서만으로는 AI를 확실히 제어하기 어려워서 정해진 시점에 우리 코드를 실행해 AI의 작업을 막거나 도와주는 장치이고, Claude Code에서는 주로 `settings.json`에 시점·조건·명령을 적어 등록한다. 훅은 도구(AI의 손)가 아니라 장치라고 불러야 섞이지 않는다.

## 헷갈렸던 점

| 처음의 생각 | 정리한 내용 |
| --- | --- |
| 게이트가 뭔지 모르겠다 | 통과해야 넘어가는 관문이다. 완료 게이트는 Stop 시점에서 AI가 끝내기 전에 통과해야 하는 관문이고, Stop 훅으로 만든다. |
| Stop에 끝내는 조건을 넣으면 멈추는 조건까지 만들 수 있다 | 우리가 정하는 건 "끝내도 되는 조건"이다. 끝내려는 시도는 모델이 하고, 게이트는 받아 줄지를 정한다. |
| 실패하면 바로 사람에게 넘긴다 | 먼저 몇 번은 AI에게 고칠 기회를 주고, 그래도 안 되면 넘긴다. |
| 훅은 기계어로 만든, AI를 제어하는 도구다 | 코드로 만든 장치다. "도구"는 AI의 손을 뜻하니 섞지 않는다. |
| 평가자는 비싸다 | 맞지만, 싼 검사부터·큰 일에만·끝에서 한 번·좁게 쓰고, 끝낸 작업 하나당 비용으로 따진다. |
| 작업마다 다 검사하면 시간이 오래 걸린다 | 작업 크기에 따라 게이트 강도를 다르게 두고, 비싼 검사는 사람이 기다리지 않는 자리로 보낸다. |
| 게이트를 통과했으면 믿어도 된다 | 게이트는 검사한 것만 보장한다. 빠진 작업, 약한 테스트, 검사를 건드리는 경우를 따로 막는다. |

### 확인 문제와 내 답

| 문제 | 내 답의 요지 | 결과 |
| --- | --- | --- |
| 1. "타입 검사·테스트·구조 검사를 통과해야 끝나게" 하는 게이트 설계(시점과 대상, 실패하면, 환경 문제로 계속 실패하면, 못 잡는 것) | Stop 시점에 검사 훅 / 무엇이 문제인지 알려 주면 다시 작업하고 다시 Stop에서 다뤄진다 / 최소 재시도 후 사용자에게 알린다 / 게이트는 무엇을 만들었어야 하는지 몰라 빠진 작업을 못 잡으니, 작업 리스트를 먼저 쓰게 하고 마지막에 확인한다 | 통과. 보충: 이유는 stderr로 어디서·왜·어떻게, 연속 8번 상한과 환경 의존 테스트는 CI로, 리스트는 사람이 승인하고 AI가 못 지우게, 의도는 평가자나 사람이 |
| 2(가). 게이트 때문에 느려지지 않나 | 느려지지만 완료 조건이라 넣어야 한다. CI로 미루거나 다른 AI에게 맡기고 넘어가는 방법도 있다 | 부분 통과. 대부분 빠른 코드 검사라는 근거, 작업 크기별 강도, 끝낸 작업당 시간으로 보기를 먼저 말한다 |
| 2(나). 게이트를 통과하면 믿어도 되나 | 처음엔 "네" → 다시: 그대로 믿을 수 없다. 게이트는 결과만 보고 무엇을 만들었어야 하는지 모르니, 작업 리스트를 먼저 쓰고 Stop에서 확인한다 | 재답변 통과. 약한 테스트와 AI가 검사를 건드리는 경우를 보충 |
