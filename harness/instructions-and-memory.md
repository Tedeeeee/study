# AI는 내 규칙을 어떻게 "기억"할까?

[목차](README.md) · [이전: "하네스"는 정확히 어디까지일까?](what-is-harness.md)

## 다루는 범위

모델이 대화와 규칙을 "기억"하는 것처럼 보이는 이유를 따라간다. 그리고 그 과정에서 같이 나온 도구, 훅, 권한, 샌드박스의 차이를 정리한다.

- 모델은 기억하지 않고, 하네스가 매번 대화 전체를 다시 보낸다
- 프롬프트 캐시와 "앞부분을 건드리지 않는" 하네스 설계
- 첫 요청에 미리 깔리는 것: 시스템 프롬프트, 도구 정의, CLAUDE.md, 메모리
- 도구와 훅의 차이
- CLAUDE.md는 강제가 아니라 컨텍스트다
- 위험한 명령을 막는 층들과 샌드박스

압축 뒤에 무엇이 남는지는 [4번 주제](README.md#공부-계획)에서, 권한과 샌드박스 설계는 5번 주제에서, 훅을 직접 거는 법은 7번 주제에서 자세히 다룬다.

## 시작한 질문

CLAUDE.md에 규칙을 써 두면 AI가 세션 내내 지킨다. 어제 대화도 이어서 한다.

1. AI는 그걸 어딘가에 기억해 두고 있는 걸까?
2. 그렇다면 CLAUDE.md에 쓴 규칙은 반드시 지켜질까?

## 내가 이해한 내용

### 1. 모델은 기억하지 않는다. 하네스가 매번 처음부터 다시 보낸다

모델은 요청과 요청 사이에 아무것도 기억하지 않는다. 기억하는 건 하네스다. 하네스가 대화 전체를 들고 있다가, 모델에게 물을 때마다 처음부터 끝까지 다시 보낸다. 모델 입장에서는 매번 처음 보는 긴 문서 하나를 받아서 이어 쓰는 셈이다.

이 공부를 한 Claude Code 세션의 기록에서, 요청마다 모델이 입력으로 읽은 토큰 수는 이렇게 늘었다.

| 요청 | 모델이 읽은 입력 | 그중 캐시에서 읽은 것 |
| --- | --- | --- |
| 1번째 | 46,496 | 31,876 |
| 11번째 | 85,298 | 84,939 |
| 51번째 | 194,424 | 194,159 |
| 101번째 | 405,154 | 405,137 |
| 마지막으로 잰 요청 | 490,109 | 474,725 |

| 우리가 "기억"이라고 느끼는 것 | 실제로는 |
| --- | --- |
| 세션 내내 앞 대화를 기억한다 | 하네스가 대화 전체를 매번 다시 보낸다 |
| CLAUDE.md 규칙을 기억한다 | 하네스가 CLAUDE.md를 매번 창 앞쪽에 다시 놓는다 |
| 어제 대화를 이어 간다 | 하네스가 저장해 둔 기록(JSONL)을 불러와 다시 보낸다 |
| 세션이 바뀌어도 진도를 안다 | Claude가 메모리 파일에 적어 두고, 다음 세션에 그 목차를 다시 넣어 준다 |

Codex도 같다. OpenAI 글에 따르면 Codex는 이전 응답을 참조하지 않고, 요청 하나하나가 대화 전체를 담은 독립된 요청이다.

### 2. 프롬프트 캐시와 "앞을 건드리지 않는" 설계

매번 전부 다시 읽으면 느리고 비싸야 하는데, 프롬프트 캐시가 그걸 막는다. 앞부분이 지난번과 똑같으면 이미 처리해 둔 결과를 다시 쓴다. 위 표에서 대부분이 캐시에서 읽은 것이다. Opus 5.5 기준으로 일반 입력은 100만 토큰당 $4이고, 캐시 읽기는 $0.20이다.

판단은 빡빡하지만 단순하다. 의미가 아니라 앞에서부터 기계적으로 똑같은지만 본다(앞부분 일치, prefix match). 요청은 `도구 목록 → 시스템 프롬프트 → 대화` 순서로 이어 붙이고, 중간에 한 글자라도 바뀌면 그 뒤는 새로 처리한다.

```text
[도구 목록][시스템 프롬프트][대화 1] … [대화 59] [새 대화]
└──────── 지난번과 똑같음 → 캐시에서 읽기 ───────┘ └ 새로 처리 ┘
```

그래서 하네스는 앞부분을 건드리지 않게 설계된다.

| 하네스가 하는 일 | 이유 |
| --- | --- |
| 안 바뀌는 건 앞에, 자주 바뀌는 건 뒤에 둔다 | 앞이 흔들리면 전부 다시 처리한다 |
| 앞의 메시지를 고치지 않고 새 메시지로 덧붙인다 | Codex는 세션 도중 설정이 바뀌면 앞을 고치지 않고 새 메시지로 추가한다 |
| 시스템 프롬프트에 현재 시각, 순서가 섞인 JSON, 매번 바뀌는 도구 목록을 넣지 않는다 | API 문서가 꼽은 "조용히 캐시를 깨는 것"이다 |

이 세션에서도 전역 CLAUDE.md가 바뀌었을 때, 대화 맨 앞을 고치는 대신 "지시 파일을 다시 읽었고 예전 것과 달라서 바꾼다"는 새 메시지가 중간에 덧붙여져서 들어왔다. Hermes가 기억 파일을 세션 시작 때 사본으로 고정해 두고, 바뀐 내용은 다음 세션부터 보여 주는 것도 같은 이유로 보인다. 다만 이유를 캐시로 보는 건 추측이다. 두 문서 모두 이유를 적어 두지는 않았다.

이미 한 대화를 고칠 수는 있다. 하네스가 들고 있는 목록을 고쳐 보내면 그게 새 역사가 된다. 대신 고친 지점부터 뒤는 캐시가 깨지고 그 뒤 대화도 다시 만들어야 한다.

| 상황 | 무엇을 고치나 |
| --- | --- |
| claude.ai에서 예전 메시지 수정 | 그 메시지부터 새 갈래가 생긴다 |
| Claude Code에서 Esc 두 번(되감기) | 예전 시점으로 대화와 파일을 되돌린다 |
| 압축(`/compact`, 자동 압축) | 긴 대화를 요약본 하나로 통째로 바꾼다 |
| `/clear` | 대화를 비우고 새로 시작한다 |

평소에는 덧붙이기만 하고, 사람이 수정하거나 되감거나 창이 차서 압축할 때만 고친다. 최신 Claude 모델은 이전 대화를 고치면 모델의 생각 기록(thinking)이 무효가 되는 검사가 있어서, API 문서가 하네스를 덧붙이기만 하는(append-only) 구조로 만들라고 권한다.

### 3. 첫 요청에 미리 깔리는 것

첫 마디를 하기도 전인 1번째 요청에 이미 46,496 토큰이 들어 있었다. 하네스가 일하는 데 필요한 기본 자료를 책상에 미리 깔아 두기 때문이다.

| 무엇 | 내용 | 넣는 방식 |
| --- | --- | --- |
| Claude Code 시스템 프롬프트 | 행동 규칙, 도구 쓰는 법, 기본 원칙 | 매번 전부 |
| 도구 정의 | Bash, Read, Edit, Grep, Agent 같은 도구의 이름·설명·입력 형식 | 매번 전부 |
| 지연 로딩 도구 목록 | MCP로 붙인 도구 수백 개 | 이름만. 쓸 때 ToolSearch로 정의를 불러온다 |
| 스킬 목록 | 스킬 이름과 설명 | 이름과 설명만. 본문은 쓸 때 불러온다 |
| CLAUDE.md | 전역과 프로젝트 | 매번 전부. 시스템 프롬프트가 아니라 그 뒤의 사용자 메시지로 들어간다 |
| 메모리 목록 | `MEMORY.md`의 한 줄짜리 목차 | 목차만 매번. 상세는 필요할 때 파일을 연다 |
| 환경 정보 | 작업 폴더, 운영체제, git 상태, 날짜 | 매번 |

넣는 방식은 세 가지다. 늘 필요한 것은 매번 전부 넣고, 다 넣으면 넘치는 것은 이름만 넣었다가 필요할 때 불러오고, 대화와 도구 결과는 일하면서 쌓인다. 2장의 "늦게 넣기"가 이렇게 구현돼 있다.

**지연 로딩**은 실행이 오래 걸린다는 뜻이 아니라, 정의를 언제 책상에 올리느냐의 이야기다. JPA의 `FetchType.LAZY`가 연관 엔티티를 프록시로 두었다가 접근할 때 가져오는 것처럼, 도구도 이름만 두었다가 쓰려는 순간 정의를 불러온다.

### 4. 시스템 프롬프트, CLAUDE.md, 메모리는 각각 다르다

| | Claude Code 시스템 프롬프트 | 전역 `~/.claude/CLAUDE.md` | 프로젝트 `CLAUDE.md` |
| --- | --- | --- | --- |
| 누가 쓰나 | Anthropic(Claude Code에 내장) | 나 | 저장소 주인이나 팀 |
| 적용 범위 | 모든 사용자, 모든 프로젝트 | 내 PC의 모든 프로젝트 | 그 프로젝트에서만 |
| 공유 | 모두 같은 걸 받는다 | 나만 쓴다 | git에 올리면 팀원도 같이 쓴다 |
| 예 | 도구 쓰는 법, 기본 행동 원칙 | 말투 규칙 | 공부 방식 |
| 들어가는 자리 | 시스템 프롬프트 칸 | 시스템 프롬프트 뒤의 사용자 메시지 | 전역 것과 이어 붙여 같은 자리 |

이 밖에 회사가 강제로 까는 관리 정책용 CLAUDE.md와, 나만 쓰고 git에는 안 올리는 `CLAUDE.local.md`가 있다. 여러 개면 넓은 범위가 먼저, 가까운 범위가 나중에 오도록 이어 붙인다.

**메모리(auto memory)**는 Claude가 일하면서 알게 된 걸 직접 적는 공책이다. `~/.claude/projects/<프로젝트>/memory/`에 목차(`MEMORY.md`)와 상세 파일들이 있다. 세션 시작 때 목차의 앞 200줄(또는 25KB)만 넣고, 상세는 필요할 때 연다. 이 공부의 진도도 여기에 적혀 있어서, 새 세션에서도 이어 갈 수 있다.

| | CLAUDE.md | auto memory |
| --- | --- | --- |
| 누가 쓰나 | 사람 | Claude가 직접(평범한 파일 도구로) |
| 무엇을 | 지켜야 할 규칙, 지시 | 알게 된 사실: 사용자 취향, 진도, 받은 피드백 |
| 어디에 | 프로젝트 폴더나 홈 폴더 | 내 PC의 프로젝트별 메모리 폴더(저장소에 안 올라간다) |
| 읽는 방식 | 세션 시작 때 전부 | 목차만 시작 때, 상세는 필요할 때 |

하네스는 폴더를 정해 주고, 목차를 넣어 주고, "이런 건 기록하라"는 규칙을 시스템 프롬프트에 넣는다. 무엇을 적을지는 모델이 판단한다. Hermes도 `MEMORY.md`(2,200자)와 `USER.md`(1,375자)를 세션 시작 때 읽고 에이전트가 직접 고치는, 거의 같은 구조다.

### 5. 도구와 훅

- **도구(tools)**는 모델이 골라서 쓰는 능력이다.
- **훅(hooks)**은 정해진 순간이 오면 하네스가 알아서 돌리는, 사용자가 만든 스크립트다.

루프에 겹쳐 보면 훅이 걸리는 대표적인 시점은 이렇다. Claude Code에는 문서 기준으로 이런 시점이 33개 있다.

```text
세션 시작 ──────────────────── SessionStart
사용자가 입력함 ─────────────── UserPromptSubmit
┌→ 모델이 요청서를 씀
│     실행하기 직전 ──────────── PreToolUse   ← 막을 수 있다
│     도구 실행
│     실행한 직후 ──────────── PostToolUse  ← 결과에 한마디 덧붙일 수 있다(도구는 이미 실행됨)
└── 반복
모델이 끝내려 함 ────────────── Stop         ← 막아서 계속 일하게 할 수 있다
```

그 시점이 오면 하네스가 스크립트를 실행하면서 상황 정보를 넘겨준다. 스크립트가 exit code 0으로 끝나면 통과하고, exit code 2로 끝나면 그 행동을 막고 남긴 이유를 모델에게 전달한다. 설정은 `settings.json`에 한다(설명용).

```json
{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Bash",
        "hooks": [{ "type": "command", "command": "python .claude/hooks/block_rm.py" }]
      }
    ]
  }
}
```

도구 한 번을 감싸면 훅 → 도구 → 훅 모양이 된다. 스프링 인터셉터의 `preHandle` → 컨트롤러 → `postHandle`과 같고, `preHandle`이 false면 컨트롤러가 안 불리는 것처럼 PreToolUse가 막으면 도구도 PostToolUse도 실행되지 않는다.

```text
UserPromptSubmit 훅
  → [PreToolUse 훅 → 도구 → PostToolUse 훅] × 여러 번
  → Stop 훅 (막으면 다시 위로)
```

| | 도구 | 훅 |
| --- | --- | --- |
| 무엇 | 모델이 쓸 수 있는 능력 | 정해진 순간에 도는 내 코드 |
| 누가 실행을 정하나 | 모델이 고른다 | 하네스가 정해진 시점에 기계적으로 돌린다 |
| 모델에게 보이나 | 보인다(정의가 컨텍스트에 있다) | 안 보인다(막을 때 이유만 전달된다) |
| 누가 만드나 | 대부분 Claude Code나 MCP가 제공 | 사용자가 만든다 |
| 비유(스프링) | 컨트롤러가 골라서 호출하는 서비스 | 요청마다 지나가는 필터·인터셉터 |
| Codex에서는 | shell, `apply_patch`, `update_plan` 등 | `hooks.json`, 이벤트 14개 |

훅은 하네스가 "필요하겠다"고 판단해서 부르는 게 아니라, 사용자가 미리 정해 둔 시점에 예외 없이 실행된다. 모델은 훅이 있는지도 모르니 건너뛸 수도 없다. 그래서 검사를 도구로 돌리면 모델이 골라야 실행되고, 훅으로 걸면 모델이 뭘 하든 실행된다.

### 6. CLAUDE.md는 강제가 아니라 컨텍스트다

Claude Code 문서는 CLAUDE.md를 "강제 설정이 아니라 컨텍스트"라고 설명하고, 반드시 지켜야 하는 건 훅이나 deny 규칙으로 하라고 한다. best practices 문서는 지시를 두 종류로 나눈다.

| | 글로 된 지시(non-deterministic) | 하네스가 실행하는 것(deterministic) |
| --- | --- | --- |
| 예 | 프롬프트, CLAUDE.md, 스킬, 출력 스타일 | 훅, 권한 deny 규칙, 관리 정책 설정 |
| 누가 판단 | 모델이 읽고 따를지 판단 | 하네스가 무조건 실행 |
| 들어가는 곳 | 컨텍스트(책상 위) | 하네스 코드 쪽(책상 밖) |

CLAUDE.md가 안 지켜질 수 있는 이유는 세 가지다.

1. **판단의 대상이다.** 다른 지시와 부딪히면 모델이 저울질한다.
2. **길어지면 흐려진다.** CLAUDE.md는 앞에 있고 새 자료는 뒤에 쌓여서 점점 멀어진다.
3. **압축 때 일부가 사라진다.** 압축 뒤에 루트 CLAUDE.md는 다시 넣어 주지만, 하위 폴더 CLAUDE.md, 특정 경로용 규칙, 대화로만 준 지시는 사라진다.

1번의 실제 예가 이 세션에 있었다. 하네스 안내는 "커밋 끝에 `Co-Authored-By: Claude …`를 붙여라"였고, 메모리에는 "커밋에 Claude 공동 작성자를 넣지 않는다"가 있었다. 안내에 "사용자가 직접 정한 규칙이 우선"이라고 적혀 있어서 Claude는 메모리 쪽을 따랐다. 결과는 맞았지만, 그건 글을 읽고 내린 판단이었다. 반드시 지켜야 한다면 커밋 메시지를 검사하는 훅이 있어야 보장된다.

| 이런 건 | 여기에 |
| --- | --- |
| 반드시 지켜야 하고 기계가 판정할 수 있는 것 | 훅, deny 규칙 |
| 판단이 필요한 것, 프로젝트 맥락, 용어 | CLAUDE.md(짧게) |
| 오래 남아야 하는데 지금 대화로만 말한 것 | 파일로 옮기기(CLAUDE.md나 메모리) |

Codex의 AGENTS.md도 시스템 칸이 아니라 사용자 메시지로 들어가는 글이고, 강제하는 건 훅과 승인 정책으로 따로 있다.

### 7. 위험한 명령을 막는 층과 샌드박스

모델이 `rm -rf`를 요청했을 때 기본으로 막는 건 훅이 아니라 권한 확인이다. 훅은 사용자가 따로 설정해야 생긴다. 문서 기준으로 막을 수 있는 층은 다섯 개다.

| 층 | 누가 만드나 | 어떻게 막나 | 기본 상태 |
| --- | --- | --- | --- |
| 모델 자신 | 모델의 학습, 시스템 프롬프트 | 위험해 보이면 스스로 안 쓴다 | 항상 있지만 보장은 아니다 |
| 권한 규칙 | 사용자(`settings.json`의 allow·ask·deny) | deny → ask → allow 순서로 확인하고, 허용 목록에 없으면 사람에게 묻는다 | 기본은 "물어보기" |
| 권한 모드 | 사용자가 고른다 | auto 모드는 분류기가 위험한 행동을 막고, bypass 모드는 아무것도 묻지 않는다 | 문서상 최근 버전 터미널의 기본 시작 모드는 auto |
| 샌드박스 | 사용자가 켠다 | OS가 쓸 수 있는 폴더와 네트워크를 제한한다(셸 명령에만) | 꺼져 있다. 네이티브 Windows는 지원하지 않는다 |
| 훅(PreToolUse) | 사용자가 스크립트를 쓴다 | 실행 직전에 명령을 검사해 exit 2로 막는다 | 없다 |

```text
모델: "Bash로 rm -rf ./build 실행해 줘"
  → [PreToolUse 훅]    설정했다면 여기서 검사
  → [권한 규칙·모드]   deny면 차단, 허용 목록에 없으면 사람에게 물어봄
                       (훅이 통과시켜도 deny 규칙은 따로 확인한다)
  → [샌드박스]         켜져 있으면 허용된 폴더 밖은 OS가 막음
  → 실행
```

같은 Claude Code라도 설정에 따라 다르다. 이 공부를 한 세션은 권한 확인을 끈 bypass 모드에, 훅도 없고, 네이티브 Windows라 샌드박스도 없어서 사실상 모델의 판단만 남아 있었다.

| | 권한 deny 규칙 | 훅 |
| --- | --- | --- |
| 예 | `"deny": ["Bash(rm -rf:*)"]`(설명용) | 명령을 파싱해 "프로젝트 폴더 밖을 지우는지" 검사 |
| 장점 | 한 줄이면 끝난다 | 복잡한 판단을 짤 수 있고 기록도 남길 수 있다 |
| 한계 | 글자 패턴이라 같은 일을 다른 형태로 쓰면 빠져나갈 수 있다 | 직접 짜야 한다 |

이렇게 층을 겹쳐 두는 걸 심층 방어(defense in depth)라고 한다. 백엔드에서 WAF, Spring Security 필터, 서비스의 입력 검증, DB 제약 조건을 겹쳐 두는 것과 같다. 대신 층이 많으면 불편해진다. 너무 자주 물으면 사람이 내용을 안 보고 승인만 누르게 되므로, 분류기가 위험한 것만 막는 auto 모드나 미리 정한 허용 목록으로 균형을 잡는다.

**샌드박스**는 명령이 실행되는 울타리다. 다른 층은 실행 전에 명령의 글자를 보고 판단하지만, 샌드박스는 실행은 시키되 실행 중인 프로세스가 건드릴 수 있는 범위를 OS가 막는다.

| | 권한 단계 | 샌드박스 |
| --- | --- | --- |
| 질문 | "이 명령을 실행해도 되나?" | "실행 중에 이 선을 넘으려 하나?" |
| 근거 | 명령의 글자 | 실제 동작(파일 쓰기, 네트워크 접속) |
| 막는 선 | 규칙에 적힌 패턴 | 작업 폴더 밖 쓰기, 허용 안 한 도메인 접속 |

예를 들어 허용 목록에 `npm test`를 넣어 두면 권한 단계는 그 글자만 보고 통과시킨다. 그런데 그 안에서 테스트 코드 하나가 홈 폴더의 비밀 키를 읽거나 다른 폴더를 지우거나 외부로 뭔가 보낼 수 있다. 권한 단계는 명령의 글자만 보니 그걸 못 막고, 샌드박스는 실행 중인 동작을 보고 선을 못 넘게 막는다. 그래서 최후 방어선이다.

| 하네스 | 샌드박스 |
| --- | --- |
| Claude Code | 기본은 꺼짐. `sandbox.enabled: true`나 `/sandbox`로 켠다. 작업 폴더(와 추가한 폴더)에만 쓸 수 있고, `.claude` 설정·`.mcp.json`·`.git/hooks`는 쓰기를 막는다. 네트워크는 허용한 도메인만 나간다. 셸 명령에만 걸린다. macOS는 Seatbelt, Linux·WSL2는 bubblewrap을 쓰고, 네이티브 Windows는 지원하지 않는다 |
| Codex | 기본으로 켜져 있다. read-only / workspace-write(작업 폴더만 쓰기, 네트워크 기본 차단) / danger-full-access 중에서 고른다 |
| Hermes | 명령을 Docker 컨테이너나 원격 서버에서 돌린다. 아예 다른 환경에서 실행하는 무거운 울타리다. 기본은 내 PC에서 바로 실행한다 |

## 헷갈렸던 점

| 처음의 생각 | 정리한 내용 |
| --- | --- |
| 지연 로딩 도구는 작업이 오래 걸리는 도구다 | 실행 시간이 아니라 정의를 언제 넣느냐의 이야기다. 이름만 두었다가 쓸 때 정의를 불러온다(JPA의 지연 로딩과 같다). |
| 도구 정의는 tools나 hooks 같은 것이다 | tools만이다. 훅은 컨텍스트에 아예 안 들어가고, 모델은 훅이 있는지도 모른다. |
| 시스템 프롬프트와 전역·프로젝트 CLAUDE.md는 같은 것이다 | 셋 다 다르다. 시스템 프롬프트는 Anthropic이 쓴 것이고 시스템 칸에 들어간다. CLAUDE.md는 내가 쓰거나 팀이 쓴 것이고 그 뒤의 사용자 메시지로 들어간다. |
| 훅은 하네스가 필요한 상황에 스스로 부른다 | 판단해서 부르는 게 아니라, 사용자가 미리 정해 둔 시점이 오면 기계적으로 실행된다. |
| `rm` 같은 명령을 막는 주체는 훅이다 | 기본으로 막는 건 권한 확인이다. 훅은 사용자가 따로 설정해야 생긴다. 모델·권한 규칙·권한 모드·샌드박스·훅의 다섯 층이 있다. |
| 샌드박스는 권한상 문제가 없는 명령이라 권한 단계에서 막기 애매한 걸 막는다 | 더 정확히는, 권한 단계는 명령의 글자만 봐서 실제로 뭘 건드릴지 모른다. 샌드박스는 실행 중인 동작을 보고 선(작업 폴더, 네트워크)을 넘지 못하게 한다. |

### 공부하며 던진 질문

이 장도 개념 정리 장이라 문제 풀이 없이 진행했다.

- **앞부분이 같은지 판단하는 기준이 빡빡하지 않나?** 빡빡하다. 글자 하나만 달라도 그 뒤는 캐시를 못 쓴다. 대신 판단은 의미가 아니라 앞에서부터 기계적으로 같은지만 본다. 그래서 하네스가 앞부분을 건드리지 않게 설계된다.
- **한 번 한 대화는 수정하지 못하나?** 고칠 수 있다. 대신 고친 지점부터 캐시가 깨지고 그 뒤 대화를 다시 만들어야 해서, 평소에는 덧붙이기만 한다.
- **메모리 목록은 뭔가?** Claude가 직접 적는 공책의 목차다. 목차만 세션 시작 때 넣고 상세는 필요할 때 연다.
- **훅 → 도구 → 훅으로 진행되나?** 도구 한 번을 감싸면 그렇다. 다만 세션 시작·입력·끝내기처럼 도구와 상관없는 훅도 있고, 설정하지 않으면 훅은 없다.
- **차단에도 단계가 이렇게 많나?** 심층 방어다. 한 층이 놓친 걸 다음 층이 잡게 겹친다. 대신 층이 많으면 불편해져서 균형이 필요하다.

## 예제와 확인 결과

실행 환경은 Windows 11, Claude Code 2.1.330, 모델은 Claude Opus 5.5였다.

- **요청당 입력 토큰:** 세션 기록(JSONL)의 응답별 `usage`에서 `input_tokens + cache_read_input_tokens + cache_creation_input_tokens`를 응답 ID로 중복 없이 셌다. 1번째 요청은 46,496이었고, 마지막으로 잰 요청은 490,109였으며 그중 474,725가 캐시 읽기였다.
- **지시 파일 변경이 덧붙여져 들어온 것:** 세션을 다시 열었을 때 전역 CLAUDE.md의 바뀐 내용이 대화 중간에 새 메시지로 들어왔다.
- **첫 요청에 깔린 것:** 3절의 표는 Claude가 자기 컨텍스트에 실제로 들어와 있는 것을 종류별로 정리한 것이다. 항목별 토큰 수는 세지 못했다. Claude Code의 `/context` 명령으로 확인할 수 있다.
- **문서로 확인한 것:** CLAUDE.md가 들어가는 자리, 메모리 200줄·25KB, 스킬 설명만 먼저 넣기, 압축 뒤 남는 것, 훅 이벤트와 exit code, 권한 평가 순서와 모드, 샌드박스 동작은 Claude Code 공식 문서를 기준으로 했다.
- **설명용:** `settings.json`의 훅 설정과 deny 규칙 예시는 설명용이고 실행하지 않았다. deny 규칙을 다른 형태의 명령으로 빠져나갈 수 있다는 건 패턴 매칭의 일반적인 한계이고, 직접 실험하지는 않았다.
