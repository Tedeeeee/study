# 모델은 글만 만드는데, 어떻게 파일을 고칠까?

[목차](README.md)

## 다루는 범위

AI 코딩 도구가 일하는 가장 바닥의 구조를 따라간다. 하네스가 무엇인지 말하려면, 먼저 모델과 도구가 어떻게 나눠서 일하는지 알아야 한다.

- 모델은 "실행 요청서"를 쓰고, 실행은 Claude Code가 한다 (`tool_use`와 `tool_result`)
- 모델은 Claude Code가 알려 준 도구 중에서만 고른다
- 요청서 한 장으로 안 끝나면 반복한다: 에이전트 루프
- 다시 도는 조건은 하나뿐이고, 테스트는 조건이 아니다
- 루프가 멈추는 이유를 알려 주는 값: `stop_reason`
- 에이전트 = 모델 + 하네스, 그리고 하네스 안에서 문서와 코드가 하는 일의 차이

모델이 대화를 어떻게 "기억"하는지와 CLAUDE.md가 들어가는 자리는 [2번 주제](README.md#공부-계획)에서, 루프에 코드를 끼우는 훅은 4번 주제에서 다룬다. 이 문서의 코드는 설명용이고, 숫자는 "예제와 확인 결과"에 적은 것만 실제로 확인한 값이다.

## 시작한 질문

AI에게 "테스트 깨진 거 고쳐 줘"라고 하면, AI가 파일을 읽고, 고치고, 테스트까지 돌린다. 그런데 모델은 글을 받아서 글을 이어 쓰는 것밖에 못 하는 프로그램이다.

1. 내 PC의 파일은 누가 고친 걸까?
2. AI는 언제까지 일하고, 언제 "다 했다"고 멈출까? 테스트가 통과할 때까지 도는 걸까?

## 내가 이해한 내용

### 1. 모델은 "실행 요청서"를 쓰고, 실행은 Claude Code가 한다

모델은 Anthropic 서버에서 돌고, Claude Code는 내 PC에서 도는 별개의 프로그램이다. 모델은 파일도 터미널도 만질 수 없다.

```text
[모델] Anthropic 서버                        [Claude Code] 내 PC
  글을 받아 글을 쓰기만 한다     ◀── 대화 ────────
  "Bash로 이 명령 실행해 줘"     ── tool_use ───▶   실제로 명령을 실행
                                 ◀── tool_result ─   실행 결과를 글로 만들어 보냄
```

- 모델이 돌려주는 것은 "이 도구에 이 입력을 넣어 실행해 줘"라는 정해진 형식의 글이다. 이것이 `tool_use`(요청서)다.
- 그 요청서를 받아 실제로 실행하는 것은 Claude Code다.
- 실행 결과는 `tool_result`로 `role: user` 자리에 붙어서 돌아간다. 모델 입장에서는 실행 결과도 "상대가 보내 온 글"이다. 어느 요청서의 결과인지는 `tool_use_id`로 짝을 맞춘다.

백엔드로 비유하면 302 응답과 비슷하다. 서버는 브라우저를 직접 옮기지 못하고 "저기로 가"라는 응답만 준다. 실제로 이동하는 건 브라우저다. 모델은 "이걸 실행해"라는 응답만 주고, 실제로 실행하는 건 Claude Code다.

그래서 **파일을 고친 건 모델이 아니라 Claude Code다.** 모델은 무엇을 할지 정하고, Claude Code가 손이 되어 실행한다.

### 2. 모델은 Claude Code가 알려 준 도구 중에서만 고른다

Claude Code는 모델에게 요청을 보낼 때마다 대화와 함께 "내가 해 줄 수 있는 일 목록"을 같이 보낸다. 도구 하나는 이름, 설명, 입력 형식으로 되어 있다.

```json
{
  "name": "Read",
  "description": "파일을 읽는다. 절대 경로를 넣는다.",
  "input_schema": {
    "type": "object",
    "properties": { "file_path": { "type": "string" } },
    "required": ["file_path"]
  }
}
```

모델의 판단은 이렇게 돌아간다.

1. 대화를 읽는다. "저장소를 원격에 맞춰 달라는구나."
2. 받은 도구 목록을 본다. "Bash가 있네. 여기에 `git pull`을 넣으면 되겠다."
3. 목록에 적힌 입력 형식을 정확히 지켜서 요청서를 쓴다. "대충 이런 거 해 줘"가 아니다.
4. Claude Code가 그 요청서대로 실행한다.

목록에 없는 도구는 쓸 수 없다. 그래서 **어떤 도구를 줄지도 하네스가 정한다.** 목록은 늘릴 수도 있다. MCP 서버를 붙이면 Claude Code가 그 도구도 목록에 넣어 보내고, 모델은 기본 도구인지 붙인 도구인지 구분하지 않고 쓴다.

### 3. 요청서 한 장으로 안 끝나면 반복한다: 에이전트 루프

"테스트 깨진 거 고쳐 줘"는 한 번에 안 끝난다. 파일을 읽어 봐야 어디를 고칠지 알고, 고친 뒤에는 테스트를 돌려 봐야 끝났는지 안다. 그래서 Claude Code는 계속 다시 묻는다.

```text
사용자: "테스트 깨진 거 고쳐 줘"
   ↓
┌→ Claude Code가 모델에게 보냄: 지금까지의 대화 + 도구 목록
│     ↓
│  모델의 답에 요청서가 있나?
│     ├─ 있다 → Claude Code가 실행하고, 결과를 대화 끝에 붙임 ─┐
└─────┴──────────────────────────────────────────────────────┘
      └─ 없다 → 모델이 쓴 글을 사용자에게 보여 주고 끝
```

실제 작업에서는 이 반복이 길다. 회사 프로젝트에서 Claude Code가 일한 기록 하나를 보면, 끝나기 직전 13분 동안만 모델에게 60번 넘게 다시 물었고 도구를 126번 실행했다. 흐름을 줄이면 이렇다.

```text
코드 수정 → 타입 검사·테스트 실행 → 테스트 4개 실패 발견 → 테스트 수정
→ 다시 실행 → 또 실패 → "원래부터 깨져 있던 건가?" 확인 → 내 것만 수정
→ 다시 실행 → 통과 → "반영했습니다" (요청서 없음 → 끝)
```

여기서 누가 무엇을 정하는지가 중요하다.

| | 누가 |
| --- | --- |
| 반복문을 돌리는 것 | Claude Code |
| 다음에 무엇을 할지 | 모델 |
| 언제 끝낼지 | 모델 (요청서를 안 쓰면 끝) |

### 4. 다시 도는 조건은 하나뿐이고, 테스트는 조건이 아니다

| | 조건 |
| --- | --- |
| 다시 돈다 | 모델의 답에 요청서(`tool_use`)가 있다 |
| 끝난다 | 요청서가 없다 (`stop_reason: "end_turn"`) |

"테스트 실패 → 수정 → 다시 실행 → 성공 → 끝"은 실제로 자주 보이는 **모습**이지만 **조건**은 아니다. 같은 흐름에 Claude Code가 보는 것을 붙이면 차이가 보인다.

```text
                                     Claude Code가 보는 것
모델: "테스트 돌려 줘"               요청서 있음 → 실행하고 다시 묻기
결과: 실패
모델: "여기 고칠게" (Edit)           요청서 있음 → 실행하고 다시 묻기
모델: "다시 돌려 줘"                 요청서 있음 → 실행하고 다시 묻기
결과: 성공
모델: "다 고쳤습니다"                요청서 없음 → 끝
```

Claude Code는 오른쪽만 본다. 테스트 결과는 Claude Code가 먼저 받지만, **해석하지 않고 그대로 모델에게 배달만** 한다. 상자를 받아 배달은 하지만 열어 보지 않는 택배 기사와 같다. 명령이 실패 코드로 끝나면 `is_error: true` 표시를 붙이는 정도가 전부고, 그 표시를 보고 루프를 어떻게 할지도 정하지 않는다.

그래서 이런 일이 똑같이 일어날 수 있다.

| 흐름 | 루프 |
| --- | --- |
| 실패 → 모델: "원래 깨져 있던 거라 두었어요" | 끝난다 (테스트가 실패했는데도) |
| 성공 → 모델: "통과했으니 린트도 돌려 볼게요" | 계속 돈다 (테스트가 성공했는데도) |
| 테스트를 아예 안 돌림 → 모델: "다 했습니다" | 끝난다 |

모델이 "원래 깨져 있었다"고 판단하는 것도 기억이 아니다. 작업 전 코드에서 같은 테스트를 돌려 본 결과가 대화에 붙어 있고, Claude Code가 매번 대화 전체를 다시 보내기 때문에 모델이 그걸 **보면서** 판단하는 것이다. 테스트 다음에 린트를 돌린다는 것도 보통 대화나 CLAUDE.md 같은 지침에 적혀 있어서 안다.

**"테스트가 통과할 때까지 돈다"는 기본 기능이 아니라, 하네스로 따로 만들어야 하는 장치다.** 모델이 끝내려는 순간 코드가 테스트를 돌리고, 실패하면 이유를 돌려줘서 루프를 다시 돌게 만드는 것이다(6번 주제의 완료 게이트).

### 5. 루프가 멈추는 이유: `stop_reason`

모델은 답을 줄 때마다 왜 여기서 멈췄는지를 `stop_reason`으로 같이 알려 준다.

| `stop_reason` | 뜻 | 하네스가 할 일 |
| --- | --- | --- |
| `tool_use` | 요청서를 끝까지 다 썼다 | 실행하고 다시 묻기 |
| `end_turn` | 할 말을 다 했다 | 사용자에게 보여 주고 끝 |
| `max_tokens` | 한 번에 쓸 수 있는 길이 한도에 걸려 중간에 잘렸다 | 끝난 게 아니다. 요청서가 들어 있어도 실행하지 않고, 한도를 늘려 다시 요청한다 |
| `refusal` | 안전 기준에 걸려 거절했다 | 끝. 요청서가 있어도 실행하지 않는다 |

이 밖에 `stop_sequence`, `pause_turn`도 있지만 코딩 도구에서는 드물다.

`stop_reason !== "tool_use"`면 끝으로 보는 단순한 반복문은 잘린 답(`max_tokens`)도 정상 종료처럼 처리해 버린다. 반대로 "답 안에 요청서가 있으면 무조건 실행"하면 더 위험하다. 잘린 요청서는 입력이 중간에 끊긴 채로 오는데, 모양은 멀쩡해 보일 수 있다.

```text
모델이 쓰려던 요청서:  Bash { command: "git checkout -- src/legacy/old-util.ts" }  (파일 하나 되돌리기)
잘려서 도착한 요청서:  Bash { command: "git checkout -- src/" }                    (src 전체의 수정을 되돌림)
```

그래서 실제 하네스는 경우를 나눈다.

```js
switch (res.stop_reason) {
  case "tool_use":   // 요청서대로 실행하고, 결과를 붙여 다시 묻기
  case "end_turn":   // 사용자에게 보여 주고 끝
  case "max_tokens": // 잘림. 잘린 요청서는 버리고, 한도를 늘려 다시 요청
  case "refusal":    // 끝. 요청서가 있어도 실행하지 않기
}
```

루프 밖에서 멈추는 경우도 있다. 사용자가 Esc로 끊거나, 권한 확인에서 거절되거나, API 오류가 계속되면 Claude Code가 멈춘다.

정상적으로 끝나는 길은 `end_turn` 하나고, 그 뜻은 "일이 끝났다"가 아니라 **"모델이 끝났다고 생각한다"**다.

### 6. 에이전트 = 모델 + 하네스

모델을 뺀 나머지 전부가 하네스다. 1~5에서 본 반복문, 도구 목록, 요청서 실행, `stop_reason` 처리가 전부 하네스였다.

```text
에이전트
├─ 모델                             ← 글을 읽고, 다음에 할 일을 정한다
└─ 하네스                           ← 나머지 전부
   ├─ Claude Code가 이미 만든 것     (전부 코드)
   │    반복문, 도구 목록과 실행, stop_reason 처리, 실행 전 권한 확인,
   │    대화 다시 보내기와 압축, CLAUDE.md·스킬 넣어 주기, 훅 자리 열어 두기
   └─ 우리가 그 위에 얹는 것
        ├─ 문서: CLAUDE.md, 스킬                 → 모델이 읽고 따르려고 한다
        └─ 코드: 검사 스크립트, 테스트, 훅, CI   → 모델과 상관없이 돌아간다
```

같은 모델이라도 claude.ai 채팅창에서는 내 PC 파일을 못 고치고, Claude Code에서는 고친다. 모델은 똑같으니 차이를 만드는 건 하네스다. 그리고 팀이 할 일은 이 하네스를 새로 만드는 게 아니라, 이미 있는 하네스 위에 프로젝트에 맞는 층을 얹는 것이다.

우리가 얹는 층에서 문서와 코드는 하는 일이 다르다.

| | 문서 | 코드 |
| --- | --- | --- |
| 어디에 작용하나 | 모델의 판단 | 실제로 일어난 일 |
| 예 | "끝내기 전에 테스트를 돌려라" | 끝내려 할 때 테스트를 직접 돌려 본다 |
| 모델이 어기면 | 그냥 지나간다 | 잡는다 |

문서를 세게 쓰면 모델이 따를 가능성은 올라가지만, 보장은 아니다. `end_turn`이 "모델이 끝났다고 생각한다"는 뜻이니, 문서는 그 생각에 영향을 줄 수 있을 뿐이다. 실제로 끝났는지는 코드만 확인할 수 있다.

위험한 명령을 막는 것도 같은 이야기다. 막는 주체는 모델이 아니라 Claude Code다. 요청서를 받은 뒤 실행하기 전에 허용 목록을 보고, 없으면 사람에게 묻는다. 이 확인을 끈 모드에서는 묻지 않고 바로 실행된다. 같은 Claude Code라도 하네스 설정에 따라 막기도 하고 통과시키기도 한다.

## 헷갈렸던 점

| 처음의 생각 | 정리한 내용 |
| --- | --- |
| 하네스는 테스트를 만들고, 통과할 때까지 계속 돌리는 것이다 | 하네스는 모델을 뺀 나머지 전부다. "통과할 때까지 돌리기"는 하네스로 만들 수 있는 장치 하나(완료 게이트)일 뿐, 기본 동작이 아니다. |
| 다시 도는 조건은 "테스트 실패 → 수정 → 다시 실행"이다 | 그건 모델이 잘 판단했을 때 나오는 모습이다. 조건은 "모델의 답에 요청서가 있느냐" 하나다. |
| 실패라는 결과를 Claude Code가 판단해서 전달하는 것 아닌가 | Claude Code는 결과를 먼저 받지만 해석하지 않고 그대로 배달한다. "실패구나"를 읽는 건 모델이다. |
| 모델이 앞에서 확인한 것을 기억한다 | 기억이 아니다. Claude Code가 매번 대화 전체를 다시 보내서, 확인한 기록을 보면서 판단한다. |
| 모델이 테스트 뒤에 할 일을 알고 있다 | 보통 대화나 CLAUDE.md 같은 지침에 적혀 있어서 안다. 적혀 있지 않으면 일반적인 습관대로 할 뿐이다. |
| 테스트 결과가 꼭 루프의 종료 조건은 아닐 수 있다 | "아닐 수 있다"가 아니라, 기본적으로 종료 조건이 아니다. |
| CLAUDE.md 문구를 "성공할 때까지"로 고치면 보장된다 | 문서는 모델의 판단에만 작용한다. 문구를 세게 써도 모델이 `end_turn`을 보내면 루프는 끝난다. |
| 요청서가 있으면 무조건 실행해야 한다 | 완성된 요청서(`stop_reason: "tool_use"`)만 실행한다. `max_tokens`로 잘린 요청서는 모양이 멀쩡해도 실행하면 안 된다. |
| 위험한 명령은 (누군가) 막는다 | 막는 건 모델이 아니라 Claude Code의 권한 확인이고, 설정에 따라 막지 않을 수도 있다. |
| 하네스가 종료된다 | 하네스는 계속 있다. 끝나는 건 이번 차례의 루프다. |

### 확인 문제와 내 답

| 문제 | 내 답의 요지 | 결과 |
| --- | --- | --- |
| 1. "모델이 내 PC에 접속해서 `rm -rf`를 직접 칠 수 있다"는 말의 맞는 부분과 틀린 부분 | 그럴 수 없다. 모델은 먼저 말을 걸어야 움직이고, 위험한 명령은 막는다 | 부분 통과. 요청서 → Claude Code 실행 → 결과의 흐름, "명령이 내 PC에서 실제로 실행될 수는 있다"는 맞는 부분, 막는 주체가 Claude Code라는 점이 빠졌다 |
| 2. CLAUDE.md에 "테스트를 돌려라"라고 썼는데 테스트가 깨진 채 끝났다. 어떻게 가능하고, 팀원 말의 어디가 틀렸나 | 루프는 테스트에 의존하지 않고, 대화 흐름을 보고 테스트가 실패해도 끝날 수 있다 / "반드시 돌려라"라고만 했지 "성공할 때까지"라고 안 했다 | 앞은 부분 통과(조건을 정확히 말하기, 안 돌렸거나 잘못 읽었을 가능성). 뒤는 다시. 문구 탓으로 봤다 |
| 2 재시험. 문구를 "통과할 때까지 절대 끝내지 마라"로 바꾸면 안 일어날까 | Claude Code는 모델 판단대로 실행할 뿐이라, 모델이 `end_turn`을 보내면 문제가 있든 없든 끝난다 | 통과 |
| 3. `stop_reason !== "tool_use"`면 끝내는 반복문에서, 긴 파일을 쓰다 답이 잘렸다 / "요청서가 있으면 무조건 실행"으로 바꾸면 | 너무 길면 잘리고, 반복문이 끝으로 처리한다 / 위험한 명령이 있을 수 있어 주의해야 한다 | 앞은 부분 통과(`max_tokens`라는 이름과 처리 방법이 빠짐). 뒤는 다시. 잘린 요청서라는 이 상황만의 위험을 못 봤다 |
| 3 재시험. `git checkout -- src/legacy/old-util.ts`가 `git checkout -- src/`에서 잘렸다 | `max_tokens`라 실행하면 안 된다 / 의도하지 않은 명령이 실행된다 / 뒷내용을 확인한 뒤 실행한다 | 통과. `src` 전체의 수정이 날아간다는 구체적인 피해, 그리고 잘린 요청서는 버리고 다시 요청하는 게 더 안전하다는 점을 보충했다 |
| 4. (면접) 하네스가 정확히 뭔가요? 문서를 잘 써 둔 것과 뭐가 다른가요? | 제각각인 개발과 인지부채 때문에 기획 → 구현 계획 → 구현 → 검증 흐름을 정했고, 스킬만으로는 확신할 수 없어 검증 스크립트로 타입·테스트·계층을 검증했다 | 부분 통과. 하네스의 정의(모델 + 하네스, 두 층)와 문서가 왜 보장을 못 하는지가 빠졌다 |
| 4 꼬리 질문. 그 검증 스크립트는 누가, 언제 실행하나요? AI가 안 돌리고 끝내면요? | PR로 개발 브랜치에 올릴 때 스크립트를 돌린다 | 부분 통과. 작업 중에는 AI가 돌리기로 할 때만 돈다는 것, 그래서 문제를 PR에서야 늦게 알게 된다는 비용이 빠졌다 |

4번의 모범 답안은 이렇게 정리했다.

> 하네스는 AI 모델을 감싸는 바깥 장치 전부입니다. 코딩 에이전트는 모델과 하네스로 이뤄지는데, 모델은 다음에 할 일을 정할 뿐이고, 도구를 실행하고 결과를 돌려주고 언제 멈출지 처리하는 건 Claude Code 같은 도구가 이미 하네스로 갖고 있습니다. 저는 그 위에 팀의 하네스를 얹었습니다. 문서와 다른 점은 보장입니다. 문서는 모델이 읽고 따르려고 할 뿐이라, 기계가 판정할 수 있는 규칙은 스크립트로 옮겨 코드가 확인하게 했습니다.
>
> 다만 작업 중에는 AI가 지침에 따라 스스로 스크립트를 돌리는 구조라, AI가 안 돌리고 끝내면 그 자리에서는 막지 못합니다. PR에서 CI가 반드시 돌리기 때문에 머지는 막지만, 문제를 늦게 알게 됩니다. 그래서 AI가 끝내려는 순간에 검사를 강제하는 것을 다음 개선 지점으로 보고 있습니다.

## 예제와 확인 결과

실행 환경: Windows 11, Claude Code 2.1.330, 모델 Claude Opus 5.5. 세션 기록은 Claude Code가 남기는 JSONL 파일(`~/.claude/projects/<프로젝트>/<세션 ID>.jsonl`)에서 읽었다.

**1. 요청서와 결과의 실제 모습**

이 공부를 하던 대화에서 Claude가 저장소를 원격에 맞추며 남긴 기록이다(내용 일부 생략).

```jsonc
// 모델이 쓴 것 (role: assistant, stop_reason: "tool_use")
{ "type": "tool_use", "id": "toolu_017neu…", "name": "Bash",
  "input": { "command": "git pull --ff-only origin main …" } }

// Claude Code가 돌려준 것 (role: user)
{ "type": "tool_result", "tool_use_id": "toolu_017neu…",
  "content": " spring/filter.md | 129 +++… 10 files changed, 1325 insertions(+) …" }
```

**2. `is_error`가 결과의 뜻을 모른다는 예**

회사 프로젝트 기록에서 모델이 테스트 출력을 `npm run test:fast | grep …`처럼 grep으로 걸러 본 적이 있다. 파이프의 마지막 명령(grep)이 성공해서 exit code가 0이 됐고, Claude Code는 `is_error: false`로 배달했다. 결과 글 안에는 실패한 테스트(`×`)가 찍혀 있었고, 그걸 알아본 건 글을 읽은 모델이었다.

**3. 이 PC의 Claude Code 기록 전체에서 `stop_reason` 세기**

기록은 응답 하나를 블록마다 여러 줄로 나눠 적기 때문에, 응답 ID(`message.id`)로 중복을 지우고 셌다.

```python
import json, glob, collections
seen = {}
for f in glob.glob('**/*.jsonl', recursive=True):
    for line in open(f, encoding='utf-8', errors='ignore'):
        if '"stop_reason":"' not in line: continue
        try: m = json.loads(line).get('message') or {}
        except json.JSONDecodeError: continue
        if m.get('stop_reason') and m.get('id'):
            seen[m['id']] = m['stop_reason']
print(collections.Counter(seen.values()))
```

| `stop_reason` | 응답 수 | 비율 |
| --- | --- | --- |
| `tool_use` | 6,206 | 76% |
| `end_turn` | 1,924 | 24% |
| `stop_sequence` | 10 | 0.1% |
| `refusal` | 1 | 0.01% |
| `max_tokens` | 0 | 0% |

응답 네 번 중 세 번은 "요청서가 있으니 계속", 한 번은 "끝"이었다. `max_tokens`는 한 번도 없었지만, 한 번 터지면 피해가 크니 하네스는 처리해야 한다.

**설명용 예제:** 2·3·5절의 반복문 코드, 도구 정의, 잘린 요청서 예시는 실행하지 않은 설명용이다.

## 남은 질문

- 모델은 한 번 답할 때 요청서를 여러 장 쓸 수 있다(병렬 도구 호출). 회사 기록에서 60번 남짓 묻는 동안 도구가 126번 실행된 것도 이 때문으로 보인다. Claude Code는 여러 장을 어떻게 실행하고 결과를 어떻게 돌려줄까?
- Claude Code는 `max_tokens`로 잘린 답을 실제로 어떻게 처리할까?
- 권한 확인에서 거절하면 루프는 어떻게 될까? 모델에게 무엇이 돌아갈까?
- 매번 대화 전체를 다시 보내면, 대화가 길어질수록 느리고 비싸지지 않을까? (2번 주제)
- 요청서를 받은 뒤 실행하기 전, 그리고 모델이 끝내려는 순간에 코드를 끼우려면 어떻게 할까? (4·6번 주제)
- Codex는 같은 루프를 어떻게 돌리고, 실행 전 확인은 어떻게 다를까?
