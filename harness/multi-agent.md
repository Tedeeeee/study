# 여러 에이전트로 나누면 무엇이 좋아지고 무엇이 비싸질까?

[목차](README.md) · [이전: 몇 시간짜리 일은 어떻게 이어 갈까?](long-running-work.md)

## 다루는 범위

일을 여러 에이전트에게 동시에 나눠 맡길 때 무엇이 좋아지고, 무엇이 비싸지고, 언제는 오히려 망가지는지 정리한다.

- 지휘자와 작업자 구조, 그리고 좋아지는 이유
- 토큰 비용과 일 크기
- 서로 얽힌 일을 나눌 때 생기는 충돌, 중복과 충돌의 차이, 컨벤션과 계약
- 실제 구조: 기획자·개발자·검사자, 스프린트 계약, Claude Code 서브 에이전트와 에이전트 팀, Codex 멀티 에이전트

여러 에이전트가 남긴 기록으로 하네스를 평가하는 법은 [11번 주제](README.md#공부-계획)에서 다룬다.

## 시작한 질문

9장에서는 긴 일을 시간 순서대로 창을 바꿔 가며 이어 갔다. 이번에는 창 여러 개가 동시에 일하는 경우다.

1. 여러 에이전트로 나누면 무엇이 좋아질까?
2. 무엇이 비싸지고, 언제는 오히려 망가질까?
3. 실제 하네스와 도구는 어떻게 나눠 쓸까?

## 내가 이해한 내용

### 1. 9장과 무엇이 다른가

| | 9장 교대 세션 | 10장 여러 에이전트 |
| --- | --- | --- |
| 나누는 기준 | 시간 (창을 차례로 교대) | 동시에, 역할로 (창 여러 개가 함께 일함) |
| 위에 누가 있나 | 없음. 바깥 루프만 | 지휘자 창이 있음 |
| 이어 주는 것 | 폴더의 파일 | 작업자가 지휘자에게 돌려주는 요약 |

### 2. 지휘자와 작업자

가장 대표적인 구조가 지휘자-작업자(orchestrator-worker)다. Anthropic이 Claude의 리서치 기능을 만든 글(2025-06)에 나온다.

```text
지휘자 창: "AI 코딩 도구 회사들 조사해 줘" → 계획 세움
  ├ 작업자 A 창: 미국 회사 조사      ─┐
  ├ 작업자 B 창: 유럽 회사 조사       ├ 동시에, 각자 자기 창에서
  └ 작업자 C 창: 오픈소스 쪽 조사    ─┘
       ↓ 각자 찾은 걸 요약해서 돌려줌
지휘자: 요약을 합쳐서 최종 답
```

4장의 서브 에이전트를 여러 개, 동시에 띄우는 것이다. 글에서 꼽는 좋아지는 이유는 세 가지다.

1. **병렬**: 여러 방향을 동시에 판다. "여러 독립적인 방향을 동시에 쫓는 넓은 질문"에 특히 강하다.
2. **압축**: 글의 표현으로 "검색의 본질은 압축"이다. 작업자가 자료를 잔뜩 읽고 요약만 올리니 지휘자 창은 가볍게 유지된다. 4장의 "컨텍스트 방화벽"이다.
3. **관심사 분리**: 작업자마다 도구, 프롬프트, 탐색 경로를 다르게 줄 수 있다.

지휘자 Opus 4 + 작업자 Sonnet 4 조합이 Opus 4 혼자보다 Anthropic 내부 리서치 평가에서 90.2% 더 좋았다. 지휘는 비싸고 똑똑한 모델에, 작업은 그보다 싼 모델에 맡긴 구성이다.

**싼 모델에 맡겨도 되는 조건.** 지휘자가 일을 잘 쪼개서 분명하게 시켜야 한다. 작업 설명이 자세하지 않으면 작업자들이 같은 일을 중복하거나, 빈 곳을 남기거나, 필요한 걸 못 찾았다. 그래서 지휘자가 작업자에게 일을 줄 때 네 가지를 넣게 했다.

1. 목표
2. 결과 형식
3. 쓸 도구와 자료
4. 어디까지가 네 일인지(경계)

| | 하는 일 | 난이도 |
| --- | --- | --- |
| 지휘자 | 계획, 쪼개기, 경계 정하기, 결과 합치기 | 어려움 → 똑똑한 모델 |
| 작업자 | 좁고 분명한 범위 안에서 찾고 요약하기 | 상대적으로 쉬움 → 싼 모델로도 됨 |

나누는 것만큼 합치는 것도 지휘자의 일이다. 작업자마다 결과를 제멋대로 정리하면 형식이 제각각이 된다. 지휘자가 형식을 정해서 주고, 돌아온 결과를 하나로 합친다.

내 해석으로는 비용 면에서도 맞는 구조다. 토큰을 제일 많이 쓰는 건 자료를 잔뜩 읽는 작업자들이라, 그 자리에 싼 모델을 두면 전체 비용이 크게 준다.

글에는 9장과 이어지는 장치도 있다. 지휘자는 계획을 메모리에 저장해 둔다. 컨텍스트가 20만 토큰을 넘으면 잘리기 때문이다.

### 3. 무엇이 비싸지나

Anthropic 리서치 글의 숫자다(일반 채팅 대비).

| 방식 | 토큰 사용량 |
| --- | --- |
| 일반 채팅 | 1 |
| 에이전트 하나 | 약 4배 |
| 여러 에이전트 | 약 15배 |

같은 글에서 리서치 평가(BrowseComp)의 성능 차이 중 80%가 토큰 사용량 하나로 설명됐다. 여러 에이전트가 잘하는 큰 이유는 토큰을 동시에 많이 쓸 수 있어서이고, 그러니 그만큼 값어치 있는 일에만 써야 한다(내 해석).

초기에는 간단한 질문에도 작업자를 50개씩 띄우는 실수가 있었다. 그래서 일 크기별 규칙을 프롬프트에 넣었다.

- 간단한 사실 찾기: 에이전트 1개, 도구 호출 3~10번
- 복잡한 리서치: 작업자 10개 이상, 책임을 분명히 나눠서

8장의 "작업 크기에 따라 게이트 강도를 다르게"와 같은 생각이다. 이런 규칙이 없으면 AI는 도구가 있으면 쓰려는 쪽으로 기운다. 예전에 간단한 일을 시켜도 에이전트가 무조건 돌던 경험이 이것이었다.

### 4. 언제 망가지나

"안 맞는다"는 두 가지 뜻이다.

| | 뭐가 안 맞나 | 결과 | 예 |
| --- | --- | --- | --- |
| 크기가 안 맞음 | 작은 일에 에이전트를 잔뜩 띄움 | 낭비 (토큰·시간) | 간단한 질문에 작업자 50개 |
| 일의 성격이 안 맞음 | 서로 얽힌 일을 나눠서 동시에 함 | 망가짐 (결과가 안 맞음) | 플래피 버드 배경과 새 |

두 번째는 일이 커도 생긴다. Cognition(Devin을 만든 회사)은 같은 달에 "Don't Build Multi-Agents"라는 글을 냈다.

> "플래피 버드 만들어 줘"를 둘로 나눴다.
> - 작업자 1(배경과 파이프): 슈퍼 마리오 같은 배경을 만들었다.
> - 작업자 2(새): 게임 그림 같지도 않고, 움직임도 플래피 버드와 달랐다.
> - 합쳐 보니 스타일이 전혀 안 맞았다.

글의 원칙은 두 가지다.

1. 맥락을 공유해라. 메시지 몇 줄이 아니라 앞에서 일어난 전체 흐름을 공유해야 한다.
2. 행동에는 숨은 결정이 들어 있고, 결정이 엇갈리면 결과가 나빠진다.

"배경을 어떤 스타일로 그릴까"는 작업자 1이 혼자 내린 결정이다. 백엔드로 치면 API 스펙도 안 정하고 프론트와 백엔드를 각자 만들다가 합칠 때 안 맞는 것과 같다. Cognition은 에이전트 하나가 한 줄로 쭉 가는 구조를 권한다.

Anthropic 글도 같은 한계를 인정한다.

- 모든 에이전트가 같은 맥락을 공유해야 하는 일은 지금은 맞지 않는다.
- 대부분의 코딩 작업은 리서치보다 진짜로 병렬로 할 수 있는 부분이 적다.
- 에이전트들은 아직 실시간으로 조율하고 맡기는 걸 잘 못한다.

**중복과 충돌은 다른 문제다.**

| 문제 | 뜻 | 지휘자가 막을 수 있나 |
| --- | --- | --- |
| 중복 | 같은 일을 두 작업자가 함 | 잘 막는다. 경계를 분명히 나눠 주면 된다 |
| 충돌 | 서로 다른 일을 했는데 합치니 안 맞음 | 일부만 막는다 |

지휘자를 똑똑한 모델로 바꾸고 설명을 자세히 쓰면 중복과 빈 곳은 많이 준다. 하지만 숨은 결정은 일하는 도중에 생긴다. "새 날개를 몇 프레임으로 움직일까" 같은 걸 지휘자가 처음에 다 예상해서 적을 수는 없고, 다 적으려면 지휘자가 일을 다 하는 셈이다. 그래서 충돌은 지휘자 문제가 아니라 구조의 한계다.

**컨벤션과 계약도 다르다.**

| | 컨벤션 | 계약 |
| --- | --- | --- |
| 뭔가 | 모든 작업에 쓰는 공통 규칙 | 이번 작업에서만 쓰는 약속 |
| 예 | 네이밍 규칙, 패키지 구조, 예외 처리 방식 | `refund()`의 인자와 반환값은 이렇게 한다, 결제 파일은 A만 고친다 |
| 막는 충돌 | 모양 충돌 (각자 다른 스타일로 짬) | 연결 충돌 (한쪽이 바꾼 게 다른 쪽을 깨뜨림) |

쓰기를 나누려면 컨벤션은 기본이고, 그 위에 이번 작업의 계약(인터페이스 고정, 파일별 담당)이 더 있어야 한다.

### 5. 실제로는 어떻게 나눠 쓰나

**Anthropic: 기획자, 개발자, 검사자.** 긴 앱 개발 하네스("Harness design for long-running application development", 2026-03)는 역할로 나눴다.

```text
Planner(기획자)    1~4문장짜리 요청 → 자세한 스펙으로 늘림
Generator(개발자)  스프린트 단위로 만듦 (git 사용)
Evaluator(검사자)  Playwright로 실제 앱을 사용자처럼 눌러 보고, 기준 못 넘으면 실패
```

- 코드를 쓰는 건 Generator 하나다. 나머지는 계획하고 검사만 한다. 그래서 충돌이 잘 안 생긴다(내 해석).
- Evaluator를 따로 둔 건 8장의 평가자 분리다.
- 스프린트 계약(sprint contract): 스프린트를 시작하기 전에 Generator와 Evaluator가 "이번에 뭐가 끝이고 어떻게 확인할지"를 먼저 합의한다(스프린트 3은 기준 27개). 에이전트끼리는 파일로 주고받는다. "부딪힐 결정을 미리 계약으로 정하기"의 실제 예다.
- 혼자 하면 20분/$9, 이 하네스로는 6시간/$200이었다. Opus 4.6에서는 스프린트 구조를 빼고 Evaluator를 마지막에 한 번만 돌려 3시간 50분/$124.70으로 줄였다. 9장처럼 모델이 좋아지니 부품을 걷어낸 사례다.

**도구에서는 이렇게 생겼다.**

| | Claude Code 서브 에이전트 | Claude Code 에이전트 팀 | Codex 멀티 에이전트 |
| --- | --- | --- | --- |
| 구조 | 메인이 띄우고, 요약만 메인으로 돌아옴 | 리드 세션 + 팀원들, 팀원끼리 직접 대화 | `spawn_agent`, `send_message`, `wait_agent` 같은 도구로 띄우고 주고받음 |
| 일 나누기 | 메인이 맡김 | 공유 작업 목록에서 팀원이 일을 가져감 | 띄운 쪽이 맡김 |
| 상태 | 정식 기능 | 실험 기능, 기본은 꺼짐 (`CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1`) | 소스에 있음 |
| 비용 | 낮음 (요약만 돌아옴) | 높음 (팀원 하나하나가 별도 Claude) | 확인 못 함 |

에이전트 팀의 공유 작업 목록은 9장의 기능 목록과 비슷하다. 문서가 정리한 쓰임새는 이렇다.

- 서브 에이전트: 빠르게 일하고 결과만 보고하는 작업자가 필요할 때
- 에이전트 팀: 팀원끼리 발견한 걸 공유하고, 서로 반박하고, 알아서 조율해야 할 때

같은 파일 충돌 경고는 양쪽에 다 있다.

- Claude Code 문서: "두 팀원이 같은 파일을 고치면 덮어쓴다. 팀원마다 다른 파일 묶음을 맡게 나눠라." "순차적인 일, 같은 파일 수정, 의존이 많은 일은 세션 하나나 서브 에이전트가 더 낫다."
- Codex 지시문: "모든 에이전트는 같은 폴더를 쓴다. 한 에이전트의 수정이 다른 에이전트에게 바로 보인다."

Cognition 글(2025-06)은 Claude Code 서브 에이전트가 메인과 동시에 코드를 쓰지 않고 보통 질문에 답하는 일만 맡는다고 썼다. 지금 문서에서는 general-purpose 서브 에이전트가 "탐색과 실행"을 다 한다. 대신 같은 파일은 나누라고 경고하는 쪽으로 바뀌었다.

### 6. 한 줄 정리

1. **왜 나누나**: 넓게 찾는 일을 동시에 하고, 각자 요약만 올려 지휘자 창을 가볍게 하려고.
2. **무엇이 문제인가**: 토큰이 약 15배 들고, 서로 얽힌 일을 나누면 숨은 결정이 엇갈려 결과가 안 맞는다.
3. **그래서 어떻게**: 읽기는 나누고, 쓰기는 한 명(또는 파일별 주인)에게 맡기고, 부딪힐 기준은 계약으로 먼저 정한다.

## 헷갈렸던 점

| 처음의 생각 | 정리한 내용 |
| --- | --- |
| 작업을 오히려 싼 모델에 시켜도 문제가 안 되나 | 지휘자가 일을 잘 쪼개서 분명하게 시키고, 작업끼리 얽히지 않는 일일 때 된다. 토큰을 제일 많이 쓰는 자리라 비용도 크게 준다. |
| 예전에 간단한 일을 시켜도 에이전트가 무조건 돌았다 | 일 크기별 규칙이 없으면 AI는 도구가 있으면 쓰려는 쪽으로 기운다. Anthropic도 같은 실수를 하고 프롬프트에 규칙을 넣어 고쳤다. |
| 충돌은 오케스트레이터 문제 아닌가, 작업은 겹칠 확률이 높다 | 중복(같은 일을 둘이 함)은 지휘자가 경계를 나눠 막을 수 있다. 충돌(다른 일인데 안 맞음)은 일하는 도중의 숨은 결정 때문이라 지휘자가 다 막지 못한다. |
| "안 맞는다"는 작은 일을 크게 만든다는 뜻이다 | 그건 크기가 안 맞는 경우(낭비)다. 일의 성격이 안 맞는 경우(얽힌 일을 나눠서 망가짐)는 일이 커도 생긴다. |
| 에이전트 팀도 지금 지원하나 | Claude Code 문서에 있다. 실험 기능이라 기본은 꺼져 있고 환경 변수로 켠다. 토큰이 훨씬 많이 들고 같은 파일 충돌을 조심해야 한다. |
| 코드 컨벤션에 따라 나눠서 할 수 있나 | 컨벤션은 모양 충돌을 줄이지만 연결 충돌은 못 막는다. 이번 작업의 계약(인터페이스 고정, 파일별 담당)이 더 있어야 한다. |
| 나눠서 하는 작업이 들어오니 어렵고 불안하다 | 맞는 감각이다. 도구 문서도 여러 에이전트에 경고를 잔뜩 달아 둔다. 세 줄 정리만 붙잡으면 된다. |
