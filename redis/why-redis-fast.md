# Redis는 왜 빠를까?

[목차](README.md)

## 다루는 범위

Redis가 무엇인지에서 출발해, 빠른 이유를 다섯 단계로 따라간다.

- 데이터가 항상 메모리에 있다는 것과 MySQL 버퍼 풀의 차이
- 한 번 읽을 때 하는 일의 양
- 명령을 스레드 하나로 처리한다는 것의 의미와 동시성
- 스레드 하나로 여러 연결을 받는 방법: I/O 멀티플렉싱, `epoll`, 이벤트 루프
- 진짜 병목인 네트워크 왕복(RTT)과 파이프라이닝

자료구조는 [2번 주제](README.md#공부-계획), 여러 명령을 묶는 `MULTI/EXEC`·Lua·분산 락은 5번 주제에서 자세히 다룬다. 이 문서의 숫자와 코드는 모두 설명용이다.

## 시작한 질문

상품 조회가 초당 5만 건이라 MySQL 앞에 Redis를 둔다고 한다. 그런데 Redis도 네트워크로 접속하는 별도 서버다.

1. 같은 데이터를 읽는데 왜 MySQL보다 빠를까?
2. Redis는 명령을 스레드 하나로 처리한다는데, 어떻게 그 많은 요청을 감당할까?

## 내가 이해한 내용

### 0. Redis는 여러 서버가 같이 쓰는 거대한 HashMap이다

Redis는 키로 값을 저장하고 꺼내는 서버다. 자바의 `HashMap`을 별도 서버로 떼어내서, 여러 애플리케이션 서버가 네트워크로 같이 쓰는 모습이다.

```text
[앱 서버 A] ──┐
[앱 서버 B] ──┼──▶ [Redis 서버]   product:1 → "키보드"
[앱 서버 C] ──┘

> SET product:1 "키보드"   ← map.put
> GET product:1            ← map.get
"키보드"
```

`HashMap`과 다른 점은 다음과 같다.

- 값 자리에 문자열뿐 아니라 List, Set 같은 **자료구조**를 넣을 수 있다. 그래서 `Map<String, 자료구조>`에 가깝다.
- 키마다 **만료 시간(TTL)**을 걸 수 있고, 백업과 복제를 지원한다.
- 모든 데이터가 메모리에 있으므로 서버 한 대에 담을 수 있는 양은 **RAM 크기까지**다. 그래서 보통 자주 쓰는 데이터만 넣는다.

**왜 Spring 안의 `ConcurrentHashMap`이 아니라 Redis를 쓸까?** 로컬 맵은 네트워크를 안 타니 더 빠르다. 하지만 서버가 3대면 맵도 3개가 따로 생긴다.

```text
[서버 1] product:1 = 50,000원   ← 가격 수정 요청이 여기로 와서 갱신됨
[서버 2] product:1 = 45,000원   ← 옛날 가격 그대로
[서버 3] (없음)                 ← 아직 안 읽어서 DB로 감
```

- 데이터가 서버마다 어긋난다.
- 같은 데이터를 서버마다 따로 DB에서 읽어서 DB 부하가 서버 수만큼 는다.
- 메모리가 중복되고, 재시작·배포하면 캐시가 사라진다.

Redis는 모든 서버가 같이 보는 저장소 하나라서 이 문제가 없다. 대신 네트워크를 한 번 탄다.

### 1. 데이터가 항상 메모리에 있다 (그런데 이것만으로는 부족하다)

RAM과 디스크는 속도 차이가 매우 크다. 너무 짧은 시간이라 감이 안 오니, RAM 한 번 읽는 시간을 1초로 늘려서 비교하면 이렇다.

| | 실제 시간 (대략) | RAM 대비 | RAM을 1초로 늘리면 |
|---|---|---|---|
| RAM | 100ns | 1배 | 1초 |
| SSD | 100µs | 1,000배 | 약 17분 |
| HDD | 10ms | 100,000배 | 약 28시간 |

단위는 한 칸 내려갈 때마다 1,000배씩 작아진다. `1초 = 1,000ms`, `1ms = 1,000µs`, `1µs = 1,000ns`.

**함정:** MySQL도 자주 읽는 데이터는 **InnoDB 버퍼 풀**에 올려두고 메모리에서 읽는다. 그러니 "Redis는 메모리, MySQL은 디스크라서 빠르다"는 절반만 맞다.

- **MySQL:** 원래 집은 디스크다. 한 번 읽은 데이터를 버퍼 풀에 올려둔다.
- **Redis:** 원래 집이 메모리다. 모든 데이터가 처음부터 항상 메모리에 있다. 디스크는 꺼졌을 때를 대비한 백업용이다.

### 2. 한 번 읽을 때 하는 일의 양이 다르다

둘 다 메모리에서 읽어도 데이터를 꺼내기까지 거치는 과정이 다르다.

```text
MySQL: SELECT * FROM product WHERE id = 1
  1. SQL 해석
  2. 실행 계획 세우기
  3. 트랜잭션 확인 (어느 시점의 데이터를 보여줄지)
  4. B+트리 인덱스를 몇 단계 내려가기
  5. 결과 형식으로 포장

Redis: GET product:1
  1. 단순한 명령 해석
  2. 해시 테이블에서 키로 바로 찾기 (O(1))
  3. 값 그대로 응답
```

MySQL은 조건 검색, 조인, 트랜잭션을 지원하느라 복잡하다. Redis는 그걸 포기하고 **"키를 알면 값을 준다"**만 잘하도록 단순하게 만들어서 빠르다. 그래서 Redis는 값 안을 들여다보는 조건 검색을 못 하고, 반드시 키를 알고 물어봐야 한다. 키 이름을 `product:1`처럼 애플리케이션이 계산해낼 수 있는 규칙으로 짓는 이유다.

### 3. 명령을 스레드 하나로 처리한다

Redis는 명령 실행을 **메인 스레드 하나**가 한다. 요청이 아무리 많아도 한 줄로 세워 하나씩 처리한다.

```text
요청들:      [GET a] [SET b] [GET c] [INCR d] ...
메인 스레드:  GET a → SET b → GET c → INCR d → ...
```

스레드 하나로도 괜찮은 이유와 장점:

- 명령 하나가 메모리 연산이라 **수 µs**면 끝난다. 하나씩 처리해도 1초에 수만~수십만 개를 처리한다. 그래서 스레드 하나로도 **충분하다.**
- 명령 실행이 동시에 일어나지 않으니 **Redis 내부 자료구조에 락이 필요 없다.** 락을 기다리는 비용과 컨텍스트 스위칭 비용이 없다.
- **명령 하나는 원자적**이다. 실행 중에 다른 명령이 끼어들 수 없다.

**대가:** 느린 명령 하나가 전체를 막는다. 키 500만 개에 `KEYS *`를 실행해 2초가 걸리면, 그 2초 동안 다른 모든 클라이언트의 명령이 줄 서서 기다린다. 운영에서는 `KEYS` 대신 조금씩 나눠 가져오는 `SCAN`을 쓴다.

#### 락이 필요 없다는 건 Redis 내부 이야기다

| | 락 필요? | 이유 |
|---|---|---|
| Redis 서버 내부 | 필요 없음 | 실행 스레드가 하나라 내부 자료구조를 동시에 건드리지 않음 |
| Redis를 쓰는 애플리케이션 로직 | 경우에 따라 필요 | 명령 여러 개 사이에 다른 요청의 명령이 끼어들 수 있음 |

Redis가 지켜주는 단위는 **명령 하나**다. Spring 요청 하나도, `@Transactional` 메서드 하나도 아니다. `@Transactional`은 DB 트랜잭션을 관리할 뿐 Redis 명령을 묶어주지 않는다.

```text
처음 stock = 1
  ① 서버1: GET stock → 1
  ② 서버2: GET stock → 1      ← ①과 ③ 사이에 끼어듦
  ③ 서버1: SET stock 0
  ④ 서버2: SET stock 0        → 재고 1개를 둘이 삼
```

동시성 문제가 생기는 조건은 **여러 요청이 같은 키를 대상으로, 명령 여러 개로 이뤄진 로직(읽고 → 판단하고 → 쓰기)을 실행할 때**다. Spring이 멀티 스레드라고 항상 문제가 되는 건 아니다.

#### 고치는 순서: 명령 하나 → Lua → 분산 락

1. **명령 하나로 바꾸기.** `INCR`, `DECR`은 "읽고 더하고 쓰기"를 명령 하나로 끝낸다. 선착순 쿠폰 100장이라면 먼저 `INCR`하고 **돌려받은 값**으로 판단한다. Redis는 100에서 멈추지 않고 계속 올리지만, 원자성 덕분에 모든 요청이 서로 다른 번호표를 받으므로 100 이하인 요청만 발급하면 정확히 100장이다.

   ```java
   Long count = redisTemplate.opsForValue().increment("coupon:count");
   if (count > 100) return;          // 멈추는 건 Redis가 아니라 내 코드
   couponRepository.save(new Coupon(userId));
   ```

2. **Lua 스크립트.** Redis 안에 Lua 실행기가 있어서, "읽기 → 판단 → 쓰기" 로직을 스크립트로 보내면 **스크립트 전체가 명령 하나처럼** 끼어듦 없이 실행된다. 대신 스크립트가 도는 동안 Redis 전체가 멈추므로 짧게 써야 한다.
3. **분산 락.** Redis 밖의 작업(DB 저장 등)까지 묶어 보호해야 할 때 쓴다. 기다림이 생기고 락 만료·장애를 챙겨야 한다.

`synchronized`는 **자기 JVM 안에서만** 락이 걸린다. 서버가 한 대면 쓸 수 있지만, 여러 대면 다른 서버의 요청을 막지 못한다. 그래서 모든 서버가 같이 보는 곳(Redis)에 락을 두는 게 분산 락이다.

### 4. 스레드 하나로 여러 연결을 받는 방법: epoll과 이벤트 루프

#### Spring과 Redis는 TCP 소켓으로 연결된다

Redis는 JVM과 상관없는 **별도 프로세스**(C로 만듦)이고, 보통 다른 서버에 띄운다. Spring은 `host`, `port` 설정으로 Redis 클라이언트(Spring Boot 기본은 **Lettuce**)가 TCP 연결을 맺는다.

```text
[Spring 서버 (JVM)]                        [Redis 서버]
 Lettuce 소켓 (Spring 쪽 fd 45)  ◀── TCP ──▶  소켓 (Redis 쪽 fd 7)
```

- 양쪽이 각자 소켓을 가지며, 소켓 두 개가 짝을 이룬 게 TCP 연결 하나다.
- **fd(파일 디스크립터)**는 프로세스마다 OS가 관리하는 "열린 파일 장부"의 줄 번호다. 네트워크 연결도 fd로 다룬다. `read(fd)`, `write(fd)`처럼 번호로 OS에 부탁한다.
- 연결은 **한 번 맺고 계속 재사용**한다. 3-way handshake로 맺고 4-way handshake로 끊는 비용이 명령 처리보다 훨씬 크기 때문이다.
- Lettuce 기본 설정이면 Spring 서버 한 대당 연결이 대체로 하나이고, 여러 스레드가 같이 쓴다. Redis 입장에서는 붙은 서버·서비스 수만큼 연결이 생긴다.
- 넓게 보면 프로세스 간 통신(IPC)이지만, 보통은 다른 서버에 있으므로 "TCP로 통신하는 클라이언트-서버 구조"라고 부른다.

#### 문제: 어느 연결에서 명령이 올지 모른다

- `read(fd 7)`로 기다리면 fd 7에 올 때까지 멈춰서, fd 8에 명령이 와도 못 받는다.
- 7 → 8 → 9를 계속 돌며 확인(폴링)하면 명령이 없어도 CPU를 낭비한다.

#### 해결: I/O 멀티플렉싱, 그리고 OS의 epoll

- **I/O 멀티플렉싱:** 여러 연결의 I/O를 스레드 하나로 다루는 **방법(개념)**이다.
- **`epoll`:** 리눅스에서 그걸 하게 해주는 **OS(커널)의 기능**이다. Redis의 기능이 아니라 Redis가 불러다 쓰는 것이다. macOS에는 `kqueue`, 옛날 방식으로는 `select`/`poll`이 있다.

OS는 원래 `read(fd)`로 **fd 하나**만 기다려줄 수 있다. `epoll`은 **여러 fd를 한꺼번에** 기다리게 해준다.

```text
연결될 때 (한 번):   epoll_ctl()  → "fd 7 지켜봐줘" (OS 안의 감시 목록에 등록)
명령 올 때 (반복):   epoll_wait() → 💤 "등록한 것 중 아무 데나 오면 깨워줘"
```

Redis는 실제 작업(읽기, 실행, 응답)을 직접 하고, **어느 연결에 명령이 왔는지 지켜보는 일만** OS에 맡긴다. 지켜보는 단위는 Spring의 스레드가 아니라 **연결(fd)**이다. Redis는 연결 너머에 스레드가 몇 개인지 모른다.

#### 데이터가 도착하면 일어나는 일

```text
① 네트워크 카드가 패킷을 받음
② 네트워크 카드가 CPU에 인터럽트 → OS가 처리 시작
③ OS: "fd 8 소켓 데이터네" → fd 8의 수신 버퍼에 넣음
④ OS: fd 8은 epoll 감시 목록에 있음 → 준비됨 목록에 추가
⑤ OS: 이 epoll에서 잠든 스레드는? → Redis 메인 스레드를 깨움
⑥ epoll_wait()가 [fd 8]을 돌려줌
⑦ Redis: fd 번호를 인덱스로 연결 정보를 바로 꺼냄 → read(8) → 실행 → write(8)
⑧ 다시 epoll_wait() → 💤
```

- 명령이 없는 동안 Redis 스레드는 `epoll_wait()`에서 **잠들어 있고**, 잠든 스레드에게 OS는 CPU를 주지 않는다. 그래서 연결이 1,000개여도 명령이 없으면 **CPU가 거의 0%**다.
- OS도 계속 확인하지 않는다. 데이터 도착은 **하드웨어 인터럽트**로 알게 된다.
- 깨어난 뒤 `read()`는 데이터가 이미 수신 버퍼에 있으니 블로킹되지 않는다.
- Redis는 준비된 fd 목록을 받고, 연결 정보를 fd 번호 인덱스 배열에서 바로 꺼낸다. 검색이나 순회가 없다.

이 ①~⑧을 계속 도는 구조가 **이벤트 루프**다.

```text
while (true) {
    준비된_fd들 = epoll_wait();
    for (fd : 준비된_fd들) { read → 실행 → write; }
}
```

#### Tomcat과 비교

| | 기다리기 | 처리하기 |
|---|---|---|
| 옛날 Tomcat (BIO) | 연결마다 스레드가 자기 연결의 `read()`에서 대기 | 같은 스레드 |
| 지금 Tomcat (NIO, Spring Boot 기본) | Poller 스레드가 `epoll`로 전체 연결 감시 | 워커 스레드 풀(기본 최대 200)이 요청을 받아 처리 |
| Redis | 메인 스레드가 `epoll`로 전체 연결 감시 | **같은 메인 스레드**가 처리 |

- BIO는 아무 일도 안 하는 연결에도 스레드가 하나씩 묶였다. NIO는 스레드가 연결이 아니라 **실제로 온 요청**에만 붙는다.
- 로그의 `http-nio-8080-exec-7`에서 번호가 매번 바뀌는 건, 그때 작업 큐에서 먼저 일감을 가져간 쉬는 워커가 처리하기 때문이다.
- Spring 요청은 DB·외부 API 때문에 수십~수백 ms 블로킹되므로 워커가 여러 개 필요하다. Redis 명령은 µs라 처리까지 스레드 하나로 충분하다.

### 5. 진짜 병목은 네트워크다: RTT와 파이프라이닝

Redis 처리는 수 µs인데, 요청을 보내고 응답이 돌아오는 **RTT(Round Trip Time)**는 그보다 훨씬 길다. Spring이 느끼는 시간의 대부분은 네트워크 왕복이다.

| Spring과 Redis의 위치 | RTT (대략) |
|---|---|
| 같은 AZ | 0.1~0.5ms |
| 같은 리전, 다른 AZ | 약 1ms |
| 다른 리전 | 수십~수백 ms |

- **리전** 안에 여러 **AZ(가용 영역)**가 있고, AZ는 물리적으로 떨어진 데이터센터 묶음이다.
- Redis는 RDS가 아니라 **Spring 서버 옆(같은 AZ)**에 둔다. Redis와 RDS는 서로 직접 통신하지 않고, Spring ↔ Redis가 훨씬 자주 오가기 때문이다. AZ 간 통신은 요금도 든다.

#### 왕복 횟수가 핵심이다

한 스레드 안에서 Redis 명령은 기본적으로 **보내고 → 응답 받고 → 다음을 보낸다.** 앞 결과를 보고 다음 행동을 정하는 코드가 많아서다. 그래서 for문으로 1만 번 보내면 RTT 1ms × 1만 = **10초**다. Redis를 같은 AZ로 옮겨도 0.2ms × 1만 = 2초다. 문제는 거리보다 **왕복 횟수**다.

**파이프라이닝**은 응답을 기다리지 않고 명령을 연달아 보내고, 응답을 한꺼번에 받아 왕복 횟수를 줄인다.

```java
// 1,000개씩 나눠서 파이프라이닝: 1만 번 왕복 → 10번 왕복
for (List<ProductView> chunk : Lists.partition(views, 1000)) {
    redisTemplate.executePipelined((RedisCallback<Object>) conn -> {
        for (ProductView v : chunk) {
            conn.stringCommands().incrBy(("view:" + v.getProductId()).getBytes(), v.getCount());
        }
        return null;
    });
}
```

- 같은 종류의 읽기 여러 개는 `multiGet`(`MGET`) 명령 하나로도 된다.
- 너무 크게 묶으면 Redis가 응답을 메모리에 쌓아야 하므로 수백~수천 개씩 나눈다.

#### 파이프라이닝은 언제 쓰나

기본값이 아니라 **개발자가 판단해서** 쓴다.

1. 한 작업 안에서 Redis 명령을 **여러 번** 보내는가?
2. 앞 명령의 결과를 보고 다음 명령을 정해야 하는가? 그렇다면 쓸 수 없다.

사용자가 많은 API(트래픽)와는 상관없다. 요청 하나에 `GET` 1번이면 묶을 게 없다. 파이프라이닝은 **여러 사용자의 요청을 모으는 게 아니라, 한 작업 안의 명령을 묶는 것**이다.

#### 파이프라이닝은 원자적이지 않다

파이프라이닝은 **보내는 방법**만 바꾼다. 내 명령들은 보낸 순서대로 처리되지만, **그 사이에 다른 연결의 명령이 끼어들 수 있다.**

```text
내가 보낸 순서:  1 → 2 → 3
Redis 처리:     [1] [2] [다른 서버의 GET] [3]
```

| | 목적 | 끼어들 수 있나? |
|---|---|---|
| 파이프라이닝 | 속도 (RTT 줄이기) | 있음 |
| Lua 스크립트 | 원자성 (끼어듦 막기) | 없음 |

"재고 확인하고 차감"은 확인 결과를 보고 차감해야 하므로 파이프라이닝으로는 만들 수조차 없다. Lua 스크립트로 한다.

## 헷갈렸던 점

| 처음의 생각 | 정리한 내용 |
| --- | --- |
| Redis가 빠른 건 메모리에 저장하기 때문이다 | 절반만 맞다. MySQL도 버퍼 풀로 메모리에서 읽는다. 진짜 차이는 쿼리 해석·실행 계획·트랜잭션·인덱스 탐색 없이 해시 테이블에서 키로 바로 찾는다는 것이다. |
| "1초를 RAM 한 번 읽는 시간"이 무슨 뜻인지 | 비율을 그대로 두고 시간을 늘린 비유다. RAM 1초면 SSD 17분, HDD 하루 남짓이다. |
| 1ms = 0.0001µs | 반대다. 1ms = 1,000µs다. µs가 더 작은 단위다. |
| 싱글 스레드로 한 줄로 처리하니 동시성 문제가 없다 | 명령 하나 안에서는 없다. 하지만 줄은 "내 로직"이 아니라 "명령" 단위로 서서, GET과 SET 사이에 다른 명령이 끼어든다. |
| Spring 트랜잭션 하나 안의 작업은 동시성이 지켜진다 | `@Transactional`은 DB 트랜잭션이라 Redis 명령을 묶지 않는다. Redis가 지켜주는 단위는 명령 하나뿐이다. |
| "락이 필요 없다"는 애플리케이션도 락이 필요 없다는 뜻이다 | Redis 서버 내부 자료구조 이야기다. 애플리케이션 로직은 경우에 따라 락이 필요하다. |
| 두 스레드가 동시에 INCR하면 2번 올라가서 문제다 | 요청 2개면 2 오르는 게 정답이다. 문제는 GET → SET으로 구현해 2개 요청에 1만 오르는 경우다. |
| 서버 여러 대에서 `synchronized`로 막는다 | `synchronized`는 자기 JVM 안에서만 걸린다. 여러 대면 분산 락이 필요하고, 그보다 먼저 명령 하나(INCR/DECR)로 바꿀 수 있는지 본다. |
| INCR이 100에 걸리면 알아서 멈춘다 | Redis는 계속 올린다. 돌려받은 값을 보고 멈추는 건 내 코드다. |
| Spring과 Redis의 통신은 IPC다 | 넓게는 맞지만, 보통 다른 서버에 있으므로 TCP 클라이언트-서버 통신이라 부른다. |
| Redis도 HTTP처럼 요청마다 연결하고 끊는다 | 한 번 맺고 계속 재사용한다. 요즘 HTTP도 Keep-Alive로 재사용한다. |
| Tomcat은 연결마다 스레드가 붙어 기다린다 | 옛날 BIO 방식이다. 지금 NIO는 Poller가 epoll로 감시하고, 워커는 작업 큐의 일감을 기다린다. |
| epoll은 어떤 Spring 스레드가 요청을 보냈는지 계속 확인한다 | 지켜보는 단위는 스레드가 아니라 연결(fd)이고, 계속 확인하지 않는다. Redis는 잠들어 있고 OS가 깨운다. |
| OS가 깨워준다면 epoll은 왜 있나 | epoll이 바로 "여러 fd 중 아무 데나 오면 깨워줘"를 하는 OS 기능이다. `read()`는 fd 하나만 기다린다. |
| epoll은 Redis의 기능이다 | OS(커널)의 기능이고 Redis는 불러다 쓴다. Nginx, Tomcat NIO, Netty도 쓴다. |
| fd는 데이터를 찾아오는 것이다 | fd는 열린 파일 장부의 줄 번호일 뿐이다. 데이터는 `read(fd)`를 받은 OS가 가져온다. |
| Redis가 먼 곳에 있어서 배치가 느리다 | 거리보다 왕복 횟수가 핵심이다. 1만 번 × RTT. 같은 AZ여도 2초다. |
| 파이프라이닝이 기본으로 된다 | 기본은 한 스레드 안에서 하나씩 보내고 기다린다. 개발자가 판단해서 쓴다. |
| 파이프라이닝은 여러 사용자의 요청을 모아 묶는다 | 한 작업 안의 명령을 개발자가 묶는 것이다. 다른 사용자 요청을 기다리지 않는다. |
| 파이프라이닝으로 묶으면 원자적이다 / 순서가 보장되지 않는다 | 원자적이지 않다. 내 명령끼리의 순서는 지켜지지만, 사이에 다른 연결의 명령이 끼어든다. |

### 확인 문제와 내 답

**1차 (5문제)**

| 문제 | 내 답의 요지 | 결과 |
|---|---|---|
| MySQL보다 빠른 이유 | MySQL도 버퍼 풀이 있지만 쿼리·실행 계획·트랜잭션·인덱스를 거치고, Redis는 해시로 바로 찾는다 | 통과 |
| 싱글 스레드로 충분한 이유 | µs 단위라 충분하고, 동시성이 발생하지 않는다 | 부분 통과. "내부 락이 필요 없고 명령 하나는 원자적"이 정확하다 |
| 재고 코드 동시성 (서버 여러 대) | 요청이 끼어들어 문제가 된다. `synchronized`나 분산 락으로 고친다 | 다시. 서버 여러 대를 못 봐서 `synchronized`를 답했고, `DECR`을 놓쳤다 |
| epoll과 이벤트 루프 | epoll이 어떤 스레드가 보냈는지 계속 확인하고 전달한다 | 다시. 단위는 연결(fd)이고, Redis는 잠들어 있다가 OS가 깨운다 |
| 상품 200개 조회가 느린 이유 | 네트워크 때문이고 한 번에 보내면 된다 | 통과 |

**2차 (개념 혼합 5문제)**

| 문제 | 내 답의 요지 | 결과 |
|---|---|---|
| 로컬 `ConcurrentHashMap` vs Redis (서버 3대) | 더 빠를 수 있지만 서버에 종속적이고 원자성을 고려해야 한다 | 부분 통과. 핵심은 서버마다 데이터가 따로 생겨 어긋난다는 것 |
| 선착순 쿠폰 103장 | GET과 INCR 사이에 끼어들어 같은 숫자를 읽는다. 분산 락으로 막는다 | 통과. 더 간단한 답은 INCR 결과로 판단하기 |
| 연결 1,000개인데 CPU 0% | epoll에 맡기고 OS가 알려주면 작업한다 | 부분 통과. "epoll_wait에서 잠들어 있어 CPU를 안 쓴다"가 빠졌다 |
| `KEYS *` 2초 장애 | 싱글 스레드라 뒤의 명령이 줄 서서 막힌다 | 통과 |
| 배치 1만 건 10초 + 파이프라이닝 원자성 | 다른 AZ라 느리니 같은 AZ에 둔다 / 원자성은 모르겠다 | 다시. 핵심은 왕복 횟수이고, 파이프라이닝은 원자적이지 않다 |

**재시험 (파이프라이닝)**

장바구니 50개 × 가격·재고 조회는 100번 왕복에 약 20ms이고 파이프라이닝으로 줄인다. 재고 확인·차감을 파이프라이닝으로 묶어도 사이에 끼어든다. → 통과. `multiGet`도 쓸 수 있고, 확인·차감은 Lua로 해야 한다는 점을 보충했다.
