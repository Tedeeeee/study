# 모니터링과 관측성은 뭐가 다를까?

[목차](README.md) · [다음: Metric·Log·Trace는 각각 어떤 질문에 답할까?](signals-and-cardinality.md)

## 다루는 범위

모니터링이 무엇을 해주고 어디까지 답하는지, 관측성(Observability)은 그 뒤에서 무엇을 쉽게 만드는지 비교한다. 이어서 MSA가 되면서 "미리 정하지 못한 질문"이 왜 늘었는지, 요청 하나를 서비스 경계 너머로 따라가려면 무엇이 필요한지 정리한다.

Trace와 Span의 구조, `traceparent` 헤더의 생김새는 3번 주제에서 다룬다.

## 시작한 질문

세미나를 들으며 모니터링과 관측성을 같이 배웠는데, 둘이 그게 그거 아닌가? 이미 대시보드에 메트릭을 잔뜩 넣어 두었는데, 관측성은 거기서 무엇이 더 필요하다는 걸까?

## 내가 이해한 내용

### 1. 모니터링은 미리 정한 질문에 답한다

모니터링은 서비스가 제대로 돌아가는지 계속 지켜보다가, **사람이 미리 정해 둔 기준**을 넘으면 알려주는 것이다. 목적은 고객보다 먼저 문제를 알아채는 것이다.

```text
숫자를 모은다 → 그래프로 본다 → 미리 정한 기준을 넘으면 알림 (예: 에러율 1% 초과 → 슬랙)
```

이때 자주 보는 숫자는 다음과 같다.

| 용어 | 뜻 | 예시 |
| --- | --- | --- |
| 요청(Request) | 서버에 들어온 "이거 해줘" 한 건 | 주문 버튼 클릭 1번 |
| 응답 시간(Latency) | 요청을 받고 결과를 돌려주기까지 걸린 시간 | 0.3초 |
| 에러율(Error rate) | 전체 요청 중 실패한 비율 | 100건 중 2건 → 2% |
| 처리량(Throughput) | 일정 시간에 처리한 요청 수 | 1초에 50건 |

모니터링은 "CPU가 80%를 넘었나?", "에러율이 1%를 넘었나?"처럼 **무엇을 볼지 이미 아는 질문(known-unknown)**에 빠르게 답한다. 즉 **"무엇이 깨졌나"**를 알려준다.

### 2. 평균보다 p99를 보는 이유

p99(99번째 백분위수)는 요청 100개의 응답 시간을 빠른 순으로 세웠을 때 99번째 값이다. "100명 중 99명은 이 시간 안에 응답받았다"는 뜻이고, 거꾸로 보면 **가장 느린 1%가 얼마나 느린지**를 보여준다.

| 지표 | 값 | 의미 |
| --- | --- | --- |
| 평균 | 0.2초 | 대부분 빠르면 평균도 좋게 나온다 |
| p99 | 3초 | 100명 중 1명은 3초를 기다렸다 |

평균만 보면 느린 1% 고객의 불만이 묻힌다. 그래서 지연 시간은 백분위로 본다.

### 3. 관측성은 예상하지 못한 "왜"에 답하게 한다

"결제 API의 p99가 오후 3시부터 올라갔다"는 알림이 왔다고 하자. 모니터링은 **"p99가 임계치를 넘었다"**까지 답한다. 진짜 궁금한 것은 그다음이다.

- 어느 하위 서비스에서 시간이 늘었나?
- 특정 사용자군이나 특정 결제 수단만 그런가?
- 느린 요청들의 공통점은 무엇인가?
- 그 시각에 배포나 설정 변경이 있었나?

이 질문들은 사고가 난 뒤에야 떠오르기 때문에 대시보드를 미리 만들어 둘 수 없다. 관측성은 이런 **미리 정하지 못한 질문(unknown-unknown)**에도, **이미 남겨 둔 데이터를 사고 당시에 원하는 기준으로 잘라 보며** 답할 수 있게 하는 성질이다.

관측성이라는 말은 제어이론에서 왔다. 원래 뜻은 "바깥 출력만 보고 내부 상태를 얼마나 추론할 수 있는가"다. 소프트웨어에서는 **코드를 다시 배포하지 않고 이미 남긴 데이터만으로 새 질문에 답할 수 있는가**라는 뜻이 된다.

| | 모니터링 | 관측성 |
| --- | --- | --- |
| 질문 | 미리 아는 질문 (known-unknown) | 미리 정하지 못한 질문 (unknown-unknown) |
| 답하는 것 | **무엇이** 깨졌나 | **왜** 깨졌나 |
| 방법 | 볼 값과 임계치를 사전에 정한다 | 남겨 둔 데이터를 원하는 축으로 잘라 본다 |
| 역할 | 사람이 지켜보지 않아도 문제 발생을 **알려준다** | 알림 뒤에 개발자가 **원인을 쉽고 빠르게 찾게** 한다 |

모니터링은 관측성의 일부다. 모니터링이 "뭔가 이상해!"라고 울리면, 관측성이 "왜?"를 파고들게 해준다.

### 4. MSA가 되면서 "모르는 질문"이 늘었다

모놀리식에서는 요청 하나가 프로세스 하나 안에서 처리된다. 느리면 그 서버의 로그, Stack Trace, Profiler로 흐름을 한 번에 볼 수 있었다.

MSA에서는 요청 하나가 여러 서버를 거친다.

```text
사용자 → gateway-service → order-service → inventory-service
```

각 서버는 들어온 요청을 **별개의 새 요청**으로 받아 자기 로그만 남긴다. 그래서 새로운 질문이 생긴다.

| 새로 생긴 질문 | 예시 |
| --- | --- |
| 호출 경로 | 이 요청이 서비스 몇 개를 거쳤나? |
| 구간별 시간 | 전체 3초 중 어느 구간이 가장 오래 걸렸나? |
| 연결 고리 | gateway 로그와 order 로그가 같은 요청인가? |

세 질문 모두 **요청 하나를 서비스 경계 너머로 따라갈 수 있어야** 답할 수 있다.

### 5. 추적 정보는 왜 서버를 넘으면 끊길까

`@Transactional`의 DB 연결이 현재 스레드(ThreadLocal)에 붙어 있듯, 요청을 추적하는 정보(trace_id 같은 trace context)도 **현재 실행 흐름(스레드)**에 붙어 있다. Spring MVC처럼 요청 하나를 스레드 하나가 처리하는 구조에서는 ThreadLocal에 두면 코드 어디서든 꺼내 쓸 수 있다. OpenTelemetry Java의 `Context`도 기본 저장소로 ThreadLocal을 쓴다.

```text
[order-service]                              [inventory-service]
 현재 스레드에 trace_id 보관   ──HTTP 호출──▶   새 스레드: 이어받은 trace_id 없음 → 새 trace 시작
```

다른 서버와는 메모리를 공유하지 않는다. 그래서 트랜잭션처럼 추적 정보도 자동으로 넘어가지 않는다. 다른 점은 다시 이을 수 있느냐다.

| | 트랜잭션 | 추적 정보 |
| --- | --- | --- |
| 서버를 넘으면 | 끊긴다 | 끊긴다 |
| 다시 잇기 | 어렵다. DB 연결 자체를 넘길 수 없어 Saga 같은 별도 설계가 필요하다 | 쉽다. ID 문자열을 HTTP 헤더(`traceparent`)에 실어 보내면 된다 |

보내는 쪽은 헤더에 trace_id를 싣고, 받는 쪽은 헤더에서 꺼내 자기 컨텍스트에 넣어 이어서 기록한다. 이것을 **컨텍스트 전파(Context Propagation)**라고 한다.

같은 서버 안에서도 `@Async`, `CompletableFuture`, 스레드 풀, WebFlux처럼 **스레드가 바뀌면** ThreadLocal이 비어 trace가 끊긴다. 이때도 컨텍스트를 직접 옮겨 담아야 한다.

## 헷갈렸던 점

- **"메트릭은 눈에 보이는 문제를 알리고, 요청 하나하나의 문제는 직접 눌러봐야 한다"고 처음 이해했다.**
  - 메트릭이 여러 요청을 합친 숫자라서 개별 요청의 사정은 사라진다는 점은 맞았다.
  - 다만 관측성은 문제를 다시 재현해 보는 것이 아니다. 요청이 처리될 때 **이미 남겨 둔** trace와 log를 여는 것이다. 다시 안 일어나는 문제도 볼 수 있어야 한다.
  - 요청 하나를 보는 데서 끝나지 않는다. "느린 요청이 전부 카드 결제네?"처럼 사고 당시 떠오른 기준으로 **잘라 보는 것**까지 포함한다.
- **직접 만든 law 프로젝트 모니터링이 떠올랐다.**
  - 개요에 메트릭 수치가 여러 개 있고, 맨 위 요청 영역은 로그 목록이다.
  - 어떤 사용자에게 어떤 문제가 있는지는 개발자가 계속 보고 있어야 알 수 있다.
  - 이것이 모니터링만 있고 관측성의 재료가 부족한 상태다. 재료는 요청을 잇는 ID와 잘라 볼 수 있는 속성이다.
- **"관측성은 사람이 보지 않아도 알 수 있게 하는 것"인지 헷갈렸다.**
  - 사람이 지켜보지 않아도 문제 발생을 알려주는 것은 **모니터링의 알림**이다.
  - 관측성은 개발자가 볼 때 **원인까지 빨리 가게** 만드는 것이다.
  - 그래서 처음 정리는 "모니터링은 수치를 스스로 감지해 알려주고, 관측성은 문제를 개발자가 알기 쉽게 한다"였다. 여기에 두 가지를 고쳤다. 모니터링의 감지는 **사람이 미리 정한 기준**에 따른 것이고, 관측성이 쉽게 해주는 것은 **예상 못 한 경우까지 포함한 원인 찾기**다.
- **"MSA에서는 트랜잭션도 로그도 끊긴다"는 말은 비유였다.**
  - 관측성이 트랜잭션을 이어 준다는 뜻이 아니었다.
  - 트랜잭션이 서버 호출을 따라가지 못하는 것처럼 로그 흐름도 끊긴다는 뜻이었다.
  - 실제로 둘 다 현재 스레드에 붙어 있어서 끊기는 원리가 같다.
- **trace_id를 ThreadLocal에 넣는 게 일반적인지 궁금했다.**
  - 요청 하나를 스레드 하나가 처리하는 구조라서 그렇다.
  - 비동기처럼 스레드가 바뀌는 경우는 예외라는 것도 확인했다.

### 확인 문제

**문제 1.** "주문 API 에러율이 1%를 넘으면 슬랙 알림"이 울렸다. (1) 이 알림은 모니터링과 관측성 중 무엇이 한 일인가? (2) 알림 뒤 원인을 찾을 때 관측성이 있으면 무엇이 달라지나?

- 내 답:
  1. 모니터링. 에러율 1%라는 수치를 보고 있다가 알려주면 되니까.
  2. 관측성이 없으면 1%를 넘었다는 사실만 알고 왜 그런지 알 수 없다. 관측성이 있어야 어떤 에러가, 누가, 왜 발생했는지 자세히 알 수 있다.
- 채점: 정답.
  - 1번은 "수치라서"보다 "**미리 정해 둔 기준**에 걸렸으니까"가 더 정확하다.
  - 2번은 보충이 필요했다. 관측성이 없어도 원인을 못 찾는 건 아니지만, 로그를 뒤지거나 재배포해야 해서 어렵고 느리다. 관측성이 있으면 이미 남긴 데이터로 바로 들어가 예상 못 한 기준으로 잘라 볼 수 있다.

**문제 2.** 모놀리식을 gateway → order → inventory로 쪼갠 뒤 "주문이 가끔 3초 걸린다"는 문의가 왔다. (1) 원인 찾기가 왜 더 어려워졌나? (2) 서비스를 넘어갈 때 무엇이 함께 넘어가야 하고, 왜 자동으로 넘어가지 않나?

- 내 답:
  1. 모놀리식은 같은 서버라 하나의 요청으로 연결해 볼 수 있다. 서버가 달라지면 완전히 다른 요청 하나가 생겨서 어려워진다.
  2. 하나의 흐름이라는 표현이 필요하다. trace_id로 하나의 요청임을 표현하는데, 서버가 달라지니까 같이 못 간다.
- 채점: 1번 정답, 2번 절반 정답.
  - 1번에는 호출 경로, 구간별 시간, 연결 고리라는 구체적인 어려움을 덧붙이면 된다.
  - 2번은 "왜"를 설명하지 못했다. 그리고 trace_id는 "못 가는" 게 아니라 "**자동으로는**" 안 가는 것이다.

**문제 2 다시.** order 로그에는 trace_id `abc123`이 찍혔는데 inventory 로그에는 다른 trace_id가 찍혔다. (1) 왜 자동으로 이어지지 않았나? (2) 어떻게 해야 이어지나?

- 내 답:
  1. trace_id는 ThreadLocal에 저장되는데, 서버가 달라지면 메모리를 공유하지 않고 사용하는 스레드도 달라서 그 정보를 쓸 수 없다.
  2. 다른 서비스를 호출할 때 trace_id를 넘겨줘야 한다.
- 채점: 정답.
  - inventory가 이어받은 ID가 없어 **새 trace를 시작**했기 때문에 다른 ID가 찍힌 것이다.
  - 넘기는 방법은 HTTP 헤더 `traceparent`이고, 받는 쪽이 꺼내 자기 컨텍스트에 넣는다(컨텍스트 전파).

## 예제와 확인 결과

이번 주제는 개념 정리라서 직접 실행한 예제는 없다. 위의 p99 수치, 쇼핑몰 서비스 흐름, trace_id `abc123`은 설명용이다.

## 남은 질문

- law 프로젝트 모니터링의 요청 영역에 trace_id나 사용자 ID가 같이 찍혀 있을까? 찍혀 있다면 연결만 안 된 것이고, 없다면 재료부터 없는 것이다.
- `traceparent` 헤더는 실제로 어떻게 생겼고, 받는 쪽은 그걸 어떻게 이어 쓸까? → 3번 주제
- `@Async`나 스레드 풀로 넘어갈 때 컨텍스트는 구체적으로 어떻게 옮겨 담을까?
