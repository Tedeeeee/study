# 도커는 왜 나왔을까?

[목차](README.md)

## 다루는 범위

"내 PC에선 되는데" 문제의 정체, 그 문제를 푸는 두 방식인 VM과 컨테이너의 구조 차이, 그리고 컨테이너 기술이 이미 있었는데 도커가 무엇을 더했는지를 정리한다.

namespace와 cgroup이 실제로 어떻게 동작하는지는 2번, 도커 엔진과 WSL2 구조는 3번, 이미지의 레이어는 4번에서 다룬다.

## 시작한 질문

VM으로도 실행 환경을 통째로 옮길 수 있는데, 왜 컨테이너와 도커가 필요했을까?

## 내가 이해한 내용

### 1. "내 PC에선 되는데"는 실행 환경의 차이다

앱은 코드(jar)만으로 돌지 않는다. 코드 바깥의 것들에 기대고 있다.

- 런타임: JDK 17인지 21인지
- OS에 깔린 것: 시스템 라이브러리, 타임존 데이터, 인증서
- 설정: 환경 변수, 설정 파일 위치, 파일 권한
- 같이 도는 것: 그 서버에 이미 떠 있는 다른 앱과 겹치는 포트·라이브러리 버전

이 묶음이 **실행 환경**이다. 내 PC와 서버는 실행 환경이 조금씩 달라서, 같은 코드인데 결과가 달라진다.

도커 이전에는 이 차이를 사람이 맞췄다. 설치 문서를 보고 서버에 JDK를 깔고 환경 변수를 넣었다. 문서가 낡거나 누가 서버를 손으로 바꾸면 서버마다 환경이 달라졌다.

> 배포가 어려운 건 코드를 옮기는 게 어려워서가 아니라, **실행 환경을 똑같이 다시 만드는 게 어려워서**다.

### 2. VM: OS까지 통째로 싸 간다

VM은 컴퓨터 한 대를 소프트웨어로 흉내 낸 것이다.

```text
[앱A]      [앱B]      [앱C]
[JDK·lib]  [JDK·lib]  [JDK·lib]
[게스트OS] [게스트OS] [게스트OS]   ← VM마다 OS(커널 포함)가 하나씩
──────────────────────────────
[ 하이퍼바이저 ]                  ← 물리 서버 한 대에 하나
[ 하드웨어 ]
```

- 하이퍼바이저가 가짜 하드웨어(CPU, 메모리, 디스크)를 만들어 각 VM에 나눠 준다. 게스트 OS는 자기가 컴퓨터 한 대를 혼자 쓰는 줄 안다.
- 이 전체를 VM 이미지로 떠서 옮기면 OS부터 앱까지 똑같은 환경이 살아난다. 격리도 확실하다.
- OS는 "앱 하나당"이 아니라 **"VM 하나당"** 하나다. VM 하나에 앱을 여러 개 넣을 수도 있지만, 그러면 그 앱들이 실행 환경을 공유해서 1절의 문제가 VM 안에서 다시 생긴다. 그래서 앱 하나에 VM 하나를 주게 되고, 결과적으로 앱 수만큼 OS가 늘어난다.

비용은 **앱 하나를 옮기려고 OS 하나를 통째로 같이 옮기는 것**에서 나온다. 앱이 무거워진 게 아니라, 앱에 딸려 오는 것이 무겁다.

| 비용 | 이유 |
| --- | --- |
| 용량이 크다 (보통 GB 단위) | 이미지에 OS 전체가 들어 있다 |
| 뜨는 데 오래 걸린다 | 게스트 OS가 부팅부터 해야 한다 |
| 메모리를 많이 먹는다 | VM마다 커널과 OS 프로세스가 따로 뜬다 |

### 3. 컨테이너: 커널은 같이 쓰고, 그 위의 파일만 싸 간다

OS는 둘로 나눌 수 있다.

- **커널**: 하드웨어를 직접 다루는 핵심부. CPU 시간, 메모리, 파일, 네트워크를 관리한다.
- **그 외**: 커널 위에 깔린 파일들. 셸, 시스템 라이브러리, 패키지, 설정 파일.

실행 환경의 차이는 대부분 커널이 아니라 그 위의 파일 쪽에서 생긴다. 그래서 컨테이너는 커널은 호스트 것을 같이 쓰고, 그 위의 파일들(라이브러리, JDK, 설정, 앱)만 따로 가진다.

```text
[앱A]        [앱B]
[JDK·lib]    [JDK·lib]     ← 컨테이너마다 따로 가진다
─────────────────────
[ 호스트 OS의 커널 ]        ← 하나를 같이 쓴다
[ 하드웨어 ]
```

게스트 OS와 하이퍼바이저 층이 없다. 하이퍼바이저는 게스트 OS를 속이려고 가짜 하드웨어를 만드는 것인데, 컨테이너에는 속일 게스트 OS가 없기 때문이다.

하이퍼바이저가 하던 "서로 가르고 자원을 나눠 주는 일"은 **호스트 커널이 직접** 한다.

| | 하는 일 | 한 줄로 |
| --- | --- | --- |
| namespace | 프로세스가 볼 수 있는 범위를 나눈다 (프로세스 목록, 네트워크, 파일 시스템, 호스트 이름) | 뭐가 보이는가 |
| cgroup | 프로세스가 쓸 수 있는 양을 제한한다 (CPU, 메모리) | 얼마나 쓰는가 |

둘은 다른 일이라 둘 다 있어야 한다. namespace만 있으면 옆 컨테이너가 안 보일 뿐, 한 컨테이너가 메모리를 다 먹는 건 못 막는다.

**컨테이너는 커널 안에 따로 있는 물건이 아니다.** namespace와 cgroup이 걸린 평범한 프로세스를 컨테이너라고 부른다.

| | VM | 컨테이너 | 이유 |
| --- | --- | --- | --- |
| 용량 | GB 단위 | MB 단위가 흔하다 | 커널이 안 들어 있다 |
| 시작 | 부팅이 필요하다 | 프로세스 하나를 띄울 뿐이다 | 부팅이 없다 |
| 메모리 | VM마다 커널이 따로 | 커널 하나를 공유한다 | 앱이 쓰는 만큼만 든다 |
| 격리 | 강하다 (가짜 하드웨어 수준) | **약하다** | 같은 커널 위에 있다 |

### 4. 격리가 약한 건 언제 문제일까

| 상황 | 문제인가 |
| --- | --- |
| 우리 팀 앱 여러 개를 한 서버에서 돌린다 | 거의 문제없다. 다 믿을 수 있는 코드다 |
| 모르는 남의 코드를 같은 서버에서 돌린다 | 문제다. 커널 취약점을 뚫으면 옆 컨테이너와 호스트까지 닿을 수 있다 |

그래서 VM과 컨테이너는 경쟁 관계가 아니라 같이 쓴다. 서로 못 믿는 사이의 경계는 VM으로 긋고, 그 안에서 앱들은 컨테이너로 나눈다. EC2(VM) 위에서 도커를 돌리는 구조가 이 조합이다.

### 5. "호스트 커널"은 컨테이너를 직접 돌리는 OS의 커널이다

호스트가 꼭 본체 컴퓨터의 OS인 것은 아니다.

| 환경 | 컨테이너가 쓰는 커널 |
| --- | --- |
| 리눅스 서버에 도커를 바로 설치 | 그 서버의 리눅스 커널 |
| Windows 11 + Docker Desktop | WSL2 VM 안의 리눅스 커널 (Windows 커널이 아니다) |
| AWS EC2 위의 도커 | EC2 인스턴스(VM)의 리눅스 커널 |

컨테이너 안의 프로그램은 리눅스용이라 리눅스 커널에게 리눅스 방식으로 요청한다. namespace와 cgroup도 리눅스 커널의 기능이다. 그래서 Windows에서는 한 층이 더 낀다.

```text
[컨테이너A] [컨테이너B]
[ 리눅스 커널 ]         ← 컨테이너 입장에서의 호스트 커널
[ WSL2 VM ]
[ 하이퍼바이저 ]        ← Windows에 원래 있는 기능을 켠다
[ Windows / 하드웨어 ]
```

- Docker Desktop을 설치할 때 WSL이 필요한 이유가 이것이다.
- Windows에서 치는 `docker` 명령은 리모컨 역할이고, 컨테이너를 만들고 돌리는 엔진은 VM 안의 리눅스에 있다.
- VM의 비용을 한 번은 치르지만, VM은 하나뿐이고 그 위의 컨테이너들은 커널 하나를 나눠 쓴다.

### 6. 도커는 컨테이너를 발명하지 않았다

"커널 하나 위에서 칸을 쳐서 나눈다"는 생각과 그 재료는 도커(2013)보다 먼저 있었다. `chroot`, FreeBSD Jails, 리눅스 namespace와 cgroup, 그리고 둘을 묶어 컨테이너를 만드는 LXC가 그렇다. 도커도 처음에는 LXC를 가져다 썼다. VM 쪽도 오래된 생각이라, VM을 개선해서 컨테이너가 나온 게 아니라 두 갈래가 나란히 있었다.

LXC는 칸은 쳐 줬지만, **그 칸 안에 실행 환경을 채우는 일과 다른 서버로 옮기는 일은 여전히 사람 몫**이었다. 1절의 문제는 격리가 아니라 "실행 환경을 똑같이 다시 만드는 것"이었는데, 그게 안 풀린 채였다.

### 7. 도커가 더한 것: build, ship, run

| 도커가 더한 것 | 무엇 | 풀어 준 문제 |
| --- | --- | --- |
| 이미지 | 실행 환경을 굳혀 놓은 묶음 | 환경을 그대로 옮길 수 있게 됐다 |
| Dockerfile | 이미지 안에 무엇을 채울지 적은 텍스트 파일 | 설치 문서 대신 실행되는 문서가 생겼다. 누가 빌드해도 같은 결과다 |
| 레지스트리 (Docker Hub) | 이미지를 올리고 받는 중앙 저장소 | `push`, `pull`로 서버 간에 전달한다 |
| 쉬운 명령 | `docker run` 한 줄 | namespace와 cgroup을 몰라도 컨테이너를 띄운다 |

```text
이전: 코드 전달 → 서버마다 사람이 환경을 맞춤 → 실행
도커: 코드 + 환경을 이미지로 굳힘 → 이미지 전달 → 어디서든 그대로 실행
```

- 이미지에는 파일 묶음(JDK, 라이브러리, 앱)과 함께 **어떻게 실행할지**(시작 명령, 환경 변수, 포트)도 들어 있다.
- 이미지는 줄이는(압축) 게 아니라 **묶어서 굳히는** 것이다. 한 번 만든 이미지는 내용이 바뀌지 않고, 바꾸려면 Dockerfile을 고쳐 새 이미지를 만든다.
- 이미지 형식은 지금은 업계 표준(OCI)이라 도커가 아닌 도구도 같은 이미지를 쓴다.
- 레지스트리는 GitHub과 닮았다. 소스 코드 대신 이미지를 `push`·`pull` 한다. Docker Hub 말고 AWS ECR, GHCR도 있다.

환경을 매번 다시 만드는 게 아니라 한 번 만든 걸 그대로 들고 가니까, 내 PC에서 돌린 그 이미지를 서버에서도 그대로 돌린다.

> 도커는 컨테이너를 발명한 게 아니라, 컨테이너에 넣을 환경을 **만들고(build), 옮기고(ship), 돌리는(run) 방법을 표준으로 만들었다.**

## 헷갈렸던 점

| 처음 생각 | 고친 생각 |
| --- | --- |
| VM은 앱 하나당 OS가 계속 생긴다 | OS는 VM 하나당 하나다. VM 하나에 앱을 여러 개 넣을 수 있지만 환경이 섞여서, 결국 앱마다 VM을 주게 된다. 하이퍼바이저는 물리 서버에 하나다. |
| VM은 앱 하나가 굉장히 무겁다 | 앱이 무거운 게 아니라, 앱을 띄우려고 딸려 오는 OS가 무겁다. |
| 컨테이너 그림에 하이퍼바이저가 빠져 있다. 빠뜨린 건가? | 진짜로 없다. 속일 게스트 OS가 없어서 필요 없다. 가르고 나누는 일은 커널의 namespace와 cgroup이 한다. |
| 호스트 커널은 진짜 본체 컴퓨터의 커널이다 | 리눅스 서버라면 맞다. Windows에서는 WSL2 VM 안의 리눅스 커널이다. 호스트는 "컨테이너를 직접 돌리는 OS"다. |
| 하이퍼바이저가 없어지면서 컨테이너 개념이 생겼다 | VM에서 하이퍼바이저를 뺀 게 아니라 출발점이 다르다. 컨테이너는 프로세스를 그냥 띄우고 커널이 칸만 쳐 주는 방식이라 처음부터 하이퍼바이저가 필요 없다. |
| namespace·cgroup 같은 개념은 도커 때문에 생겼다 | 아니다. 리눅스 커널의 기능이고 도커보다 먼저 있었다. 도커는 가져다 쓴 쪽이다. |
| 이미지는 도커만의 압축파일이다 | 압축이 아니라 묶음이다. 파일뿐 아니라 실행 방법도 들어 있다. 형식도 지금은 OCI 표준이라 도커만의 것이 아니다. |
| Dockerfile은 압축을 시키는 명령을 적는 문서다 | 묶는 일은 도커가 한다. 사람은 안에 무엇을 채울지(레시피)만 적는다. |
| 컨테이너는 같은 메모리를 사용한다 | 공유하는 건 커널이다. 각 컨테이너의 프로세스는 자기 메모리를 따로 가지고, cgroup이 몫을 나눈다. "커널이 먹는 메모리를 한 번만 치른다"는 뜻이라면 맞다. |
| 격리가 약한 건 단점이다 | 믿을 수 있는 우리 코드끼리라면 안고 갈 만하다. 남의 코드를 돌리는 곳에서는 VM으로 경계를 긋고 그 안에서 컨테이너를 쓴다. |

### 확인 문제

**문제 1.** 동료가 "VM으로도 실행 환경을 통째로 옮길 수 있는데 왜 컨테이너를 써? 둘이 뭐가 다른데?"라고 묻는다. ① 구조적으로 무엇이 다른지 ② 그래서 컨테이너가 얻는 것 ③ 잃는 것

내 답 (첫 시도):

> 기존의 VM 은 너무 무거워 단순한 앱을 띄우기 위해서 OS 를 준비해야해서 너무 과해 그래서 단순 컨테이너를 사용하면 가볍게 사용하게 될 수 있어

채점: 얻는 것만 맞았다. 컨테이너가 **왜** 가벼운지(커널 공유)와 잃는 것(격리가 약하다)이 빠졌다. "컨테이너도 앱을 돌리려면 OS가 필요하잖아?"라고 되물으면 답이 막힌다.

내 답 (재시도):

> 1. vm 은 하나의 컴퓨터 위에 os 를 포함한 형태로 계속 올리니까 너무 무거운데 컨테이너는 따로 무엇을 올리지는 않고 실제 커널을 이용해서 같은 메모리를 사용해
> 2. 그렇기 때문에 컨테이너는 기존의 vm 보다 훨씬 가벼운 공간으로 앱을 운영하기 좋다
> 3. 대신vm 은 os 적으로도 분리되는 반면에 컨테이너는 같은 os 를 사용하게 되면서 격리성이 좀 낮아질 수 있어

채점: 통과. 고칠 곳은 "같은 메모리를 사용해"다. 공유하는 건 메모리가 아니라 커널이다. "따로 무엇을 올리지는 않고"도 과하다. OS는 안 올리지만 커널 위의 파일들은 컨테이너마다 따로 가진다. namespace와 cgroup이 답에 빠졌다.

**문제 2.** 컨테이너 기술은 도커 전부터 있었다. ① 도커 이전에 여전히 사람이 해야 했던 일 ② 도커가 더한 것들과 각각의 역할 ③ 그래서 "내 PC에선 되는데"가 어떻게 풀리는지

내 답:

> 1. os 만 격리되었을뿐 그 컨테이너 안에서 앱이 돌아가게 하기 위한 설정은 또 따로 해줘야겠지
> 2. 그래서 도커는 앱이 돌아가기 위해 필요한 것들을 묶어주는 이미지라는걸 만들었고 또 이미지를 만들기 위한 명령 파일인 dockerfile 을 통해서 이미지를 만들 수 있게 해줬어 그리고 그 이미지를 어디에서든 쓸 수 있도록 중앙 저장소를 만들어줬었지
> 3. 이게 사람들이 각 설정이 다르다보니까 문제가 됐었는데 이렇게 설정 자체를 묶어버리니까 괜찮아졌어

채점: 통과. "os만 격리되었을 뿐"은 표현이 반대다. OS(커널)는 공유하고, 격리된 건 프로세스가 보는 공간이다. 도커 이전에는 채우는 일뿐 아니라 **옮기는 일**도 사람 몫이었다는 점, 묶이는 게 "설정"만이 아니라 런타임과 라이브러리를 포함한 실행 환경 전체라는 점을 보충했다.

## 예제와 확인 결과

아래는 모두 설명용이고 실행하지 않았다.

Dockerfile이 "무엇을 채울지 적는 레시피"라는 것을 보여 주는 예다.

```dockerfile
FROM eclipse-temurin:21-jre      # JDK 21이 깔린 환경에서 시작해서
COPY app.jar /app.jar            # 내 jar를 넣고
CMD ["java", "-jar", "/app.jar"] # 이 명령으로 실행해라
```

Windows에서 컨테이너가 WSL2의 리눅스 커널을 쓰는지 확인하는 방법이다. 두 결과가 같은 커널 버전이면 커널을 공유한다는 뜻이다.

```text
wsl uname -r
docker run --rm alpine uname -r
```
