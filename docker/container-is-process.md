# 컨테이너는 그냥 프로세스일까?

[목차](README.md) · [이전: 도커는 왜 나왔을까?](why-docker.md) · [다음: 도커 엔진은 어떻게 생겼을까?](docker-engine.md)

## 다루는 범위

평범한 프로세스가 커널을 통해 세상을 보는 방식에서 출발해, namespace(보이는 범위)와 cgroup(쓰는 양)이 그 프로세스에 무엇을 더하는지, 그래서 컨테이너가 어떤 성질을 갖는지를 정리한다.

Network namespace의 자세한 동작은 10번, 메인 프로세스(PID 1)와 종료 과정은 9번, JVM과 cgroup 메모리는 15번에서 다룬다.

## 시작한 질문

컨테이너 안에서는 내 앱만 보이고 자기만의 IP와 파일도 있다. 그러면 컨테이너는 작은 컴퓨터일까, 그냥 프로세스일까?

## 내가 이해한 내용

### 1. 프로세스는 세상을 커널을 통해서만 본다

여기서 말하는 프로세스는 컨테이너가 아니라, 리눅스에서 `java -jar app.jar`처럼 그냥 실행한 평범한 프로세스다. 컨테이너와 비교할 기준이다.

프로세스는 하드웨어를 직접 못 만진다. 필요한 건 전부 커널에게 요청해서 얻는다. 이 창구가 **시스템 콜**이다.

| 프로세스가 궁금한 것 | 커널에게 묻는 것 |
| --- | --- |
| 지금 어떤 프로세스들이 떠 있지? | 프로세스 목록 |
| `/etc/hosts` 열어 줘 | 파일 시스템 |
| 내 IP는 뭐고, 8080 써도 돼? | 네트워크 |
| 이 컴퓨터 이름이 뭐야? | 호스트 이름 |

- Spring Boot가 뜰 때 톰캣이 커널에게 8080 포트를 달라고 요청한다. 누가 쓰고 있으면 커널이 거절하고 `Port 8080 was already in use`가 난다.
- 커널이 중간에 있는 이유는 **보호**(남의 메모리나 디스크를 못 건드리게)와 **조율**(같은 포트·디스크를 두고 다툴 때 정리)이다.
- 프로세스는 커널이 대답해 준 것만이 세상의 전부라고 믿는다. 직접 확인할 방법이 없다.
- 평소에는 커널이 **모든 프로세스에게 같은 대답**을 한다. 그래서 서로가 다 보이고, 같은 포트를 두고 다툰다.

커널이 유일한 창구라는 점이 컨테이너의 열쇠다. 모든 요청이 커널을 거치니, 커널이 대답을 바꾸면 프로세스가 보는 세상이 바뀐다.

### 2. 유저 영역과 커널 영역, 커널과 OS

"프로세스 쪽"과 "커널 쪽"이 유저 영역과 커널 영역이다. 네트워크에서는 이렇게 나뉜다.

```text
[유저 영역]  Spring Boot: HTTP 요청·응답을 만든다
     │  소켓 (시스템 콜)
     ▼
[커널 영역]  TCP, IP(라우팅), 드라이버
     ▼
[하드웨어]   랜카드
```

앱은 HTTP 내용만 만들고 TCP·IP 처리는 커널이 한다. Network namespace(10번)는 이 커널 영역의 네트워크 부분을 컨테이너마다 따로 갖게 하는 것이고, 포트 매핑과 NAT(12번)도 커널 영역에서 일어난다.

**커널은 OS의 일부다.** OS = 커널 + 커널 위의 것들(셸, 기본 명령어, 시스템 라이브러리, 패키지 관리자, 설정 파일).

| | 커널 | 커널 위의 것들 |
| --- | --- | --- |
| Ubuntu | 리눅스 커널 | `apt`, bash, glibc |
| CentOS | 리눅스 커널 | `yum`, bash, glibc |
| Alpine | 리눅스 커널 | `apk`, ash, musl |

`ubuntu`, `alpine` 같은 이미지에는 커널이 없고 커널 위의 것들만 들어 있다. 그래서 호스트가 Ubuntu여도 그 위에서 Alpine 컨테이너와 CentOS 컨테이너가 같이 돈다. "컨테이너는 같은 OS를 쓴다"보다 **"같은 커널을 쓴다"**가 정확하다.

### 3. namespace: 커널이 묶음마다 다른 대답을 한다

namespace는 커널이 프로세스를 묶음으로 나누고, 묶음마다 다른 대답을 하게 만드는 커널 기능이다.

```text
[호스트에서 ps]                    [컨테이너 안에서 ps]
 PID 1     systemd                  PID 1   java -jar app.jar
 PID 812   sshd                     (이것뿐)
 PID 4521  java -jar app.jar   ← 같은 프로세스
 ... (300개)
```

- **프로세스는 하나다.** 호스트의 4521번과 컨테이너 안의 1번은 같은 프로세스다. PID 번호는 PID namespace마다 따로 매긴다.
- **안에서 밖은 안 보이고, 밖에서 안은 보인다.** 호스트에서는 그 프로세스를 볼 수 있고 `kill`도 할 수 있다.
- 벽이 있어서 안 보이는 게 아니라, **커널이 그것만 대답해 줘서** 안 보인다.

namespace는 큰 상자 하나가 아니라 **주제마다 종류가 따로** 있다.

| namespace | 나누는 것 | 컨테이너 안에서 보면 |
| --- | --- | --- |
| PID | 프로세스 목록 | 내 프로세스만 보이고, 메인 앱이 1번 |
| Mount | 파일 시스템 | 나만의 `/` 디렉토리 |
| Network | IP, 포트, 라우팅 | 나만의 IP와 포트 장부 |
| UTS | 호스트 이름 | 나만의 컴퓨터 이름 |

이 밖에 IPC, User 등도 있다.

### 4. 프로세스는 namespace를 종류별로 하나씩 든다

namespace는 프로세스가 들어가 있는 장소라기보다 **프로세스에 붙은 명찰**에 가깝다. 커널의 장부를 그리면 이렇다.

| 프로세스 (호스트 번호) | PID ns | Network ns | Mount ns | UTS ns |
| --- | --- | --- | --- | --- |
| 812 sshd | 기본 | 기본 | 기본 | 기본 |
| 4521 java | A | A | A | A |
| 4530 (java의 자식) | A | A | A | A |
| 5102 postgres | B | B | B | B |

- 가로 한 줄이 프로세스 하나다. 한 프로세스가 **종류별로 딱 하나씩**, 네 칸을 전부 가진다.
- 프로세스가 물으면 커널은 ① 무슨 주제인지 보고 ② 그 프로세스의 해당 주제 명찰을 읽고 ③ 그 namespace의 정보만 대답한다.
- 호스트의 평범한 프로세스도 namespace에 안 속한 게 아니라 **기본 namespace**에 다 같이 속해 있다.
- namespace 쪽에서 보면 "나한테 이 프로세스들이 올라와 있다"는 명단이고, 그 묶음만의 정보(IP, 포트 장부, 파일 시스템)도 같이 들고 있다.
- namespace를 정하는 건 앱이 아니라 **띄우는 쪽**이다. 평범한 프로세스는 부모 것을 물려받고, 컨테이너는 도커가 새 세트를 만들어 넣는다. 앱은 자기가 어느 namespace에 있는지 모른다. 그래서 앱을 한 줄도 안 고치고 컨테이너에 넣을 수 있다.

**커널에는 "컨테이너"라는 칸이 없다.** 커널이 아는 건 프로세스, namespace, cgroup뿐이다. 위 표에서 A가 붙은 줄들을 사람과 도커가 "컨테이너 A"라고 부른다. 컨테이너라는 단위(이름, ID, 이미지, 상태)를 아는 건 도커다.

> 컨테이너 하나 = namespace 한 세트

종류별로 나뉘어 있어서 골라서 나눌 수 있다. `docker run --network host`는 네트워크만 호스트 것을 쓰고, Kubernetes의 Pod는 컨테이너들이 Network namespace를 같이 써서 `localhost`로 통신한다.

한 namespace에 프로세스가 여러 개 들어갈 수 있다. 자식 프로세스는 부모와 같은 namespace에 생기고, `docker exec`는 새 프로세스에 그 컨테이너와 같은 명찰을 붙여 주는 것이다. 같은 namespace 안에서는 같은 대답을 받으므로 서로 보이고 포트도 다툰다.

### 5. cgroup: 묶음이 쓸 수 있는 자원에 상한을 건다

namespace는 보이는 범위만 나누고 쓰는 양은 건드리지 않는다. 서로 안 보여도 같은 서버의 메모리를 나눠 쓰기 때문에, 한 컨테이너가 메모리를 다 먹으면 옆 컨테이너가 피해를 본다. cgroup은 프로세스 묶음이 쓸 수 있는 자원에 상한을 건다.

```text
docker run --memory 512m --cpus 1.5 my-app
```

| 자원 | 상한을 넘으려 하면 | 결과 |
| --- | --- | --- |
| CPU | 커널이 그 이상은 안 준다 | 느려진다. 죽지는 않는다 |
| 메모리 | 줄 수 있는 게 없다 | 커널이 그 묶음의 프로세스를 죽인다 (OOM Kill) |

- 도커는 컨테이너마다 cgroup을 하나 만들고, 상한을 적고, 컨테이너의 프로세스를 넣는다.
- 상한은 컨테이너 안 프로세스 **전체의 합계**다.
- **옵션을 안 주면 상한이 없다.** 제한은 내가 걸어야 걸린다.
- cgroup도 namespace처럼 커널의 일반 기능이고, 컨테이너 전용이 아니다.

| | namespace | cgroup |
| --- | --- | --- |
| 나누는 것 | 보이는 범위 | 쓰는 양 |
| 없으면 | 옆 컨테이너가 보인다 | 옆 컨테이너의 자원을 뺏는다 |

### 6. 일반 프로세스와 컨테이너 프로세스

같은 `java -jar app.jar`를 그냥 실행한 것과 `docker run`으로 실행한 것을 비교한다.

| | 일반 프로세스 | 컨테이너 프로세스 |
| --- | --- | --- |
| 도는 곳 | 호스트 커널 위 | 호스트 커널 위 |
| 호스트의 `ps`에 나오나 | 나온다 | 나온다 |
| 커널 눈에는 | 프로세스 | 프로세스 |
| 들고 있는 namespace | 기본 세트 | 새로 만든 세트 |
| cgroup 상한 | 보통 없음 | 도커가 만든 cgroup (옵션을 주면 상한이 걸림) |
| 프로세스 목록을 물으면 | 컴퓨터 전체 | 자기 컨테이너 것만 |
| `/`를 물으면 | 호스트의 파일들 | 이미지에서 온 자기만의 파일들 |
| IP와 포트를 물으면 | 호스트의 IP, 포트는 같이 씀 | 자기만의 IP와 포트 장부 |

호스트에서 보면 둘은 구분이 안 되는 `java` 프로세스 한 줄씩이다. 다른 건 명찰과 상한뿐이다.

```text
컨테이너 = 호스트의 평범한 프로세스 + namespace 한 세트 + cgroup 하나
```

### 7. "그냥 프로세스"라서 생기는 성질

| 성질 | 이유 |
| --- | --- |
| 빨리 뜬다 | 부팅이 없고 프로세스 하나를 시작할 뿐이다 |
| 호스트에서는 다 보인다 | 호스트의 프로세스 목록에 그대로 나온다 |
| 메인 프로세스가 끝나면 컨테이너도 끝난다 | 컨테이너는 켜 두는 기계가 아니라 프로세스 그 자체다 |
| 커널은 못 바꾼다 | 컨테이너 안에서 보이는 커널은 호스트의 커널이다 |

컨테이너에서 맨 처음 띄운 프로세스가 **메인 프로세스**이고 컨테이너 안에서 PID 1이다. 다른 프로세스가 끝나도 컨테이너는 살아 있지만, PID 1이 끝나면 컨테이너가 멈추고 남은 프로세스도 커널이 정리한다. VM은 앱이 종료돼도 OS가 떠 있는 것과 다르다.

**컨테이너 하나에 앱 하나**는 할 수 없어서가 아니라 관례다. 커널은 프로세스가 몇 개든 상관하지 않는다. 편한 쪽은 도커와 운영하는 사람이다. 도커는 컨테이너의 상태, 재시작, 로그, 종료 신호를 **메인 프로세스 하나만 보고** 다루기 때문에, 메인이 아닌 앱은 죽어도 모른다. 관례는 정확히는 "프로세스 하나"가 아니라 "앱(역할) 하나"다. PostgreSQL처럼 혼자 프로세스를 여러 개 띄우는 앱도 컨테이너 하나에 둔다.

## 헷갈렸던 점

| 처음 생각 | 고친 생각 |
| --- | --- |
| 커널 == OS다 | 커널은 OS의 일부다. 배포판들은 커널이 같고 그 위의 것들이 다르다. 컨테이너가 공유하는 건 커널이다. |
| namespace가 많다는 게 무슨 말인가? | 큰 상자 하나가 아니라 주제별(PID, Mount, Network, UTS)로 종류가 따로 있다는 뜻이다. |
| 하나의 앱은 하나의 namespace에 묶인다 | 종류별로 하나씩, namespace 한 세트에 묶인다. 컨테이너 하나 = namespace 한 세트로 기억한다. |
| 여기저기 다른 공간에 같은 앱들이 있고, 주는 정보가 다르다 | 앱은 하나뿐이고 흩어져 있지 않다. namespace는 장소가 아니라 명찰이다. 묻는 주제에 따라 커널이 읽는 명찰이 다를 뿐이다. |
| 앱이 등록될 때 해당 namespace에 본인을 등록한다 | 명단에 올라가 있다는 그림은 맞다. 다만 앱이 스스로 등록하는 게 아니라 띄우는 쪽(도커)이 정한다. 앱은 모른다. |
| namespace를 가지는 건 컨테이너인가, 안의 앱인가? | 프로세스다. 커널에는 컨테이너라는 게 없다. 같은 세트를 든 프로세스들을 컨테이너라고 부른다. |
| cgroup은 컨테이너 하나에 대한 설정이다 | 도커를 쓰는 입장에서는 맞다. 상한은 컨테이너 안 프로세스 전체의 합계이고, cgroup 자체는 커널의 일반 기능이다. |
| 컨테이너 하나에는 프로세스 하나만 뜰 수 있다 | 여러 개 뜰 수 있다. 그중 메인(PID 1)이 수명을 정한다. |
| 커널 입장에서 하나만 떠 있어야 관리를 잘 해 준다 | 커널은 상관하지 않는다. 메인 프로세스 하나만 보는 도커와 운영하는 사람이 편한 것이다. |
| `ps`는 도커 명령이다 | 리눅스의 평범한 프로그램이고 커널에게 묻는다. `docker ps`는 도커 엔진에게 컨테이너 목록을 묻는 다른 명령이다. |
| 컨테이너 안에서 `ps`를 쳤으면 자기 것만 나오는 게 당연하다 | 당연한 건 맞다. 다만 컨테이너는 벽으로 막힌 방이 아니라서 원래는 다 보여야 한다. 그 당연함을 만드는 장치가 PID namespace다. |
| 호스트는 컨테이너 내부를 보지 않고, 컨테이너 하나를 프로세스 하나로 본다 | 호스트에서는 안이 다 보인다. 호스트가 보는 건 컨테이너가 아니라 프로세스 하나하나다. |

### 확인 문제

**문제 1.** 동료가 "컨테이너 안에서 `ps`를 치니 내 앱이 PID 1번이고 다른 프로세스가 없다. 그러면 컨테이너는 호스트와 완전히 분리된 작은 컴퓨터다"라고 한다. ① 왜 내 앱만 1번으로 보이는지 ② 그 앱은 호스트에서 보면 무엇인지 ③ 프로세스 목록 말고 같은 방식으로 나뉘는 것들

내 답:

> 1. 컨테이너는 하나의 프로세스라고 생각을 하면 되는거야 그리고 그 안에서는 하나의 앱만 돌고 있기 때문에 그런거야 물론 다양한 앱이 돌수는 있지만 보통 하나만 두고 작업을 하는게 통용적이긴해
> 2. 호스트는 컨테이너 내부의 상황을 보는게 아니라 컨테이너 하나를 프로세스로 생각하기 때문에 그냥 namespace 로 묶인 하나의 프로세스로 보고 이써
> 3. namespace, cgroup

채점: "컴퓨터가 아니라 프로세스다"라는 결론은 맞았다. 1번은 호스트의 프로세스가 왜 안 보이는지(PID namespace)가 빠졌다. 2번은 호스트가 컨테이너 내부를 못 본다고 한 게 반대다. 3번은 Mount, Network, UTS를 꼽아야 했고 cgroup은 해당하지 않는다.

문제 문장이 모호했던 탓도 있다. `ps`를 `docker ps`로 읽었고, 3번이 "PID 말고 다른 namespace 종류"를 묻는다는 게 드러나지 않았다. 소질문을 하나씩 다시 본 뒤 이렇게 고쳐 말했다.

> 아 그러니까 완전히 분리되었다는게 잘 못된 내용이구나 컨테이너는 호스트 커널이 관리하는거다 라고 하는게 중요한거였구나?? 하나 밖에 없던 이유는 해당 컨테이너에서는 컨테이너 내부의 앱들만 다루기 때문에 하나만 나온거고?

> 호스트에서 보면 평범한 그냥 앱 아냐?

> 아 프로세스 목록 말고 나뉘는 방식이 PID 말고를 얘기한거구나 mount, network, uts 이렇게 더 나뉜다는 말을 했어야 했구나

"다루는" 주체는 컨테이너가 아니라 커널이라는 점만 고쳤다. 다시 풀지는 않고 넘어갔다.

**문제 2.** 컨테이너 A(Spring Boot)와 B(PostgreSQL)를 자원 옵션 없이 띄웠다. A에 메모리 누수가 생겼고 B가 죽었다. ① 격리돼 있는데 왜 B가 영향을 받았나 ② 무엇을 해 뒀어야 했나 ③ 그랬다면 A는 어떻게 되나

내 답:

> 1. 컨테이너는 결국 같은 os 위에서 돌기 때문에 메모리 사용량을 공유한다 그래서 a가 너무 많은 공간을 사용하게 되면 b가 사용할 공간이 사라지면서 문제가 될 수 있다
> 2. cgroup 을 통해 이미지를 띄울때 상한 공간을 두기도 한다
> 3. 최대 상한을 치면...죽나??

채점: 통과. 보충하면 namespace의 격리는 보이는 범위만 나눌 뿐 쓰는 양은 나누지 않는다. 상한은 "이미지를 띄울 때"가 아니라 **컨테이너를 띄울 때** `--memory`로 건다. 3번은 맞다. 메모리 상한을 넘으면 커널이 A의 프로세스를 죽이고(OOM Kill) B는 무사하다. CPU였다면 죽지 않고 느려진다.
