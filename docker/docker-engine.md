# 도커 엔진은 어떻게 생겼을까?

[목차](README.md) · [이전: 컨테이너는 그냥 프로세스일까?](container-is-process.md)

## 다루는 범위

`docker run`이 커널에 닿기까지 거치는 부품(`docker` CLI, `dockerd`, `containerd`, `runc`, shim)과 각자의 역할, `dockerd`가 컨테이너와 호스트를 이어 주는 방식, Kubernetes가 `dockerd` 없이 도는 이유, Windows에서 이 부품들이 놓인 위치를 정리한다.

네트워크와 포트 매핑의 실제 동작은 10~13번, 볼륨은 8번, 오케스트레이션은 16번에서 다룬다.

## 시작한 질문

`docker run`을 치면 누가 커널에게 namespace와 cgroup을 만들어 달라고 할까? "도커"는 프로그램 하나일까?

## 내가 이해한 내용

### 1. `docker`는 입구이고, 요청을 받는 건 dockerd다

"도커"는 프로그램 하나가 아니다. 최소한 클라이언트와 서버로 나뉜다.

| | 이름 | 하는 일 |
| --- | --- | --- |
| 클라이언트 | `docker` (CLI) | 내가 친 명령을 API 요청으로 바꿔 보낸다. 명령 한 번에 떴다가 끝난다 |
| 서버 | `dockerd` (도커 데몬) | 계속 떠서 요청을 받는다. 컨테이너를 붙들고 있는 쪽이다 |

- 데몬은 백그라운드에 떠서 요청을 기다리는 프로그램이다. 톰캣이 HTTP 요청을 기다리는 것과 같고, 실제로 CLI와 `dockerd`는 HTTP API로 대화한다.
- 입구는 CLI가 아니어도 된다. Docker Desktop 화면이나 IntelliJ의 도커 탭도 같은 API로 `dockerd`에게 직접 요청한다.
- `docker ps`가 컨테이너 목록을 아는 건 CLI가 아니라 `dockerd`에게 물어서다.

### 2. dockerd → containerd → runc → 커널

`dockerd`도 컨테이너를 직접 만들지 않고 아래로 넘긴다.

```text
docker        명령을 전달하는 입구
   ▼
dockerd       도커의 기능 전체. 요청을 받아 지휘한다
   ▼
containerd    컨테이너의 일생을 관리한다 (시작, 정지, 감시)
   ▼
runc          커널에게 요청해서 컨테이너를 만들고 종료한다
   ▼
커널          namespace와 cgroup을 만들고 프로세스를 돌린다
```

| 도커 | Spring 비유 | 하는 일 |
| --- | --- | --- |
| `docker` CLI | 브라우저 | 요청을 보낸다 |
| `dockerd` | Controller | 요청을 받아 해석하고 아래로 넘긴다. 이미지 빌드, 네트워크, 볼륨, 재시작 정책을 맡는다 |
| `containerd` | Service | 이미지를 받아 보관하고, 컨테이너를 시작·정지·감시한다 |
| `runc` | Repository / JDBC | 커널에게 namespace와 cgroup을 만들게 하고 프로세스를 시작시킨다 |
| 커널 | DB | 실제로 수행한다 |

2번 주제의 질문 "누가 커널에게 namespace와 cgroup을 요청하나"의 답은 `runc`다.

### 3. runc는 잠깐 불려 오고, shim이 곁에 남는다

`runc`는 데몬이 아니다. 컨테이너에 커널 수준의 손질이 필요할 때 잠깐 불려 와서 일하고 종료한다. 이름은 "run container"를 줄인 것이다.

| 상황 | `runc`가 불려 오나 |
| --- | --- |
| `docker run` (컨테이너 만들기) | 온다. namespace와 cgroup을 만들고 프로세스를 시작한다 |
| `docker exec` (프로세스 추가) | 온다. 새 프로세스에 같은 namespace를 달아 시작한다 |
| `docker stop`, `docker rm` (종료·정리) | 온다 |
| 컨테이너가 돌고 있는 동안 | 없다 |
| `docker ps`, `docker build`, `docker network` | `runc`까지 안 내려간다 |

리눅스에서 모든 프로세스는 종료 코드를 받아 줄 부모가 있어야 한다. `runc`가 떠난 자리에서 컨테이너 곁을 지키는 작은 프로세스가 **shim**이고, 컨테이너마다 하나씩 붙는다.

```text
containerd
   └─ shim ── 컨테이너 A의 프로세스
   └─ shim ── 컨테이너 B의 프로세스
```

| | containerd | shim |
| --- | --- | --- |
| 몇 개인가 | 서버에 1개 | 컨테이너마다 1개 |
| 아는 것 | 모든 컨테이너의 목록과 상태 | 자기가 붙은 컨테이너 하나 |
| 결정하나 | 한다. 시작·정지 명령을 내린다 | 안 한다. 지켜보고 전달만 한다 |

shim은 컨테이너가 끝났는지 지켜보고, 출력(로그) 통로를 붙들고, containerd와 컨테이너를 떼어 놓는다. 사이에 shim을 끼운 가장 큰 이유는 containerd나 dockerd를 재시작해도 컨테이너가 같이 죽지 않게 하려는 것이다.

| 부품 | 떠 있는 기간 |
| --- | --- |
| `runc` | 컨테이너를 만드는 잠깐 |
| shim | 그 컨테이너가 살아 있는 동안 |
| `containerd`, `dockerd` | 계속 |

### 4. dockerd와 containerd의 차이

둘 다 데몬이지만 맡은 범위가 다르다. `containerd`는 "컨테이너를 돌린다"는 핵심 한 가지만 하고, `dockerd`는 그 위에 도커라는 제품의 편의 기능을 얹는다.

| | 없으면 |
| --- | --- |
| `runc` | 컨테이너를 만들 수 없다 |
| `containerd` | 컨테이너를 관리할 수 없다 |
| `dockerd` | 컨테이너는 돌릴 수 있다. `docker build`, `docker network`, `-p` 같은 도커의 편의 기능이 없다 |

> `containerd`는 컨테이너를 돌리는 엔진이고, `dockerd`는 그 엔진에 빌드·네트워크·볼륨과 쓰기 편한 명령을 붙여 만든 완성차다.

지금 구조로는 `containerd`가 공용 부품이고 `dockerd`가 도커 전용이다. 만들어진 순서는 반대로, 처음에 한 덩어리였던 도커에서 컨테이너를 돌리는 핵심을 떼어 낸 것이 `containerd`다. `runc`는 컨테이너를 만드는 방법의 표준(OCI) 구현체다.

`docker run nginx`에서 `dockerd`는 전체 순서를 지휘한다. 이미지가 있는지 확인하고, 없으면 받아 오게 하고, 네트워크와 볼륨을 준비한 뒤 `containerd`에게 시작을 넘긴다.

### 5. dockerd는 떨어진 것을 필요한 만큼 다시 이어 준다

컨테이너는 자기만의 Network namespace와 Mount namespace를 가져서 네트워크와 파일이 호스트와 떨어져 있다. `containerd`와 `runc`만으로 띄우면 컨테이너의 네트워크는 아무 데도 연결되지 않은 상태다.

| | 무엇을 잇나 | 어디에 만들어지나 |
| --- | --- | --- |
| 도커 네트워크, 포트 매핑(`-p`) | 컨테이너의 네트워크 ↔ 호스트의 네트워크 | 호스트 쪽 |
| 볼륨 | 컨테이너의 파일 시스템 ↔ 호스트의 저장 공간 | 호스트 쪽 |

> namespace가 컨테이너를 떼어 놓고, `dockerd`가 필요한 만큼만 다시 이어 준다.

주의할 점이 세 가지 있다.

- **컨테이너와 커널 사이에는 이어 줄 게 없다.** 컨테이너 프로세스는 처음부터 호스트 커널 위에서 돌고 시스템 콜로 직접 묻는다. 이어 주는 건 namespace 때문에 떨어진 네트워크와 파일이다.
- **끊겨 있는 건 네트워크 길이지 프로세스가 아니다.** 프로세스는 호스트의 `ps`에 멀쩡히 보인다.
- **`dockerd`는 길을 설정할 뿐, 패킷을 넘기는 건 호스트 커널이다.** 앱은 아무것도 모르고 평소처럼 8080을 연다.

`dockerd`와 커널이 아는 것은 다르다.

| | 아는 것 | 하는 일 |
| --- | --- | --- |
| `dockerd` | 의도 (어떤 컨테이너를, 어떤 이미지와 설정으로, 죽으면 다시 띄울지) | 의도를 구체적인 커널 요청으로 쪼갠다 |
| 커널 | 실행 상태 (namespace, cgroup 상한, 패킷을 넘기는 규칙) | 요청받은 대로 실행한다 |

커널은 요청받지 않으면 아무것도 만들지 않는다. 요청해서 만들어진 뒤에는 그 상태를 커널이 다 안다. "컨테이너를 운영한다"는 건 모른 채로 요청을 하나씩 수행할 뿐이다.

### 6. 도커는 컨테이너를 감싸지 않는다

```text
[흔히 그리는 그림]              [실제 구조]

┌─ 도커 ───────────┐           dockerd   컨테이너A   컨테이너B
│ ┌────┐  ┌────┐  │           (프로세스) (프로세스)  (프로세스)
│ │ A  │  │ B  │  │           ───────────────────────────────
│ └────┘  └────┘  │                    호스트 커널
└──────────────────┘
```

`dockerd`도 컨테이너도 호스트 커널 위의 프로세스로 나란히 있다. 관리 범위로 보면 도커가 다 관리하지만, 실행될 때 컨테이너가 도커 안에 있는 건 아니다. 하이퍼바이저가 VM 아래에서 실제로 감싸고 중계하는 것과 다르다.

들어가는 길은 둘이다.

| 들어가는 것 | 지나가는 길 |
| --- | --- |
| 관리 명령 ("띄워", "멈춰", "목록 보여 줘") | `docker` → `dockerd` → `containerd` → ... |
| 앱으로 가는 요청 (`GET /orders`) | 호스트의 포트 → 커널 → 컨테이너의 앱. 도커를 거치지 않는다 |

### 7. Kubernetes가 dockerd 없이 도는 이유

```text
도커:        docker → dockerd → containerd → runc
Kubernetes:          kubelet → containerd → runc
```

Kubernetes는 `dockerd`가 하던 일을 자기 방식으로 직접 하거나 필요로 하지 않는다.

| `dockerd`가 하던 일 | Kubernetes에서는 |
| --- | --- |
| 요청 받고 전체를 지휘 | kubelet |
| 네트워크 길 놓기 | 네트워크 플러그인 (CNI) |
| 저장 공간 잇기 | Kubernetes의 볼륨 기능 |
| 죽으면 다시 띄우기 | Kubernetes가 직접 |
| 이미지 빌드 | 안 한다. 만들어진 이미지를 받아 오기만 한다 |

남는 필요는 "이미지를 받아서 컨테이너를 돌리는 것"뿐이고, 그건 `containerd`와 `runc`로 충분하다. 이미지는 표준 형식(OCI)이라 도커로 만든 이미지가 그대로 돈다. "Kubernetes가 도커 지원을 중단한다"는 소식은 `dockerd`를 거치지 않게 됐다는 뜻이었다.

용어도 구분한다. 도커는 **서버 한 대**에서 사람이 시키는 대로 컨테이너를 **관리**하고, Kubernetes는 **여러 서버**에 걸쳐 원하는 상태를 알아서 맞추는 **오케스트레이션**을 한다.

### 8. Windows에서는 CLI만 Windows에 있다

```text
┌─ Windows ─────────────────────────────────────────────┐
│  docker (CLI)        Docker Desktop 화면               │
│      │ API 요청            │                           │
│  ┌───▼─────────────────────▼──── WSL2 VM (리눅스) ──┐  │
│  │  dockerd → containerd → runc                     │  │
│  │  [컨테이너 A]  [컨테이너 B]                       │  │
│  │  ───────────────────────────────                 │  │
│  │           리눅스 커널                             │  │
│  └──────────────────────────────────────────────────┘  │
│  하이퍼바이저 (Windows 기능)                            │
└────────────────────────────────────────────────────────┘
```

- Docker Desktop은 `dockerd`가 아니라, 이 전체를 설치하고 켜 주는 프로그램이다. Docker Desktop을 켠다는 건 WSL2 안의 `dockerd`와 `containerd`를 띄운다는 뜻이다.
- CLI는 요청만 보내는 통로라서 `dockerd`와 같은 곳에 있을 필요가 없다. 같은 원리로 원격 서버의 `dockerd`에 명령을 보낼 수도 있다.
- "호스트"라는 말은 구분해서 쓴다. CLI가 설치된 곳은 Windows(내 PC)이고, 컨테이너의 호스트는 WSL2 안의 리눅스다.
- 운영 서버는 대부분 리눅스라 VM 없이 바로 돈다. VM이 끼는 건 개발용 PC의 사정이다.

| Windows에서 겪는 일 | 이유 |
| --- | --- |
| Docker Desktop이 메모리를 많이 먹는다 | VM 하나가 통째로 떠 있다 |
| `localhost:8080`으로 컨테이너에 접속이 된다 | Windows의 `localhost`로 온 요청을 VM 안으로 넘기는 길이 놓여 있다 |
| Windows 폴더를 컨테이너에 연결하면 느리다 | 파일을 읽을 때마다 Windows와 VM의 경계를 넘는다 |

### 9. CLI는 어디로 보낼지 알아야 한다

CLI에는 `dockerd`의 주소가 설정돼 있고, 설치할 때 자동으로 잡힌다.

| 환경 | 기본으로 보내는 곳 |
| --- | --- |
| 리눅스 | `/var/run/docker.sock` 소켓 파일. `dockerd`가 뜨면서 만들고, CLI는 이 경로를 기본값으로 안다 |
| Windows + Docker Desktop | Windows의 named pipe. Docker Desktop이 만들어 VM 안의 `dockerd`로 이어 준다 |

- 둘 다 같은 컴퓨터 안에서 프로세스끼리 대화하는 통로다. 네트워크 포트를 열지 않아 아무나 접속하지 못한다. `docker.sock`은 "`dockerd`로 들어가는 문"이다.
- 바꾸려면 `DOCKER_HOST` 환경 변수, `-H` 옵션, `docker context`를 쓴다.
- `Cannot connect to the Docker daemon` 에러는 설정된 주소에서 받아 주는 `dockerd`가 없다는 뜻이다. `dockerd`가 안 떠 있거나 주소가 잘못 잡혀 있다.

## 헷갈렸던 점

| 처음 생각 | 고친 생각 |
| --- | --- |
| `dockerd`가 실제로 일을 다 한다 | `dockerd`도 컨테이너를 직접 만들지 않고 `containerd`와 `runc`에게 넘긴다. Controller가 SQL을 직접 날리지 않는 것과 같다. |
| containerd가 관리도 안 하고 shim에게 맡긴다 | 판단과 기록은 containerd가 한다. shim은 컨테이너 곁에 세워 둔 연락원으로, 지켜보고 전달만 한다. |
| dockerd와 containerd는 뭐가 다른가? | containerd는 컨테이너를 돌리는 핵심만, dockerd는 도커가 편하게 쓰이도록 얹은 기능이다. Kubernetes가 무엇을 버렸는지 보면 구분된다. |
| containerd가 공용이고, 거기에 dockerd를 붙였다 | 지금 구조는 그렇다. 순서는 반대로, 한 덩어리였던 도커에서 containerd를 떼어 냈다. |
| 네트워크와 포트 매핑은 컨테이너 앱이 아니라 "docker VM"의 일이다 | 앱 밖에서 일어나는 건 맞다. 그 자리는 VM이 아니라 호스트다. `dockerd`가 호스트에 설정하고 호스트 커널이 수행한다. |
| 도커가 컨테이너들을 감싸고 있다 | 관리 범위로는 맞지만, 실행될 때는 호스트 커널 위에 나란히 있다. 요청과 시스템 콜은 도커를 거치지 않는다. |
| 들어가는 입구는 `docker`다 | 관리 명령의 입구는 맞다. 앱으로 가는 요청은 도커를 거치지 않는 다른 길이다. |
| 도커가 컨테이너를 오케스트레이션한다 | 지휘한다는 뜻으로는 맞는 감각이다. 다만 오케스트레이션은 여러 서버에 걸친 관리를 가리키는 용어라 도커에는 "관리"를 쓴다. |
| 컨테이너와 호스트 커널을 매핑해 주는 게 dockerd다 | 컨테이너와 커널은 원래 직접 붙어 있다. dockerd가 잇는 건 컨테이너의 네트워크·파일과 호스트의 네트워크·저장 공간이다. |
| containerd만 쓰면 컨테이너가 둥둥 떠다니고, dockerd가 호스트에게 알려 준다 | 떠다니는 건 네트워크다. 호스트 커널은 그 프로세스를 이미 안다. 알려 주는 게 아니라 길을 놓는다. |
| dockerd가 알려 주지 않으면 커널은 컨테이너의 설정을 모른다 | 커널이 모르는 건 의도다. 요청받아 만든 namespace, cgroup, 규칙은 커널이 다 안다. 요청이 없으면 아무것도 만들지 않는다는 뜻으로는 맞다. |
| `runc`는 사용자가 원하는 명령을 실제로 한다 | 컨테이너를 만들고, 프로세스를 넣고, 정리할 때만 잠깐 불려 온다. `docker ps`나 `docker build`는 `runc`까지 안 내려간다. |

### 확인 문제

**문제 1.** Docker Desktop이 켜진 Windows에서 `docker run nginx`를 쳤다. ① 거치는 부품의 순서 ② 각 부품이 맡은 일 ③ Windows와 WSL2 중 어디에 있는지

내 답:

> 1. docker cli -> dockerd -> containerd -> runc
> 2. docker cli 는 실제 일을 하는 dockerd 로 전달을 하고 그 작업을 containerd 에게 맡기고 containerd 는 실제로 그 작업을 할 수 있는 runc 에게 맡긴다
> 3. docker cli 만 windows 에 존재하고 나머지 부품은 모두 wsl2 에 존재한다

채점: 통과. 순서와 위치는 정확하다. 2번은 넘기는 흐름만 있고 각자의 일이 빠져서, 왜 부품이 넷으로 나뉘는지가 안 보인다. 순서의 맨 끝에 커널이 있다. 채점 뒤에 이렇게 고쳐 말했다.

> dockerd 는 도커의 네트워크, 볼륨과 같은 도커의 전반적인 기능을 맡고 containerd 는 각 컨테이너의 전반적인 생명주기를 책임진다 그리고 실제로 사용자가 원하는 명령을 하는 것은 runs 이다

앞의 둘은 정확하다. `runc`는 "명령 전부"가 아니라 컨테이너를 만들고 프로세스를 넣고 정리하는 일만 한다.

**문제 2.** 동료가 "Kubernetes는 `dockerd` 없이 `containerd`만 쓴다는데, 도커로 만든 이미지를 못 돌리는 거 아니냐, `dockerd` 없이 어떻게 컨테이너가 도느냐"고 묻는다. ① `dockerd` 없이 돌 수 있는 이유 ② `dockerd`가 하던 일은 어떻게 되나 ③ 이미지를 그대로 쓸 수 있는 이유

내 답:

> 1. 기존의 dockerd 는 컨테이너와 호스트 커널사이에서 연결을 해주는 역할과 도커의 설정 전반적인것을 관리할 수 있도록 했다 실제로 컨테이너의 생명주기를 관리하는건 containerd 라는 애이기 때문에 중요한건 containerd 와 runc 다
> 2. 그래서 쿠버네티스는 도커에 의존하지 않기 위해 스스로 dockerd 의 역할을 할 수있게 만들어놓았다
> 3. 도커에 만들어진 이미지를 가져오는걸 하고 이미지는 containerd 를 이용해서 띄우기 때문에 가능하다

채점: 통과. 1번의 "컨테이너와 호스트 커널 사이의 연결"은 "컨테이너의 네트워크·파일과 호스트의 네트워크·저장 공간 사이의 연결"로 고친다. 2번은 맞고, kubelet·네트워크 플러그인·볼륨 기능이 나눠 맡는다고 하면 더 구체적이다. 3번은 아래 두 층이 같다는 이유는 맞게 짚었고, 이미지 형식이 표준(OCI)이라는 이유가 빠졌다.
