# 이미지와 컨테이너는 뭐가 다를까?

[목차](README.md) · [이전: 도커 엔진은 어떻게 생겼을까?](docker-engine.md)

## 다루는 범위

이미지와 컨테이너의 관계, 컨테이너가 이미지를 복사하지 않고 쓰기 층만 따로 갖는 구조, 이미지를 이루는 레이어와 베이스 이미지, 레이어를 겹쳐 컨테이너의 `/`로 보여 주는 OverlayFS, 그리고 Dockerfile·이미지·컨테이너가 만들어지고 읽히는 시점을 정리한다.

Dockerfile의 명령이 각각 어떤 레이어를 만드는지는 5번, 이미지를 작게 만드는 방법은 6번, 볼륨은 8번에서 다룬다.

## 시작한 질문

이미지는 바뀌지 않는다는데, 컨테이너는 어떻게 파일을 쓰고 고칠까? 이미지 하나로 컨테이너를 여러 개 띄우면 이미지도 여러 벌이 될까?

## 내가 이해한 내용

### 1. 이미지는 굳어 있는 틀이고, 컨테이너는 그걸 실행한 것이다

| | 이미지 | 컨테이너 |
| --- | --- | --- |
| 무엇인가 | 실행 환경을 굳혀 놓은 파일 묶음 | 그 이미지로 띄운 실행 중인 프로세스 |
| 바뀌나 | 안 바뀐다 (읽기 전용) | 돌면서 파일을 쓰고 지울 수 있다 |
| 어디에 있나 | 도커의 저장 공간, 레지스트리 | 호스트 커널 위의 프로세스 |

| 저장된 것 | 실행하는 주체 | 실행된 결과 |
| --- | --- | --- |
| `app.jar` | OS | 프로세스 |
| 이미지 | 도커 (`dockerd` → `containerd` → `runc`) | 컨테이너 |

- 이미지 하나로 컨테이너를 여러 개 띄울 수 있다. 같은 파일에서 출발했지만 서로 다른 프로세스다.
- **컨테이너는 이미지를 실행하는 주체가 아니라 실행한 결과다.** 빈 상자가 먼저 있고 이미지를 넣어 돌리는 게 아니라, 이미지를 실행하는 순간 컨테이너가 생긴다.
- 그림 비유: 매장(레지스트리)에서 똑같은 그림(이미지)을 사 가지만, 집마다 걸린 그림(컨테이너)은 따로 다뤄진다. 원본 그림은 어디서나 같고, 달라지는 건 각 집에서 그 위에 생기는 변화다.

### 2. 이미지는 호스트에 한 벌이고, 컨테이너는 그걸 같이 본다

이미지는 컨테이너에 받는 게 아니라 **호스트(도커의 저장 공간)에** 받는다.

```text
[레지스트리] ──docker pull──▶ [호스트의 저장 공간] ──docker run──▶ [컨테이너]
                복사해 옴        (이미지 한 벌)        복사 안 함     (같이 봄)
```

컨테이너는 뭔가를 담는 상자가 아니라 프로세스다. 프로세스는 파일을 갖고 있지 않고 디스크의 파일을 읽을 뿐이다. 서버에서 `app.jar` 하나로 `java -jar`를 세 번 실행해도 `app.jar`가 세 개가 되지 않는 것과 같다.

```text
[도커 저장 공간]
  my-app 이미지 (한 벌)
     ▲   ▲   ▲      같은 파일을 읽어서 실행
  컨테이너1 컨테이너2 컨테이너3
  (쓰기 층) (쓰기 층) (쓰기 층)
```

컨테이너마다 따로 갖는 건 프로세스(메모리), namespace 세트와 cgroup, 쓰기 층이다. 디스크는 이미지 한 벌에 각자 바꾼 만큼만 더 들고, 메모리는 프로세스마다 따로 쓴다.

### 3. 쓰기 층: 고칠 때만 그 파일을 가져와서 고친다

컨테이너는 이미지 위에 **쓰기 층 한 장**을 얹는다. 원본 그림 위에 투명 필름을 덮고 필름에만 그리는 것과 같다.

| 동작 | 실제로 일어나는 일 |
| --- | --- |
| 읽기 | 쓰기 층에 있으면 그걸, 없으면 이미지의 것을 읽는다 |
| 새 파일 쓰기 | 쓰기 층에 만든다 |
| 이미지에 있던 파일 고치기 | 그 파일을 쓰기 층으로 복사한 뒤 복사본을 고친다 (Copy-on-Write) |
| 이미지에 있던 파일 지우기 | 쓰기 층에 "없는 걸로 쳐" 표시를 남긴다 |

이미지에 `config.yml`(`port=8080`)이 있고 컨테이너 1이 이를 `port=9090`으로 고치면 이렇게 된다.

| | 컨테이너 1의 쓰기 층 | 컨테이너 2의 쓰기 층 | 이미지 |
| --- | --- | --- | --- |
| `config.yml` | `port=9090` (복사본) | (없음) | `port=8080` (그대로) |

- 컨테이너를 띄울 때는 아무것도 복사하지 않는다. 고치는 파일만, 고치는 순간에 가져온다.
- 쓰기 층은 프로세스 안이 아니라 **호스트 디스크의 폴더**다. 프로세스는 고치는 주체이고, 결과가 남는 곳은 쓰기 층이다.
- 파일을 쓰는 건 대부분 사람이 아니라 앱이다(로그, 임시 파일, 업로드 파일). 쓰기 층이 없으면 대부분의 앱은 파일을 못 써서 뜨다가 죽는다.
- 운영 중인 컨테이너에 들어가서 고치는 일은 하지 않는다. 컨테이너는 고쳐 쓰는 게 아니라 갈아 끼우는 것이다. 바꿀 게 있으면 Dockerfile을 고쳐 이미지를 다시 만든다.

"껐다 켠다"는 두 가지가 다르다.

| 하는 일 | 명령 | 쓰기 층 | 고친 내용 |
| --- | --- | --- | --- |
| 멈췄다가 다시 시작 | `docker stop` → `docker start` | 남아 있다 | 남아 있다 |
| 지우고 새로 띄움 | `docker rm` → `docker run` | 지워지고 빈 것이 새로 생긴다 | 리셋된다 |

배포, Compose의 `down` → `up`, Kubernetes의 재시작은 모두 새로 만드는 쪽이라, 쓰기 층에 쓴 건 언제든 사라질 수 있다고 보고 쓴다.

### 4. 이미지도 레이어 여러 장이 쌓인 것이다

```text
┌──────────────────────────┐
│ 쓰기 층 (컨테이너 전용)    │  ← 컨테이너를 띄울 때 얹음
├──────────────────────────┤
│ 레이어 3: app.jar         │ ┐
│ 레이어 2: JDK 21          │ ├ 이미지 (읽기 전용)
│ 레이어 1: Ubuntu의 파일들  │ ┘
└──────────────────────────┘
```

- 레이어 한 장은 바로 아래에서 달라진 파일들만 담는다.
- **쌓이는 단위는 레이어, 가져다 쓰는 단위는 이미지**다. 이미지 = 레이어 여러 장을 순서대로 쌓은 것에 이름과 실행 설정이 붙은 것.
- 이미지는 여전히 실행 환경이 통째로 든 완성품이다. 다만 저장된 모양이 "이 레이어들을 이 순서로 겹쳐라"라는 목록이다.

`FROM`으로 기존 이미지(베이스 이미지)를 지정하면 그 이미지의 레이어들이 바닥에 들어오고, 내 명령이 그 위에 레이어를 얹는다. 모든 이미지가 실행 환경을 바닥부터 하나하나 만드는 게 아니다.

```text
my-app            FROM eclipse-temurin:21-jre  →  jar를 얹음
eclipse-temurin   FROM ubuntu                  →  JDK를 얹음
ubuntu            (맨 바닥)                     →  Ubuntu의 기본 파일들
```

"기존 이미지를 바닥에 깐다"는 말은 "그 이미지의 레이어들 위에 레이어를 더 얹는다"로 읽는다. 최종 이미지 안에는 이미지 속의 이미지가 아니라 레이어들이 한 줄로 쌓여 있다.

같은 레이어는 한 벌만 두고 여러 이미지가 같이 쓴다.

| | 통짜였다면 | 레이어라서 |
| --- | --- | --- |
| 디스크 | 이미지마다 전체 | 같은 레이어는 한 벌 |
| 내려받기 | 매번 전체 | 없는 레이어만 (`Already exists`) |
| 올리기 | 매번 전체 | 바뀐 레이어만 |

### 5. OverlayFS: 따로 보관하고, 겹쳐서 하나로 보여 준다

레이어 한 장은 도커 저장 공간의 폴더 하나다. 쓰기 층도 폴더 하나다.

```text
폴더 A (Ubuntu)      폴더 B (JDK)           폴더 C (app.jar)     폴더 W (쓰기 층)
  bin/sh              opt/java/bin/java      app.jar
  etc/hosts
     └────────────────┴──────────────────────┴───────────────────┘
                          OverlayFS가 겹침
                                ▼
                 컨테이너의 "/" : bin, etc, opt, app.jar
```

- 파일은 여전히 따로 있고, 보이는 모습만 하나다. 실제로 한 곳에 모아 복사하지 않는다.
- 겹치는 일은 도커가 아니라 **리눅스 커널의 기능(OverlayFS)**이 한다. 도커는 어떤 폴더를 어떤 순서로 겹칠지 알려 줄 뿐이다.
- 겹쳐지는 건 **그 컨테이너를 띄운 이미지 하나의 레이어들과 자기 쓰기 층**이다. 호스트의 다른 이미지는 안 보인다.
- 2번 주제의 Mount namespace가 보여 주는 "나만의 `/`"의 정체가 이 겹쳐진 결과다. PID namespace가 프로세스 목록을 걸러 대답하듯, 커널이 `/`에 대해 겹친 결과를 대답한다.

"폴더"라는 형태보다 **따로 보관된다**는 점이 중요하다. 합쳐서 저장하면 레이어 공유, 바뀐 것만 옮기기, 원본 보호, 이미지 한 벌을 같이 보기가 모두 안 된다. 보관은 따로, 보이는 건 하나로 하는 구조다.

| 커널 기능 | 컨테이너에게 주는 것 |
| --- | --- |
| namespace | 좁혀진 시야 |
| cgroup | 자원의 상한 |
| OverlayFS | 이미지와 쓰기 층을 겹친 파일 시스템 |

### 6. 도커 엔진의 저장 공간

도커 엔진이 관리하는 전용 저장 공간이 **호스트에 전역으로 하나** 있다. Windows에서는 WSL2 VM 안에 있다.

```text
[도커 엔진의 저장 공간]
  ├─ 이미지 레이어들        읽기 전용. 이미지를 지울 때 지워진다
  ├─ 컨테이너의 쓰기 층들    컨테이너를 지울 때 같이 지워진다
  └─ 볼륨들                 컨테이너를 지워도 남는다. 직접 지워야 지워진다
```

- 도커가 어느 이미지가 어느 레이어를 쓰는지 장부로 관리한다. 사람이 그 폴더를 직접 건드리지 않는다.
- DB를 도커로 띄울 때 데이터를 두는 곳이 볼륨이다. 같은 저장 공간 안이지만 쓰기 층과는 다른 칸이고, 임시가 아니라 오래 남기려고 만든다.

### 7. Dockerfile, 이미지, 컨테이너는 서로 다른 것이고 읽히는 때도 다르다

| 설명서 | 결과물 |
| --- | --- |
| `build.gradle` + 소스 코드 | `app.jar` |
| Dockerfile | 이미지 |

```text
[만들기]
docker build (내가 침)
   → dockerd(빌더)가 Dockerfile을 읽는다
   → 없는 베이스 이미지를 받아 오고, 레이어 폴더를 채운다
   → 이미지 생성

        ── 끊김. 따로 명령을 쳐야 이어진다 ──

[띄우기]
docker run (내가 침)
   → dockerd가 요청을 받는다
   → containerd가 이미지를 읽고 레이어를 준비한다
   → runc가 커널에게 요청해 프로세스를 시작시킨다
   → 컨테이너
```

| | `dockerd` (빌더) | `containerd` / `runc` |
| --- | --- | --- |
| 언제 | `docker build` | `docker run` |
| 무엇을 읽나 | Dockerfile | 이미지 (레이어들 + 실행 설정) |
| 하는 일 | 이미지를 만든다 | 컨테이너를 띄운다 |
| 없는 게 있으면 | `FROM`의 베이스 이미지는 자동으로 받아 온다. 그 밖에는 적힌 명령만 실행하고, 안 되면 빌드 실패 | 이미지 통째는 받아 온다. 안의 내용은 못 채우고, 없으면 실행 실패 |

- Dockerfile의 `CMD`는 레이어가 아니라 "시작 명령"이라는 **설정**으로 이미지에 옮겨 적힌다. 띄울 때 읽는 건 Dockerfile이 아니라 이 설정이다. 그래서 Dockerfile이 없는 서버에서도 컨테이너가 뜬다.
- `COPY build/libs/app.jar /app.jar`에는 위치가 세 개 얽힌다. ① 내 프로젝트의 원본 ② 도커 저장 공간의 레이어 폴더(도커가 자동으로 만든다) ③ 컨테이너에서 보이는 경로. 적는 건 ①과 ③이다.
- 띄울 때는 이미지에 든 것만 쓴다. 그래서 필요한 건 전부 만들 때 넣어야 하고, 그래서 어디서 띄워도 같은 환경이 나온다.
- 컨테이너는 이미지를 갖고 있지 않지만, 이미지에서 태어나고 도는 내내 이미지의 파일을 직접 읽는다(커널을 통해). 시작시키는 건 `containerd`와 `runc`이고, 뜬 뒤에 파일을 읽는 건 컨테이너의 프로세스다.

| 컨테이너가 뜨자마자 죽을 때 | 볼 곳 |
| --- | --- |
| 아예 시작이 안 된다 | 이미지에 시작 명령의 프로그램이 없거나 경로가 틀렸다 |
| 떴다가 바로 죽는다 | 앱이 필요한 파일이나 설정을 못 찾았다. `docker logs`를 본다 |

## 헷갈렸던 점

| 처음 생각 | 고친 생각 |
| --- | --- |
| 원본 이미지를 건드리지 않으려고 이미지를 복사해 간다 | 원본을 안 건드리는 건 맞다. 하지만 복사하지 않고 같이 본다. 고치는 파일 하나만 고치는 순간에 쓰기 층으로 가져온다. |
| 컨테이너에 이미지를 받는다 | 이미지는 호스트의 저장 공간에 받는다. 컨테이너가 받는 건 빈 쓰기 층뿐이다. |
| 호스트가 받아서 같이 본다는 게 이상하다 | 컨테이너를 상자로 떠올려서 그렇다. 컨테이너는 프로세스이고, `app.jar` 하나로 프로세스를 여러 개 띄우는 것과 같다. |
| 파일을 수정하면 프로세스를 수정하는 것이다 | 수정되는 건 파일이고, 그 컨테이너의 쓰기 층(디스크)에 남는다. |
| 컨테이너에 들어가서 직접 수정하는 경우가 있나? | 운영에서는 하지 않는다. 쓰기 층은 앱이 돌면서 쓰는 로그와 임시 파일을 받아 주는 곳이다. |
| 이미지는 실행 환경 통째가 아니라 기존 이미지를 이용하는 것이다 | 둘 다 맞다. 완성품이면서, 저장된 모양은 기존 이미지의 레이어 위에 내 레이어를 얹은 목록이다. |
| 여러 이미지가 층층이 쌓여 하나의 이미지가 된다 | 쌓이는 단위는 레이어다. `FROM`에 적는 건 이미지 이름이고, 그 결과 들어오는 건 그 이미지의 레이어들이다. |
| Dockerfile이 실행될 때(컨테이너를 띄울 때) 명령을 본다 | Dockerfile은 `docker build` 때만 읽힌다. `docker run` 때는 만들어진 이미지를 읽는다. |
| 컨테이너의 `/`는 도커가 가진 모든 이미지를 보여 준다 | 그 컨테이너를 띄운 이미지 하나의 레이어들과 자기 쓰기 층만 겹쳐 보여 준다. |
| DB 데이터를 두는 폴더가 레이어를 두는 그 폴더다 | 같은 도커 저장 공간 안이지만 다른 칸(볼륨)이다. 임시가 아니라 오래 남기는 쪽이고, 볼륨을 직접 지워야 지워진다. |
| 컨테이너가 이미지를 실행한다 | 도커가 이미지를 실행하면 그 실행된 것이 컨테이너다. |
| 컨테이너는 이미지와 크게 상관이 없고 시키는 걸 할 뿐이다 | 갖고 있지 않을 뿐 깊게 의존한다. 보이는 파일, 시작 명령, 기본 설정이 모두 이미지에서 온다. |
| Dockerfile에 적힌 명령을 containerd가 본다 | containerd가 읽는 건 이미지에 옮겨 적힌 설정이다. 이미지와 Dockerfile은 다른 것이다. |
| containerd가 실행하다 없는 게 있으면 받아 온다 | 이미지 통째만 받아 올 수 있다. 이미지 안에 빠진 건 못 채우고 실패한다. |
| 쓰기 층에 고친 건 껐다 켜면 리셋된다 | `stop` → `start`면 남고, `rm` → `run`이면 리셋된다. |

### 확인 문제

**문제 1.** 500MB짜리 이미지로 컨테이너 3개를 띄웠다. 동료가 "디스크를 1.5GB 쓰겠네. 컨테이너 1에서 설정 파일을 고치면 이미지가 바뀌니까 2와 3도 바뀌겠지?"라고 한다. ① 1.5GB를 쓰지 않는 이유 ② 고친 내용은 어디에 남고 이미지와 나머지 컨테이너는 어떻게 되나

내 답:

> 1. 일단 우리가 사용하는 app 은 도커에 하나의 파일로써 저장이 되고 컨테이너는 그걸 실행시켜주는거라서 갯수에 따라 메모리를 일정하게 500mb 를 차지하지는 않아 그리고 또 말했듯이 특정 파일을 실행시키는거라서 각 컨테이너는 서로 다른 앱을 연거야 그냥 코드만 같을뿐이라서 설정을 바꿀 꺼면 모든 컨테이너에 들어가서 수정해줘야해

채점: 통과. 이미지가 하나만 저장되고 컨테이너끼리 영향이 없다는 결론은 맞다. "메모리"는 "디스크"로 고친다. 메모리는 프로세스마다 따로 쓴다. 2번은 고친 내용이 그 컨테이너의 **쓰기 층**에 남고, 이미지가 읽기 전용이라 그대로라는 이유가 빠졌다. 채점 뒤에 "해당 변경 내용은 쓰기 층에 남지"라고 직접 말했다.

**문제 2.** `order`와 `payment` 이미지가 둘 다 `FROM eclipse-temurin:21-jre`에서 시작해 jar만 `COPY` 한다. 한 서버에 둘 다 받아 띄웠다. ① JDK 파일이 두 벌 저장되나 ② 컨테이너 안에서 JDK와 `app.jar`가 한 곳에 있는 것처럼 보이는데, 실제로는 어떻게 보관되고 무엇이 그렇게 보여 주나

내 답:

> 1. 두 벌이 아니라 한 벌, containerd 가 이미지를 실행할때 기존에 도커의 폴더 공간을 확인하는데 이미 있는 파일은 그대로 사용하기 때문에 공유하여 실행해
> 2. 원래는 각 폴더에 따라 종류 별로 저장이 되는데 이걸 일일히 보기 어려우니까 리눅스의 기능인 overlayF뭐시기가 그렇게 보여준다

채점: 통과. 1번은 한 벌이고 같이 쓴다는 게 맞다. 같이 쓰는 단위가 **레이어**라는 것과, 공유가 정해지는 때가 실행할 때가 아니라 **이미지를 받거나 만들 때**(없는 레이어만 받는다)라는 점을 보충했다. 2번은 맞다. "종류별"이 아니라 "레이어별"로 보관되고, 겹쳐 보여 주는 이유는 앱이 평범한 `/`를 보며 돌게 하려는 것이다. 이름은 OverlayFS다.
